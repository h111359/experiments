## Overview

- Request ID: R-20260727-0906
- Request title: Make AIB context upgrades selective

### Background

The current AIB upgrade path archives `.aib_memory/` but then always replaces `context.md` and the registered Context Data Model extension with seed artifacts, forcing semantic migration or regeneration even when their governing conventions are unchanged. The request seeks to prevent avoidable rewriting and information loss by making compatibility an artifact-level convention-version decision rather than a consequence of an overall AIB SemVer mismatch.

### Scope

The change covers context and context-extension convention metadata, artifact metadata, validators, selective upgrade classification and restoration, the single-run migration/refresh directive consumed by `aib-modify.md`, migration-completion gating, automated upgrade and validation tests, current workspace context artifacts, internal README guidance, and the self-contained user guide.

### Out of scope

The change does not alter archive creation, request/input preservation rules, the lossless semantic migration algorithm, overall AIB SemVer rules, non-context memory upgrade behavior, network behavior, or the standard-library-only implementation constraint.

## Input Interpretation

### User Original Inputs

- Initial input: Avoid semantic context upgrades when a higher AIB version does not change the applicable context convention, because unnecessary rewriting can lose or corrupt collected information.
- Goal: Make context upgrades selective so artifacts whose conventions remain compatible are not migrated or regenerated.
- Stakeholders and value: Preserve AIB users' collected context; let maintainers evolve the main context and registered extensions independently; determine safety from artifact conventions rather than overall AIB SemVer.
- Required behavior: Continue the existing memory upgrade on brain/memory version mismatch; independently version `context.md` and every registered extension; place a positive-integer `convention_version` in each artifact's YAML frontmatter and declare the expected version in its convention; increment the convention version when the convention changes; compare applied and expected versions; preserve compatible artifacts unchanged; semantically migrate incompatible main context; refresh incompatible extensions through their registered prompts; preserve compatible siblings; treat missing/invalid metadata as incompatible; generate one complete migration directive; show the completion gate only when work exists; otherwise mark the upgrade compatible without instructions or confirmation.
- Scope: Conventions, validators, compatibility detection, preservation, migration/refresh orchestration, completion-menu behavior, tests, documentation, and product-context updates.
- Exclusions: Archive behavior, non-context upgrade behavior, active-request or old-input preservation, semantic-migration algorithm changes, and overall SemVer rules.
- Constraints: Python standard library only, no network access, model-agnostic prompts, byte-for-byte preservation of compatible artifacts, and continued use of registered refresh prompts.
- Acceptance: Cover all-compatible, main-only, extension-only, mixed, missing/invalid-metadata, aggregate-directive, post-migration validation, tests, and documentation scenarios.

### AI interpretation

- A brain/memory SemVer mismatch remains the trigger for the existing destructive memory-upgrade lifecycle, including timestamped archive creation and non-context reseeding.
- Immediately after archival, AIB must classify the archived main context and each extension registered by the upgraded framework against the expected positive-integer version declared by the corresponding current convention.
- Compatible artifacts must be restored from the archive without decoding and rewriting their content, so their bytes—including whitespace and line endings—remain identical.
- An incompatible main context must continue through `aib-context-migration.md`; each incompatible extension must be regenerated independently by the refresh prompt registered for it; one artifact's incompatibility must not cause compatible siblings to be regenerated.
- Missing, malformed, non-positive, or otherwise unacceptable version metadata is an incompatibility signal, not permission to discard the archive or silently treat the artifact as current.
- `initialize.py --upgrade` must produce one deterministic `input.md ## Input` directive containing the complete affected-artifact set and enough prompt/source metadata for one `aib-modify.md` execution to finish all required work.
- `memory_version_compatibility` must be `compatible` immediately when no artifact needs work and must enter the existing pending state only when at least one artifact needs migration or refresh.
- Refresh and migration prompts must stamp the expected convention version into their output, and validators must reject artifacts that are missing, invalid, or do not match their corresponding convention after processing.
- Assumption: The request is prioritized for the current iteration because the existing unconditional rewrite presents a direct information-retention risk; if deferred, future upgrades can continue to rewrite valid collected context.
- Assumption: The current managed Context Data Model is the first registered extension, but the upgrade algorithm must iterate registry metadata so future registered extensions do not require a bespoke compatibility branch.

### Issues and Risks

- A compatible extension can be lost if the implementation clears memory before recording its classification or restores only the main context.
- A new extension introduced by the upgraded brain can be missed if discovery relies solely on the archived registry; a removed legacy extension can be incorrectly restored if discovery relies solely on archived entries.
- Treating only lower artifact versions as incompatible would allow an artifact from a newer/unknown convention to pass an older validator; exact mismatch behavior needs an explicit decision.
- A registered extension with `Update: no` creates a policy conflict between user refresh preference and mandatory convention migration.
- If a convention or refresh prompt is missing, AIB cannot safely determine compatibility or complete regeneration; the current generic warning-and-continue behavior is insufficient for a pending upgrade without an explicit failure contract.
- Re-seeding an incompatible artifact before its refresh makes it structurally valid but semantically empty; the completion gate and directive must remain pending until the refresh has actually run.
- Partial multi-artifact success can leave a mixture of migrated and pending artifacts; retry behavior and directive retention must be deterministic.
- Manual completion confirmation can mark migration compatible even if a required refresh was skipped unless validators and directive completion are checked before confirmation.
- The requirement to increment versions on every convention change cannot be proven from one checkout without either a stored baseline/fingerprint or VCS-aware enforcement.
- Strict frontmatter parsing can accidentally reject future metadata keys; permissive parsing can conceal duplicate or ambiguous `convention_version` declarations.
- Validator check-count changes can break documentation and tests even if behavior is correct; folding version validation into existing checks provides less granular failure reporting.
- Compatible byte preservation must be tested with CRLF/LF, trailing whitespace, non-ASCII text, and no-final-newline cases rather than only semantic equality.
- Upgrade classification must prevent registry paths from escaping the workspace and must never execute arbitrary prompt paths obtained from an untrusted archived artifact.

## Proposed Solution

### High-Level Concept

Introduce a shared strict convention-version contract, classify each current registered context artifact independently during the existing upgrade, restore compatible archive bytes unchanged, and create one pending migration/refresh directive only for incompatible artifacts. Refresh/migration outputs and validators will enforce the same contract so the menu can skip the completion gate when no work exists.

## Decision Register

### Decision Points

#### Decision Point: Convention declaration format

- Tag: ask
- Applies to: Task 1 convention metadata and Task 2 parsers; the request specifies artifact YAML frontmatter but not the machine-readable declaration syntax inside convention files.
- Alternative A — YAML frontmatter in conventions: Put `convention_version: <positive integer>` in a YAML frontmatter block at the top of each convention; consistent parser and explicit document metadata, but changes convention title placement and requires body-aware tooling; impacts both conventions and shared parsing.
- Alternative B — Dedicated convention body line: Put one exact `Convention-Version: <positive integer>` line after the convention title; preserves title-first convention files, but requires separate parsing rules for convention and artifact metadata; impacts both conventions and shared parsing.
- Alternative C — Named metadata section: Add a `## Convention Metadata` section containing the integer; human-readable and extensible, but more complex to parse deterministically and easier to duplicate; impacts both conventions and shared parsing.
- Rationale/Resolution: The user explicitly requires YAML frontmatter only for artifacts; no workspace convention resolves the declaration format for convention files.

#### Decision Point: Initial convention version

- Tag: ask
- Applies to: Task 1 and Task 5; both existing conventions and artifacts need their first positive integer.
- Alternative A — Start at 1: Treat this feature as the first explicitly versioned contract; simple and conventional, but provides no encoded history before adoption; impacts both convention declarations and current artifact metadata.
- Alternative B — Derive from current AIB major/minor: Seed an integer derived from the release line; gives rough historical context, but couples artifact evolution back to overall SemVer and can create large jumps; impacts declarations, tests, and docs.
- Alternative C — Maintainer-selected independent values: Choose separate starting integers for main context and data model based on known prior convention revisions; reflects perceived history, but requires undocumented historical judgment and may not be reproducible; impacts declarations and fixtures.
- Rationale/Resolution: Positive integers are required, but the starting value is not specified by input or conventions.

#### Decision Point: Version comparison rule

- Tag: ask
- Applies to: Task 2 compatibility helper and Task 3 classifier; behavior for an artifact version greater than the convention is unspecified.
- Alternative A — Exact equality: Any applied/expected mismatch is incompatible and routed through processing; fail-safe for downgrade/future artifacts, but may rewrite an artifact whose newer format is backward-compatible; impacts classifier and validators.
- Alternative B — Older-only incompatibility: Process only when applied is lower; preserves newer artifacts, but an older validator may accept unknown semantics; impacts classifier and validators.
- Alternative C — Greater-version hard failure: Process older artifacts, but abort when applied is greater; avoids destructive downgrade while requiring manual intervention; impacts upgrade error handling, menu, and tests.
- Rationale/Resolution: The request says to compare versions and defines missing/invalid metadata as incompatible, but does not define ordering semantics for unequal positive integers.

#### Decision Point: Artifact frontmatter strictness

- Tag: ask
- Applies to: Task 2 parsers and validators; future metadata extensibility and ambiguity handling differ.
- Alternative A — Version key only: Require a frontmatter block containing exactly one `convention_version` key; maximally deterministic, but blocks future artifact metadata without a convention change; impacts parser and fixtures.
- Alternative B — Allow unique additional keys: Require exactly one valid `convention_version` while preserving and ignoring other unique scalar keys; extensible, but broadens parser and validation behavior; impacts shared parser and validators.
- Alternative C — Allow only an explicit key allowlist: Permit `convention_version` plus convention-defined metadata keys; controlled extensibility, but needs another maintained schema; impacts conventions, parser, and tests.
- Rationale/Resolution: The request requires the version key but neither prohibits nor authorizes other YAML frontmatter fields.

#### Decision Point: Registry authority during upgrade

- Tag: ask
- Applies to: Task 3 extension discovery; new and removed registered extensions produce different results depending on the authority source.
- Alternative A — Upgraded current registry only: Process only extensions registered by the new brain's managed registry; handles additions/removals cleanly, but archived user flags must be reconciled separately; impacts initialize registry parsing.
- Alternative B — Union of current and archived registries: Examine both sets and classify all unique entries; protects legacy artifacts, but can preserve or execute prompts for extensions the new version removed; impacts safety validation and directive generation.
- Alternative C — Archived registry only: Preserve exactly what the workspace previously registered; honors legacy state, but misses newly mandatory extensions; impacts initialize behavior and future extensibility.
- Rationale/Resolution: Current context says the registry is AIB-managed, but neither input nor convention defines which version of the registry controls an upgrade.

#### Decision Point: Incompatible extension with Update no

- Tag: ask
- Applies to: Task 3 classification and Task 4 aggregate dispatch; user refresh preference can conflict with required convention migration.
- Alternative A — Override for compatibility migration: Execute the registered refresh prompt despite `Update: no`, only during a version-incompatible upgrade; guarantees conformity, but temporarily overrides the user's automatic-update preference; impacts directive and `aib-modify.md`.
- Alternative B — Respect Update no and remain pending: List the extension but require the user to change the flag or handle it manually; preserves user control, but one-run processing and completion can stall; impacts gate messaging and retry flow.
- Alternative C — Preserve incompatible artifact with warning: Do not refresh and allow upgrade completion; honors the flag, but violates validator and incompatibility acceptance criteria; impacts validators and weakens safety.
- Rationale/Resolution: The input requires incompatible extensions to refresh, while context defines `Update: no` as skipping refresh; no precedence rule exists.

#### Decision Point: Missing registered dependency behavior

- Tag: ask
- Applies to: Task 3 classification when Location, Convention, or Prompt is absent or unsafe.
- Alternative A — Aggregate as blocked and keep pending: Finish safe classification, write the problem into the directive, and keep the gate pending until repaired; preserves archives and reports all issues, but requires a later retry; impacts initialize output and menu messaging.
- Alternative B — Fail the upgrade immediately: Abort before clearing active memory when a dependency is missing; strongest safety, but prevents non-context upgrade completion; impacts transaction ordering and errors.
- Alternative C — Warn and continue: Follow current extension warning behavior; keeps upgrade moving, but can mark incomplete context compatible; impacts safety and acceptance criteria.
- Rationale/Resolution: The shared extension reader treats missing artifacts as non-blocking, but upgrade compatibility cannot be completed without the convention and refresh prompt.

#### Decision Point: Aggregate directive contract

- Tag: ask
- Applies to: Task 3 `input.md` generation and Task 4 `aib-modify.md` consumption.
- Alternative A — Ordered Markdown records: One directive with one structured record per artifact containing Location, Convention, Action, Prompt, and legacy Source when needed; readable and deterministic for an AI prompt, but not a formal data format; impacts generator, prompt, tests, and docs.
- Alternative B — YAML payload inside Input: Emit a machine-oriented list of artifact mappings; unambiguous and extensible, but adds a second YAML contract inside Markdown input; impacts parser expectations and user readability.
- Alternative C — Compact prose list: Name artifacts and prompts in one paragraph; minimal, but fragile for multiple extensions and failure reporting; impacts only generator/prompt wording but weakens determinism.
- Rationale/Resolution: The request mandates one complete directive but does not define its schema or ordering.

#### Decision Point: aib-modify upgrade dispatch

- Tag: ask
- Applies to: Task 4 authorization and orchestration.
- Alternative A — Bounded prompt migration mode: Teach `aib-modify.md` to recognize the generated directive and authorize only the listed current registered migration/refresh prompts and their artifact paths; preserves prompt-driven orchestration and narrows writes, but increases prompt complexity; impacts `aib-modify.md` and prompt-contract tests.
- Alternative B — New Python orchestrator: Add a tool that validates the directive and dispatches commands/prompts; centralizes checks, but Python cannot directly execute AI prompts and adds a new framework component; impacts tools, file structure, tests, and docs.
- Alternative C — Broad context-write exception: Let `aib-modify.md` execute any prompt listed in Input; simple, but permits untrusted archived paths and weakens safety boundaries; impacts only the prompt but creates security risk.
- Rationale/Resolution: One `aib-modify.md` run is required, but the existing sole migration exception does not define a safe extension-refresh mechanism.

#### Decision Point: Partial-failure handling

- Tag: ask
- Applies to: Task 4 when multiple affected artifacts are processed and one fails.
- Alternative A — Process all, aggregate failures, remain pending: Independent artifacts continue, successful outputs remain, failures are reported together, and compatibility is not cleared; maximizes progress and complete diagnostics, but retries must avoid needless reprocessing; impacts directive state and completion logic.
- Alternative B — Fail fast: Stop at the first failed migration/refresh and remain pending; simple and limits mixed states, but delays discovery of later failures; impacts prompt procedure and logs.
- Alternative C — Roll back all context outputs: Restore archived/seed pre-run artifacts if any action fails; atomic outcome, but requires a second transaction/backup design and can undo successful expensive refreshes; impacts prompts/tools substantially.
- Rationale/Resolution: The request defines the success path but not transactional behavior for partial multi-artifact failures.

#### Decision Point: Compatibility completion transition

- Tag: ask
- Applies to: Task 3 state initialization, Task 4 completion, and Task 3 menu behavior.
- Alternative A — Retain manual confirmation: `aib-modify.md` validates all artifacts but leaves `initialized-not-populated`; the existing gate lets the user confirm and then sets `compatible`; preserves human control, but confirmation can be incorrect unless evidence is displayed; impacts menu wording and tests.
