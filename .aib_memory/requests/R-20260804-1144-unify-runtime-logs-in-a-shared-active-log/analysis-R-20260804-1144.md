## Overview

- Request ID: R-20260804-1144
- Request title: Unify runtime logs in a shared active log

### Background

AIB currently splits runtime events between `.aib_memory/log_general.md` and `.aib_memory/log_<request_id>.md`, which fragments the chronological audit trail and prevents pre-request activity from following the request through closure. The request replaces those active files with one predictable `.aib_memory/log.md` stream and archives its complete contents when a request closes.

### Scope

The change covers shared-log writing in `log-entry.py`, request-close archival in the artifact-moving and closure tools, removal of the `--general` CLI mode and all repository callers, removal of idle-state logging rejection and obsolete error-suppression instructions, the normative log convention, internal and user documentation, regression tests, and the conflicting logging statements in product context.

### Out of scope

The implementation will not migrate, merge, rename, or delete existing legacy runtime logs; change CI-generated release logs under `logs/`; change the UTC timestamp or entry-line format; add network access or third-party dependencies; or alter unrelated request artifacts.

Request closure shall take a loss-averse snapshot of that stream into the active request folder's `log_<request_id>.md`, preserve and extend any prior archive, and re-establish an empty shared root stream; legacy runtime logs remain inert historical artifacts. ## Research Results

### Workspace Pattern Scan

- `.aib_brain/tools/log-entry.py` currently parses `input.md`, rejects idle state, chooses either `log_<request_id>.md` or `log_general.md`, exposes `--general`, appends UTF-8 text, and echoes the entry to stdout. The shared-path change can remove all request-header parsing from this tool while retaining workspace validation, timestamp formatting, append mode, UTF-8, and stdout behavior.
- `.aib_brain/tools/move-request-artifacts.py` is the existing lifecycle owner for moving plan, analysis, and request log artifacts before closure. Its log branch currently uses `shutil.move`, skips a missing request-named root log, and cannot preserve an existing destination by appending. It is invoked explicitly by `aib-implement.md` and again as a safety net from `close-request.py`, so any new archival operation must be idempotent under two calls.
- `.aib_brain/tools/close-request.py` catches every artifact-move exception, emits a warning, and still resets the request to idle. That behavior can close a request after failed log archival, conflicting with the request's audit-preservation constraint unless the failure policy changes.
- `--general` occurs in `.aib_brain/prompts/aib-input-from-context.md`, `.aib_brain/prompts/aib-modify.md`, and `.aib_brain/prompts/aib-refresh-context.md`. Those invocations must become ordinary shared-log calls before the CLI option is removed.

- `.aib_brain/README.md` describes `log-entry.py` as writing request or general logs. `.aib_brain/user_guide.html` promises a full audit trail but does not list the active runtime log or explain its close-time archive lifecycle.

### Industry Knowledge and External Benchmarking

- Python's standard `FileHandler` uses append mode by default and supports delayed creation, so the requested append-only shared log and lazy first-write creation follow established standard-library behavior. Applicability: retain direct append and explicit UTF-8 without adopting the heavier `logging` framework. Source: [Python logging handlers](https://docs.python.org/3/library/logging.handlers.html).
- Python's rotating handlers keep one stable active filename and rename the prior stream during rollover before continuing on a new active file. Applicability: a stable `.aib_memory/log.md` with close-time archival matches a familiar rotation model, but AIB additionally needs append-to-existing-archive and retry rules. Source: [Python rotating file handlers](https://docs.python.org/3/library/logging.handlers.html#rotatingfilehandler).
- `os.replace` provides an atomic successful rename on the same filesystem, while a complete archive-append-plus-root-clear transaction spans multiple operations. Applicability: an atomic snapshot rename can narrow the data-loss window, but the workflow still needs explicit retry semantics because two files cannot be committed as one portable filesystem transaction. Source: [Python `os.replace` documentation](https://docs.python.org/3/library/os.html#os.replace).
- Python's logging cookbook states that serializing multiple processes into one file has no general built-in logging solution. Applicability: the request needs an explicit concurrency contract or an AIB-specific lock protocol; ordinary append alone is not a complete multi-process rotation guarantee. Source: [Python logging cookbook](https://docs.python.org/3/howto/logging-cookbook.html#logging-to-a-single-file-from-multiple-processes).

## Proposed Solution

### High-Level Concept

Replace mode-dependent path resolution in `log-entry.py` with a state-independent append to `.aib_memory/log.md`, and let `move-request-artifacts.py` rotate that active stream into `<request-folder>/log_<request_id>.md` at request closure by renaming the root to a staging snapshot, creating a new empty root, then streaming the snapshot into the archive with a conditional newline separator and an fsynced binary append; align every prompt caller, convention, documentation, and test with the new single-log contract while preserving legacy runtime logs untouched.

### Execution Steps

#### Task 1: Simplify Shared Logging

- `.aib_brain/tools/log-entry.py`: Remove request-header parsing, the `--general` argument definition, and idle-state rejection; append every valid invocation to `.aib_memory/log.md` with lazy first-write creation, UTC `YYYYMMDD-HHmmss` prefix, UTF-8 output, and stdout echo; rely on argparse to reject the removed `--general` token as an unrecognized argument.
- `.aib_brain/prompts/aib-input-from-context.md`: Remove `--general` from every `log-entry.py` invocation so calls target the shared stream.
- `.aib_brain/prompts/aib-modify.md`: Remove `--general` from the pre-request `log-entry.py` invocation.
- `.aib_brain/prompts/aib-refresh-context.md`: Remove `--general` from every `log-entry.py` invocation.

- `.aib_brain/prompts/aib-sync-spec.md`: Delete the pre-active-request logging-failure suppression note and treat any non-zero `log-entry.py` exit as a normal tool failure.

## Decision Register

### Decision Points

#### Decision Point: Archive Component Ownership

- Tag: resolved-by-user
- Applies to: Task 2, shared-log archival placement.
- Rationale: The workspace currently gives `move-request-artifacts.py` artifact ownership, but `close-request.py` owns the final state transition and could instead enforce the log-specific transaction directly.
- Resolution: Developer selected Artifact mover ownership (Q001, Option A).
- Chosen Alternative — Artifact mover ownership: Implement archival in `move-request-artifacts.py`, preserving the current explicit pre-close invocation and the close-time safety-net invocation; centralizes artifact relocation and keeps the lifecycle owner unchanged, at the cost of requiring strict idempotency across both invocations and updates to `tests/test_artifact_placement.py`.

#### Decision Point: Closure Failure Policy

- Tag: resolved-by-user
- Applies to: Task 2, handling I/O or validation failures during log archival.
- Rationale: Current closure warns and continues after mover failure, while the request requires audit preservation but does not explicitly define whether closure must fail.
- Resolution: Developer selected Fail closed (Q002, Option A).
- Chosen Alternative — Fail closed: Propagate log-archive failure and keep the request active; protects attribution and retryability at the cost of blocking closure on filesystem problems and changing current warning behavior in `close-request.py`.

#### Decision Point: Retry Delivery Guarantee

- Tag: resolved-by-user
- Applies to: Task 2, reruns after interruption between archive append and root clearing.
- Rationale: Portable file operations cannot atomically append one file and clear another, so the request's retry-preservation constraint needs an explicit duplicate-data policy.
- Resolution: Developer selected At-least-once preservation (Q003, Option A).
- Chosen Alternative — At-least-once preservation: Never delete the staging snapshot until archive persistence has succeeded and tolerate duplicate entries after an ambiguous crash; minimizes loss with simple recovery at the cost of possible repeated entries; no additional durable journal is introduced.

#### Decision Point: Rollover Mechanism

- Tag: resolved-by-user
- Applies to: Task 2, establishing the archive snapshot and new empty active stream.
- Rationale: The root log can be appended then truncated in place, renamed to a staging snapshot, or folded into an atomically replaced archive, with different identity and failure windows.
- Resolution: Developer selected Rename to staging snapshot (Q004, Option A).
- Chosen Alternative — Rename to staging snapshot: Move the root `.aib_memory/log.md` to a stable staging path inside `.aib_memory/`, create a new empty root immediately, then drain the snapshot into `<request-folder>/log_<request_id>.md`; provides a clear rotation boundary and a recoverable snapshot at the cost of adding staging-path recovery logic in `move-request-artifacts.py` and platform-conditional handling for Windows rename semantics.

#### Decision Point: Concurrent Writer Policy

- Tag: resolved-by-user
- Applies to: Tasks 1, 2, and 4, log writes that overlap request closure.
- Rationale: The shared file invites a race between short-lived append processes and rotation, and the workspace has no existing cross-process lock convention.
- Resolution: Developer selected Serialized workflow contract (Q005, Option A).
- Chosen Alternative — Serialized workflow contract: Declare in `log-convention.md` that AIB prompt execution and closure are single-writer operations and test only sequential invocations; matches current local workflow simplicity at the cost of not protecting against accidental concurrency, and requires only documentation and behavior tests rather than new locking code.

#### Decision Point: Archive Boundary Normalization

- Tag: resolved-by-user
- Applies to: Task 2, appending root bytes to a non-empty existing archive.
- Rationale: A legacy or manually edited archive may lack a trailing newline, and literal concatenation can merge two otherwise valid entries.
- Resolution: Developer selected Conditional separator (Q006, Option A).
- Chosen Alternative — Conditional separator: Insert exactly one newline only when both the archive and the incoming snapshot are non-empty and the archive lacks a trailing line ending; preserves valid content and entry boundaries with minimal byte modification at the cost of one boundary-inspection read of the archive tail in `move-request-artifacts.py`.

#### Decision Point: Archive Copy Mode

- Tag: resolved-by-user
- Applies to: Task 2, reading and appending runtime-log content.
- Rationale: The active tool writes UTF-8 text, but preserving existing archive content can use either raw bytes or decoded text with different corruption and normalization behavior.
- Resolution: Developer selected Binary streaming (Q007, Option A).
- Chosen Alternative — Binary streaming: Copy raw bytes and inspect only boundary bytes during append; preserves existing content byte-for-byte and scales without full-memory reads at the cost of explicit newline separator handling in `move-request-artifacts.py`.

#### Decision Point: Durability Level

- Tag: resolved-by-user
- Applies to: Task 2, persistence ordering before the staging snapshot is deleted.
- Rationale: Closing a Python file flushes process buffers, while explicit `fsync` provides stronger storage persistence at additional platform and performance cost.
- Resolution: Developer selected File fsync (Q008, Option A).
- Chosen Alternative — File fsync: Flush and `fsync` the archive file before deleting the staging snapshot; strengthens crash durability using only the standard library at the cost of one extra synchronous write per closure.

#### Decision Point: Unexpected Path-Type Handling

- Tag: resolved-by-user
- Applies to: Tasks 1, 2, and 4, root and archive paths that are not ordinary files.
- Rationale: Current code follows normal `Path.open` and `shutil.move` behavior, while the new archival process could encounter a directory, symlink, or special file at a managed path.
- Resolution: Developer selected Require regular non-symlink files (Q009, Option A).
- Chosen Alternative — Require regular non-symlink files: Reject unexpected path types at both `.aib_memory/log.md` and `<request-folder>/log_<request_id>.md` and block the affected operation without modification; prevents writes outside managed files at the cost of changing permissive symlink behavior for advanced users, and requires new pre-checks in `move-request-artifacts.py` and additional test cases.

#### Decision Point: Removed Flag Error Experience

- Rationale: The option must no longer be exposed or accepted, but rejection can use generic argument parsing or a targeted migration error.
- Resolution: Developer selected Standard argparse rejection (Q010, Option A).
- Chosen Alternative — Standard argparse rejection: Delete the argument definition from `log-entry.py` and let argparse report `--general` as an unrecognized option; fully removes the API with minimal code at the cost of providing no migration guidance beyond the standard argparse message.

#### Decision Point: Prompt Logging Failure Policy
