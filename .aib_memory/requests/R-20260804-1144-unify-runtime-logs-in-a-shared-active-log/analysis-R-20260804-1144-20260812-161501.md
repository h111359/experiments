## Overview

- Request ID: R-20260804-1144
- Request title: Unify runtime logs in a shared active log

### Background

AIB currently splits runtime events between `.aib_memory/log_general.md` and `.aib_memory/log_<request_id>.md`, which fragments the chronological audit trail and prevents pre-request activity from following the request through closure. The request replaces those active files with one predictable `.aib_memory/log.md` stream and archives its complete contents when a request closes.

### Scope

The change covers shared-log writing in `log-entry.py`, request-close archival in the artifact-moving and closure tools, removal of the `--general` CLI mode and all repository callers, removal of idle-state logging rejection and obsolete error-suppression instructions, the normative log convention, internal and user documentation, regression tests, and the conflicting logging statements in product context.

### Out of scope

The implementation will not migrate, merge, rename, or delete existing legacy runtime logs; change CI-generated release logs under `logs/`; change the UTC timestamp or entry-line format; add network access or third-party dependencies; or alter unrelated request artifacts.

### Industry Knowledge and External Benchmarking

- Python's standard `FileHandler` uses append mode by default and supports delayed creation, so the requested append-only shared log and lazy first-write creation follow established standard-library behavior. Applicability: retain direct append and explicit UTF-8 without adopting the heavier `logging` framework. Source: [Python logging handlers](https://docs.python.org/3/library/logging.handlers.html).
- Python's rotating handlers keep one stable active filename and rename the prior stream during rollover before continuing on a new active file. Applicability: a stable `.aib_memory/log.md` with close-time archival matches a familiar rotation model, but AIB additionally needs append-to-existing-archive and retry rules. Source: [Python rotating file handlers](https://docs.python.org/3/library/logging.handlers.html#rotatingfilehandler).
- `os.replace` provides an atomic successful rename on the same filesystem, while a complete archive-append-plus-root-clear transaction spans multiple operations. Applicability: an atomic snapshot rename can narrow the data-loss window, but the workflow still needs explicit retry semantics because two files cannot be committed as one portable filesystem transaction. Source: [Python `os.replace` documentation](https://docs.python.org/3/library/os.html#os.replace).
- Python's logging cookbook states that serializing multiple processes into one file has no general built-in logging solution. Applicability: the request needs an explicit concurrency contract or an AIB-specific lock protocol; ordinary append alone is not a complete multi-process rotation guarantee. Source: [Python logging cookbook](https://docs.python.org/3/howto/logging-cookbook.html#logging-to-a-single-file-from-multiple-processes).

## Decision Register

### Decision Points

#### Decision Point: Archive Component Ownership

- Tag: ask
- Applies to: Task 2, shared-log archival placement.
- Rationale: The workspace currently gives `move-request-artifacts.py` artifact ownership, but `close-request.py` owns the final state transition and could instead enforce the log-specific transaction directly.
- Alternative — Artifact mover ownership: Implement archival in `move-request-artifacts.py`, preserving the current explicit pre-close call and close-time safety-net call; this centralizes artifact relocation but requires strict idempotency across both invocations and changes `tests/test_artifact_placement.py`.
- Alternative — Close tool ownership: Implement archival only in `close-request.py`; this places archive success next to the idle transition but makes the explicit mover call incomplete and changes `tests/test_close_request.py` more heavily.
- Alternative — Dedicated archive tool: Add a separate log-archive script invoked by both lifecycle paths; this isolates complexity and testing but adds a new public tool and orchestration surface.

#### Decision Point: Closure Failure Policy

- Tag: ask
- Applies to: Task 2, handling I/O or validation failures during log archival.
- Rationale: Current closure warns and continues after mover failure, while the request requires audit preservation but does not explicitly define whether closure must fail.
- Alternative — Fail closed: Propagate log-archive failure and keep the request active; this protects attribution and retryability but can block closure on filesystem problems and changes current warning behavior.
- Alternative — Warn and close: Preserve current best-effort closure; this avoids lifecycle blockage but can leave the requested archive incomplete or absent.
- Alternative — Retry then fail closed: Perform a bounded internal retry and keep the request active if it still fails; this handles transient errors but adds timing and retry-policy complexity.

#### Decision Point: Retry Delivery Guarantee

- Tag: ask
- Applies to: Task 2, reruns after interruption between archive append and root clearing.
- Rationale: Portable file operations cannot atomically append one file and clear another, so the request's retry-preservation constraint needs an explicit duplicate-data policy.
- Alternative — At-least-once preservation: Never clear the root until archive persistence succeeds and tolerate duplicate entries after an ambiguous crash; this minimizes loss with simple recovery but can repeat entries.
- Alternative — Exactly-once archival: Add a durable journal, marker, or content identity to detect a previously committed snapshot; this avoids duplicates but adds managed state and complex recovery cases.
- Alternative — Best-effort single pass: Append and clear without durable recovery metadata; this is simplest but provides weaker guarantees during abrupt termination.

#### Decision Point: Rollover Mechanism

- Tag: ask
- Applies to: Task 2, establishing the archive snapshot and new empty active stream.
- Rationale: The root log can be appended then truncated in place, renamed to a staging snapshot, or folded into an atomically replaced archive, with different identity and failure windows.
- Alternative — Append then truncate in place: Read or stream root content into the archive and truncate the same root file after success; this is simple and preserves file identity but risks concurrent writes entering the cleared range.
- Alternative — Rename to staging snapshot: Move the root to a stable staging path, create a new empty root immediately, then drain the snapshot into the archive; this gives a clear rotation boundary but introduces staging recovery and Windows rename considerations.
- Alternative — Build and replace archive: Create a combined temporary archive and atomically replace the destination before resetting the root; this protects archive replacement but still needs a root-clear retry rule and temporary-file cleanup.

#### Decision Point: Concurrent Writer Policy

- Tag: ask
- Applies to: Tasks 1, 2, and 4, log writes that overlap request closure.
- Rationale: The shared file invites a race between short-lived append processes and rotation, and the workspace has no existing cross-process lock convention.
- Alternative — Serialized workflow contract: Declare that AIB prompt execution and closure are single-writer operations and test only sequential calls; this matches current local workflow simplicity but does not protect accidental concurrency.
- Alternative — Lock-file protocol: Coordinate log entry and archival with an exclusively created workspace lock and stale-lock recovery; this is standard-library-only and explicit but adds failure, timeout, and cleanup behavior.
- Alternative — Snapshot-boundary tolerance: Do not lock; define entries that land after snapshot creation as belonging to the new root stream; this reduces coordination but requires a rollover mechanism that cannot clear post-snapshot writes.

#### Decision Point: Archive Boundary Normalization

- Tag: ask
- Applies to: Task 2, appending root bytes to a non-empty existing archive.
- Rationale: A legacy or manually edited archive may lack a trailing newline, and literal concatenation can merge two otherwise valid entries.
- Alternative — Conditional separator: Insert one newline only when both files are non-empty and the archive lacks a trailing line ending; this preserves valid content and entry boundaries but changes the exact byte concatenation.
- Alternative — Literal concatenation: Append root content byte-for-byte with no separator; this maximizes source fidelity but can merge the first new entry into the prior final line.
- Alternative — Full newline normalization: Rewrite both streams to canonical newline-separated text; this repairs malformed boundaries but modifies pre-existing archive bytes beyond the requested append.

#### Decision Point: Archive Copy Mode

- Tag: ask
- Applies to: Task 2, reading and appending runtime-log content.
- Rationale: The active tool writes UTF-8 text, but preserving existing archive content can use either raw bytes or decoded text with different corruption and normalization behavior.
- Alternative — Binary streaming: Copy raw bytes and inspect only boundary bytes; this preserves existing content and scales without full-memory reads but requires explicit separator handling.
- Alternative — Strict UTF-8 text: Decode and append with UTF-8 text I/O; this matches the writer contract and is easy to inspect but fails on any legacy invalid byte.
- Alternative — Replacement-decoded text: Decode invalid content with replacement characters; this keeps closure moving but silently mutates audit data.

#### Decision Point: Durability Level

- Tag: ask
- Applies to: Task 2, persistence ordering before the root log is cleared.
- Rationale: Closing a Python file flushes process buffers, while explicit `fsync` provides stronger storage persistence at additional platform and performance cost.
- Alternative — Flush and close: Treat successful close as sufficient before clearing the root; this matches existing tool practices but has a larger power-loss window.
- Alternative — File fsync: Flush and `fsync` the archive before resetting the root; this strengthens crash durability using the standard library but costs an extra synchronous write.
- Alternative — File and directory fsync where supported: Sync the archive plus relevant directories after create/replace operations; this is strongest on POSIX but requires platform-conditional behavior and has limited Windows symmetry.

#### Decision Point: Unexpected Path-Type Handling

- Tag: ask
- Applies to: Tasks 1, 2, and 4, root and archive paths that are not ordinary files.
- Rationale: Current code follows normal `Path.open` and `shutil.move` behavior, while the new archival process could encounter a directory, symlink, or special file at a managed path.
- Alternative — Require regular non-symlink files: Reject unexpected path types and block the affected operation; this prevents writes outside managed files but changes permissive symlink behavior.
- Alternative — Follow filesystem semantics: Open symlinks and fail naturally only for incompatible types; this is simple and consistent with current append behavior but can redirect audit data outside the apparent workspace path.
- Alternative — Replace unexpected paths: Remove or replace incompatible targets with ordinary files; this is self-healing but destructive and risks erasing user-managed data.

#### Decision Point: Removed Flag Error Experience

- Tag: ask
- Applies to: Task 1 and `tests/test_log_entry.py`, behavior when an old caller supplies `--general`.
- Rationale: The option must no longer be exposed or accepted, but rejection can use generic argument parsing or a targeted migration error.
- Alternative — Standard argparse rejection: Remove the argument definition and let the parser report an unrecognized option; this fully removes the API with minimal code but gives no migration guidance.
- Alternative — Targeted hidden rejection: Detect the token outside the advertised parser and emit a specific “remove --general” error; this improves migration guidance but retains special compatibility code for a removed option.
- Alternative — Versioned deprecation window: Accept and ignore the flag temporarily with a warning; this eases transition but conflicts with immediate non-acceptance success criteria.

#### Decision Point: Prompt Logging Failure Policy

- Tag: ask
- Applies to: Task 1, the first logging calls in `aib-analyze.md` and `aib-sync-spec.md`.
- Rationale: Their only documented suppression reason disappears when idle logging succeeds, but the prompts do not define whether other logging errors are fatal.
- Alternative — Remove suppression entirely: Treat a non-zero logging result like other tool failures; this surfaces workspace or I/O faults but can stop the workflow because audit logging failed.
- Alternative — Retain generic best effort: Continue suppressing first-call failures without tying them to active state; this favors workflow progress but can hide loss of the shared audit trail.
- Alternative — Warn and continue: Replace silent suppression with a visible warning; this balances observability and progress but makes logging reliability non-mandatory.

#### Decision Point: Initial Log Creation Policy

- Tag: ask
- Applies to: Tasks 1 and 3, existence of `.aib_memory/log.md` before the first write or closure.
- Rationale: The input permits lazy creation, while user documentation and initialized workspace structure could instead guarantee an empty file immediately.
- Alternative — Lazy creation only: Create `log.md` on first log write or when closure requires it; this avoids initializer changes but means a fresh workspace may not display the documented artifact.
- Alternative — Seed during initialization: Update initialization and upgrade seeds to create an empty `log.md`; this makes workspace structure deterministic but broadens scope into setup and migration tests.
- Alternative — Launcher assurance: Have launcher/menu startup ensure the file exists without changing initialization archives; this creates a predictable runtime artifact but couples logging setup to menu execution.

#### Decision Point: Caller Regression Enforcement

- Tag: ask
- Applies to: Task 4 and Task 6, preventing future use of the removed mode.
- Rationale: Behavior tests prove the tool contract but do not guarantee that every prompt caller drops `--general` or that obsolete suppression prose stays removed.
- Alternative — Add source-scan regression tests: Assert no live prompt/tool/convention caller contains `--general` and no pre-request suppression reason remains; this prevents repository drift but couples tests to documentation text.
- Alternative — Rely on behavior and manual scan: Update only tool and lifecycle tests and use a one-time `rg` validation; this keeps tests semantic but allows later callers to regress unnoticed.
- Alternative — Centralize prompt commands: Introduce a shared prompt command convention or generated caller inventory; this reduces duplicated syntax long-term but is a larger framework refactor.
