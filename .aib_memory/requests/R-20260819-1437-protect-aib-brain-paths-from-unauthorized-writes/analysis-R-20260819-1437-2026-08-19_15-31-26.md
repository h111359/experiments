# Analysis — R-20260819-1437

- **Request ID:** R-20260819-1437
- **Request title:** Protect .aib_brain paths from unauthorized writes

## Overview

### Background

The developer observed that ordinary project implementation runs are creating project-specific artifacts under `.aib_brain/` — most visibly the Python helper scripts `add_fo_to_bottler_seed.py` and `add_fo_to_bottlers_json.py` under `.aib_brain/tools/` (see the screenshot in `.aib_memory/attachments/624418228-59c8a7e5-6e8a-4251-9ab4-62af94f85118.png`) and generated Python bytecode caches at `.aib_brain/tools/__pycache__/` and `.aib_brain/tools/.pytest_cache/`. AIB is intended to be a model-agnostic, dependency-free framework distributed as a versioned zip archive of `.aib_brain/`; framework-owned assets must remain isolated from project implementation output. The current rules are internally inconsistent because `.aib_memory/instructions.md` requires ordinary implementation runs to review and update `.aib_brain/README.md` and `.aib_brain/user_guide.html`, which defeats the isolation.

The request explicitly authorizes the AIB framework changes needed to enforce the new isolation policy — namely audit every writing prompt, add a concise mandatory prohibition and canonical-convention reference to every writing prompt, define the canonical policy in `.aib_brain/conventions/coding-general-convention.md`, revise `.aib_memory/instructions.md` to remove the conflicting exceptions, add self-contained bytecode prevention (launcher environment variables, `-B` flag in prescribed commands, `menu.py` child-process propagation, and archive validation), and extend the automated test suite.

### AI interpretation

The AI Automation Agent interprets the request as a **framework-integrity hardening** change with three intertwined concerns:

1. **Policy consolidation and enforcement surface.** Move the authoritative `.aib_brain/` protection rule into a single normative section of `.aib_brain/conventions/coding-general-convention.md` and back-reference it from every prompt in `.aib_brain/prompts/` that is capable of causing writes. The prompt-side text is a concise, load-bearing prohibition (single paragraph plus link) — not a duplication of the full policy. The canonical section becomes the sole source that changes when the policy evolves.

2. **Explicit authorization propagation.** For a request to legitimately touch `.aib_brain/`, the developer must include an explicit authorization statement in `.aib_memory/input.md ## Input`. `aib-analyze.md` MUST detect this statement, reflect it in a dedicated section of `analysis-<request_id>.md`, and record an equivalent authorization line in `## Constraints` of `plan-<request_id>.md`. `aib-implement.md`, `aib-modify.md`, and `aib-execute.md` MUST refuse any change under `.aib_brain/` unless the authorization is present in the current plan (or, for `--exec-input` and `aib-modify.md`, in the current `## Input`). Installation (`initialize.py`) and upgrade (`initialize.py --upgrade`) are pre-authorized by design and do not require the sentinel.

3. **Bytecode-prevention hardening kept fully inside `.aib_brain/`.** The framework does not rely on the host `.gitignore`. Instead:
   - `.aib_brain/run.bat` sets `PYTHONDONTWRITEBYTECODE=1` before launching `menu.py`, and `.aib_brain/run.sh` exports the same variable before invoking `python3`.
   - Every prompt-prescribed direct invocation of a script under `.aib_brain/tools/*.py` uses `python -B` on Windows and `python3 -B` on POSIX. This applies uniformly to `log-entry.py`, `input-header.py`, `verify-input.py`, `verify-context.py`, `create-request.py`, `finalize-input.py`, `move-request-artifacts.py`, `close-request.py`, `edit-context.py`, `file-inventory.py`, `read-setup.py`, `initialize.py`, and `verify-context-data-model.py`.
   - `menu.py` builds every child-process command with `[sys.executable, "-B", ...]` and passes an environment that includes `PYTHONDONTWRITEBYTECODE=1` (using `env=os.environ.copy()` merged with that key) to `subprocess.Popen` and `subprocess.run`.
   - `scripts/release_bookkeeping.py` walks `.aib_brain/` and fails with a non-zero exit code and diagnostic message when any `__pycache__/` directory or `*.pyc` file is present under `.aib_brain/`, before creating the zip. The tool never silently skips such artifacts; it demands the workspace be clean, so the CI signal is loud.

Task-specific helper scripts that an implementation prompt needs are created via Python's `tempfile.mkdtemp()` under the operating system's temporary directory (`%TEMP%` on Windows, `$TMPDIR` on POSIX) and are removed on successful completion or, when applicable, in a `try/finally` block. When a helper genuinely belongs to the project (long-lived tooling), it is written under an existing project-owned directory such as `scripts/` — never under `.aib_brain/`.

The unauthorized-change inspection is a lightweight step inside every writing prompt: before returning control, the prompt lists any file it created, modified, moved, or deleted during the run and compares each path against the protection scope (`.aib_brain/**`). If a match is found and the current run is not an installation, upgrade, or authorized framework-maintenance request, the prompt outputs `ERROR: Unauthorized modification detected under .aib_brain/. Affected paths:` followed by one line per affected path and halts. No automatic revert is performed, per user Answer Q010.

The `.aib_memory/instructions.md` directives titled `Directive (MUST): README maintenance` and `Directive (MUST): Update .aib_brain\user_guide.html` are removed because they conflict with the new protection policy. The `Directive: Maintain \`logs/next_version_changes.md\` during implementation` and `Directive (MUST): Commit after analysis and after implementation` remain in place unchanged.

### Edge Cases

- **First-time implementation with the new policy.** A developer whose `input.md ## Input` legitimately targets `.aib_brain/` (e.g., a framework fix) but forgets the explicit authorization sentence will be halted by `aib-analyze.md` (or `aib-implement.md`) with a clear message asking them to add the sentence. The workflow does not proceed silently.
- **Analysis authorized, plan authorized, implementation halted anyway.** If the developer manually edits `plan-<request_id>.md` to remove the authorization line before implementation, the writing prompt still refuses the write. This is intended.
- **Installation on a workspace that already contains `.aib_brain/tools/__pycache__/`.** Installation is exempt from the prohibition and is expected to place the framework files as-is; the archive validation gate in `release_bookkeeping.py` ensures the distributed archive itself is clean, so a fresh install cannot introduce contamination.
- **Upgrade path.** `initialize.py --upgrade` continues to archive the legacy `.aib_memory` and reseed `.aib_brain/` from the archive. The upgrade is pre-authorized and does not need the sentinel.
- **Existing helper scripts remain.** `add_fo_to_bottler_seed.py` and `add_fo_to_bottlers_json.py` under `.aib_brain/tools/` are left in place per user Answer Q007. The archive-validation test asserts that FUTURE archives are clean; existing contamination is a pre-existing state that will need a separate maintenance request to remove.
- **Direct external invocation of AIB tools bypassing AIB launchers and prescribed commands** (e.g., `python .aib_brain/tools/menu.py` typed by the user in a shell without `-B` and without `PYTHONDONTWRITEBYTECODE=1`) is outside AIB's execution control. The user explicitly acknowledges this in the input's Constraints section. The archive-validation gate remains the last line of defense.
- **Cross-platform launcher parity.** `run.bat` uses `set VAR=value` (batch semantics: session-local export), while `run.sh` uses `export VAR=value`. Both must be present and both must precede the Python invocation.
- **`menu.py` running as a child of `run.bat`/`run.sh` inherits the env**, but the `subprocess` module's child processes DO inherit the parent env by default. Explicit `env=os.environ.copy()` merged with `PYTHONDONTWRITEBYTECODE=1` is defensive against future refactors and works even when `menu.py` is launched directly with `python -B menu.py` bypassing the launcher (belt-and-suspenders approach).
- **Archive-validation error at CI time.** If a PR-triggered CI run detects a `__pycache__/` under `.aib_brain/`, `release_bookkeeping.py` exits with a non-zero code and a clear message identifying the offending path. The CI job fails; the maintainer opens a framework-maintenance request to clean up and re-runs. No silent skipping.
- **Answer Application Sub-flow re-run.** When the developer answers Q-blocks and re-runs `aib-analyze.md`, the authorization sentinel remains in `## Input` (the developer keeps re-supplying it while the request is active); after `finalize-input.py` archives the input, the sentinel lives in the request-folder archive and in `analysis-<request_id>.md ## Overview → ### Authorization` and `plan-<request_id>.md ## Constraints`.

#### Decision Point: DP-02 authorization sentence format

- **Tag:** ask
- Alternatives:
  - **Alternative A: Canonical fixed sentence.** Require the literal sentence `This request explicitly authorizes changes under .aib_brain/.` verbatim in `input.md ## Input`. Trade-offs: trivially detectable by prompt-level regex; deterministic; developer friction is a single copy-paste line. Codebase impact: fixed string, easy tests.

#### Decision Point: DP-03 archive validation location

- **Tag:** ask

  - **Alternative A: In-place check in `scripts/release_bookkeeping.py::_create_brain_zip`.** Add `_validate_brain_clean(brain_path)` invoked immediately before the `ZipFile` is opened. #### Decision Point: DP-04 unauthorized-change inspection mechanism

- **Tag:** ask
- Alternatives:
  - **Alternative A: Prompt-level path-comparison at end of run.** Each writing prompt maintains an internal list of paths it touched during the run, filters that list for `.aib_brain/**`, and halts if any match and authorization was not detected. Trade-offs: fully self-contained in AIB, no `git` dependency, works even in a non-git workspace; relies on the AI honoring the "list what I touched" instruction. Codebase impact: prose-only prompt changes; testable by simulating a run.
  - **Alternative B: `git diff --name-only` invocation at end of run.** Trade-offs: authoritative, based on actual filesystem state; adds a git dependency for AIB correctness, contradicting the model-agnostic and dependency-free ethos; fails in a non-git workspace or when index state is stale. Codebase impact: adds `subprocess` call in prompt-executed step; harder to unit-test.
  - **Alternative C: Filesystem fingerprint before and after.** Compute a hash of every `.aib_brain/**` file at run start and again at run end; halt on any difference. Trade-offs: expensive on large frameworks; requires temp storage; strongest guarantee. Codebase impact: new tool or prompt step; measurable overhead.
