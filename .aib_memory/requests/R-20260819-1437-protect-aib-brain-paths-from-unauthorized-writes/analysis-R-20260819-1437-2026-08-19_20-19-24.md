# Analysis — R-20260819-1437

- **Request ID:** R-20260819-1437
- **Request title:** Protect .aib_brain paths from unauthorized writes

## Overview

### Background

The developer observed that ordinary project implementation runs are creating project-specific artifacts under `.aib_brain/` — most visibly the Python helper scripts `add_fo_to_bottler_seed.py` and `add_fo_to_bottlers_json.py` under `.aib_brain/tools/` (see the screenshot in `.aib_memory/attachments/624418228-59c8a7e5-6e8a-4251-9ab4-62af94f85118.png`) and generated Python bytecode caches at `.aib_brain/tools/__pycache__/` and `.aib_brain/tools/.pytest_cache/`. AIB is intended to be a model-agnostic, dependency-free framework distributed as a versioned zip archive of `.aib_brain/`; framework-owned assets must remain isolated from project implementation output. The current rules are internally inconsistent because `.aib_memory/instructions.md` requires ordinary implementation runs to review and update `.aib_brain/README.md` and `.aib_brain/user_guide.html`, which defeats the isolation.

The request explicitly authorizes the AIB framework changes needed to enforce the new isolation policy — namely audit every writing prompt, add a concise mandatory prohibition and canonical-convention reference to every writing prompt, define the canonical policy in `.aib_brain/conventions/coding-general-convention.md`, revise `.aib_memory/instructions.md` to remove the conflicting exceptions, add self-contained bytecode prevention (launcher environment variables, `-B` flag in prescribed commands, `menu.py` child-process propagation, and archive validation), and extend the automated test suite.

The latest developer answers close the remaining placement gap by rejecting any AIB-level policy for host-repository `scripts/` paths. AIB prompts, conventions, and tools must enforce only the `.aib_brain/` boundary and must not assume that a host repository has a `scripts/` directory or assign ownership or authorization semantics to it. This request separately authorizes the repository-specific `scripts/release_bookkeeping.py` update already required for archive validation.

### Authorization

This request explicitly authorizes the `.aib_brain/` framework-maintenance changes listed in `### Scope`. The authorization was supplied in the original developer input and is preserved in this analysis for propagation into `plan-R-20260819-1437.md ## Constraints`.

### AI interpretation

The AI Automation Agent interprets the request as a **framework-integrity hardening** change with three intertwined concerns:

1. **Policy consolidation and enforcement surface.** Move the authoritative `.aib_brain/` protection rule into a single normative section of `.aib_brain/conventions/coding-general-convention.md` and back-reference it from every prompt in `.aib_brain/prompts/` that is capable of causing writes. The prompt-side text is a concise, load-bearing prohibition (single paragraph plus link) — not a duplication of the full policy. The canonical section becomes the sole source that changes when the policy evolves.

2. **Explicit authorization propagation.** For a request to legitimately touch `.aib_brain/`, the developer supplies an explicit authorization statement whose meaning is semantically equivalent to the canonical example `This request explicitly authorizes changes under .aib_brain/.` The statement may appear in `.aib_memory/input.md ## Input` OR directly in the developer's chat message to the AI Automation Agent; the exact wording is not fixed. `aib-analyze.md` MUST detect an authorization statement in either source, reflect it in a dedicated `### Authorization` sub-section of `analysis-<request_id>.md ## Overview` (recording the verbatim statement and its source — `input.md ## Input` or `chat`), and record an equivalent authorization line in `## Constraints` of `plan-<request_id>.md`. `aib-implement.md`, `aib-modify.md`, and `aib-execute.md` MUST refuse any change under `.aib_brain/` unless the authorization is present in the current plan or (for `--exec-input` and `aib-modify.md`) in the current `## Input` or the current chat message. Installation (`initialize.py`) and upgrade (`initialize.py --upgrade`) are pre-authorized by design and do not require an authorization statement.

3. **Bytecode-prevention hardening kept fully inside `.aib_brain/`.** The framework does not rely on the host `.gitignore`. Instead:
   - `.aib_brain/run.bat` sets `PYTHONDONTWRITEBYTECODE=1` before launching `menu.py`, and `.aib_brain/run.sh` exports the same variable before invoking `python3`.
   - Every prompt-prescribed direct invocation of a script under `.aib_brain/tools/*.py` uses `python -B` on Windows and `python3 -B` on POSIX. This applies uniformly to `log-entry.py`, `input-header.py`, `verify-input.py`, `verify-context.py`, `create-request.py`, `finalize-input.py`, `move-request-artifacts.py`, `close-request.py`, `edit-context.py`, `file-inventory.py`, `read-setup.py`, `initialize.py`, and `verify-context-data-model.py`.
   - `menu.py` builds every child-process command with `[sys.executable, "-B", ...]` and passes an environment that includes `PYTHONDONTWRITEBYTECODE=1` (using `env=os.environ.copy()` merged with that key) to `subprocess.Popen` and `subprocess.run`.
   - `scripts/release_bookkeeping.py` walks `.aib_brain/` and fails with a non-zero exit code and diagnostic message when any `__pycache__/` directory or `*.pyc` file is present under `.aib_brain/`, before creating the zip. The tool never silently skips such artifacts; it demands the workspace be clean, so the CI signal is loud.

Task-specific helper scripts that an implementation prompt needs inside the repository are created under `.aib_memory/scratch/`, an AIB-owned working directory that `.aib_brain/tools/initialize.py` seeds on fresh workspace setup (with a `.gitkeep` sentinel) and preserves on `--upgrade`, and that `.aib_brain/tools/finalize-input.py` sweeps at every analysis-time archive/reset (deleting every file and subdirectory under `.aib_memory/scratch/` except `.gitkeep`). AIB makes no ownership, destination, or authorization rule for host-project directories outside `.aib_brain/`; any host policy remains external to the portable framework.

The unauthorized-change inspection is a lightweight step inside every writing prompt: before returning control, the prompt lists any file it created, modified, moved, or deleted during the run and compares each path against the protection scope (`.aib_brain/**`). If a match is found and the current run is not an installation, upgrade, or authorized framework-maintenance request, the prompt outputs `ERROR: Unauthorized modification detected under .aib_brain/. Affected paths:` followed by one line per affected path and halts. No automatic revert is performed, per user Answer Q010.

The `.aib_memory/instructions.md` directives titled `Directive (MUST): README maintenance` and `Directive (MUST): Update .aib_brain\user_guide.html` are removed because they conflict with the new protection policy. The `Directive: Maintain \`logs/next_version_changes.md\` during implementation` and `Directive (MUST): Commit after analysis and after implementation` remain in place unchanged.
