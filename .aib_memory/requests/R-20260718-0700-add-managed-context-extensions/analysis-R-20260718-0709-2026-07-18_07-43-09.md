## Overview

- Request ID: R-20260718-0709
- Request title: Add managed context extensions

### Background

The developer wants context extensions to provide detailed, topic-specific workspace knowledge without overloading context.md, beginning with a managed data-model extension.

### Scope

Define mandatory managed References metadata, add data-model refresh and context-read prompts, update all extension consumers from boolean to yes/no flags, seed the data-model registration during initialization, validate the new structure, and cover the behavior in tests and documentation.

### Out of scope

Creating extension types other than context-data-model.md is explicitly excluded from this iteration.

## Input Interpretation

### User Original Inputs

- Create context extensions as context-<extension-name>.md files registered in context.md References.
- Make References mandatory and framework-managed except for Read and Update values.
- Initially register only context-data-model.md, its existing convention, a new refresh prompt, Read: no, and a yes/no Update flag.
- Add aib-refresh-context-data-model.md to synchronize all workspace data models when updates are enabled and remove models no longer present in context.md.
- Add aib-context-read.md to load registered extensions only when Read: yes.
- Leave additional extension types out of scope.

### AI interpretation

AIB must evolve References from optional bibliographic entries into a mandatory registry with one H3 entry per convention-backed extension. Each entry needs deterministic metadata for location, summary, convention, refresh prompt, Read, and Update; initialization must seed the data-model entry, consumers must honor the flags, validation must reject drift, and documentation/tests must describe and enforce the contract.

## Research Results

### Workspace Pattern Scan

- .aib_brain/conventions/context-convention.md currently makes References optional, permits plain references, and accepts boolean Update values.
- .aib_brain/tools/verify-context.py implements optional References and boolean Update validation; its tests encode those behaviors.
- .aib_brain/prompts/aib-analyze.md, aib-modify.md, aib-sync-spec.md, and aib-input-from-context.md independently perform semantic relevance loading rather than delegating to a context-read prompt.
- .aib_brain/prompts/aib-refresh-context.md and aib-implement.md update extensions only when Update: true.
- .aib_brain/tools/initialize.py creates minimal context content but does not seed a managed extension registry.
- .aib_brain/conventions/context-data-model-convention.md exists, but the requested extension and refresh prompt do not.
- .aib_memory/context.md contains duplicate writable-extension Solution statements and boolean flag terminology that conflict with the requested contract.

### Industry Knowledge

- Registry schemas benefit from required fields, constrained enums, and validation at write boundaries; this is directly applicable to preventing malformed extension metadata.
- Lazy loading controlled by explicit opt-in metadata keeps prompt context bounded and predictable; Read: yes/no provides a clear inclusion gate.
- Generated configuration regions need ownership boundaries and validation to prevent manual drift; the requested framework-managed registry needs an explicit reconciliation policy.
- Synchronization systems should define source-of-truth and deletion semantics; the proposed data-model refresh needs an authoritative workspace evidence rule to avoid accidental loss.

### AI Agent Critique

- The request says the data-model prompt should remove models no longer present in context.md while also finding models across other workspace sources; those sources can disagree.
- The phrase "executed every time context.md is read" requires updates to every current and future prompt, but no single executable dispatch mechanism currently wraps file reads.
- The request calls Update optional in one sentence while requiring user-editable Update behavior elsewhere, leaving registry cardinality ambiguous.
- context-convention.md currently describes References as optional and bibliographic; this directly conflicts with the requested mandatory managed registry.
- verify-context.py currently permits absent References and validates true/false, so its checks and diagnostics will drift unless changed together.
- test_context_formatting_rules.py and test_verify_context_planned.py assert the obsolete optional/boolean behavior.
- aib-refresh-context.md forbids reading most .aib_brain files, which could prevent discovery of registered extension refresh prompts unless an explicit exception is added.
- context.md repeats the writable-extension update behavior in two Solution bullets.
- context.md says the document has a 6-section structure while the convention defines seven valid sections with five mandatory sections, creating terminology drift.
- context-data-model-convention.md allows an optional H1 and requires entities, which may not represent empty-workspace initialization cleanly.
- The analysis convention says Proposed Solution contains exactly three H3 subsections but lists only two names; this analysis follows the explicitly named subsections.
- The user input names backslash paths while repository documentation generally uses slash-separated workspace paths; output normalization needs a decision.

### Edge Cases

- No data models are discoverable during initialization or refresh.
- Read or Update metadata is absent, capitalized, duplicated, or has an invalid value.
- A registered extension file, convention, or refresh prompt is missing.
- context.md lists a model that no longer exists while scripts or documentation still describe it.
- A workspace model is renamed, producing an apparent delete-and-add pair.
- Multiple files describe the same model with conflicting fields.
- A refresh run is read-only because Update: no but the extension file is absent.
- Future extension conventions are added without corresponding registry migration.
- Existing workspaces upgrade with legacy References entries or boolean Update values.
- Recursive invocation occurs if aib-context-read.md reads context.md itself.

## Decision Register

### Decision Points

#### Decision Point: Registry field syntax
- Tag: ask
- Rationale/Resolution: Task 1 needs the exact metadata labels and layout. Alternatives: separate lines Convention/Prompt/Read/Update (explicit and easy to validate; expands entries; affects convention, validator, seeds), or encode convention and prompt in the H3 heading (compact; harder to parse; affects the same files).

#### Decision Point: Update cardinality
- Tag: ask
- Rationale/Resolution: Task 1 must decide whether every managed entry requires Update. Alternatives: require Update: yes/no (deterministic; more metadata), or allow it to be absent with no as default (backward-friendly; implicit behavior).

#### Decision Point: User edit boundary
- Tag: ask
- Rationale/Resolution: Task 5 must define permitted manual edits. Alternatives: users edit only Read and Update values (strict ownership; predictable regeneration), or users may also edit Summary (custom descriptions; potential drift).

#### Decision Point: Heading policy
- Tag: ask
- Rationale/Resolution: Task 4 needs stable entry identity. Alternatives: fixed display heading supplied by AIB (consistent; less customizable), or heading derived from extension filename (deterministic; less friendly).

#### Decision Point: Entry ordering
- Tag: ask
- Rationale/Resolution: Task 4 must validate registry order. Alternatives: convention-defined order (stable diffs; requires central list), or alphabetical filename order (simple; may not reflect importance).

#### Decision Point: Path syntax
- Tag: ask
- Rationale/Resolution: Task 5 must choose canonical paths. Alternatives: slash-separated workspace-relative paths (cross-platform; differs from request spelling), or backslash-separated paths (matches request; Windows-specific).

#### Decision Point: Read integration
- Tag: ask
- Rationale/Resolution: Task 3 needs the meaning of "every time context.md is read." Alternatives: update every AIB prompt that reads context.md to invoke aib-context-read.md (broad coverage; many edits), or apply only to workflows that consume supplementary context (smaller scope; exceptions remain).

#### Decision Point: Read relevance behavior
- Tag: ask
- Rationale/Resolution: Task 2 must decide whether Read: yes is sufficient. Alternatives: always load every yes extension (literal and deterministic; larger context), or load yes extensions only when Summary is semantically relevant (bounded context; model-dependent selection).

#### Decision Point: Missing artifact behavior
- Tag: ask
- Rationale/Resolution: Task 2 must handle missing registered files. Alternatives: halt with an explicit error (strong integrity; blocks workflow), or warn and continue (resilient; may omit required context).

#### Decision Point: Refresh dispatch
- Tag: ask
- Rationale/Resolution: Task 3 must update writable extensions. Alternatives: execute each registered prompt path when Update: yes (extensible; dynamic dispatch), or hard-code the data-model prompt initially (simple; future code edits required).

#### Decision Point: Model source authority
- Tag: ask
- Rationale/Resolution: Task 2 faces conflicting model evidence. Alternatives: workspace implementation artifacts are authoritative (current-state oriented; context descriptions can be overridden), or context.md is authoritative (matches removal wording; may discard implemented models).

#### Decision Point: Deletion evidence threshold
- Tag: ask
- Rationale/Resolution: Task 2 needs safe removal semantics. Alternatives: remove only after exhaustive workspace scan finds no evidence (safer; more scanning), or remove whenever absent from context.md (literal; risks deleting workspace-backed models).

#### Decision Point: Model identity
- Tag: ask
- Rationale/Resolution: Task 2 needs rename/deduplication matching. Alternatives: H2 business name is identity (human-readable; rename becomes replacement), or physical location plus name is identity (stable for renames; more complex).

#### Decision Point: No-model representation
- Tag: ask
- Rationale/Resolution: Task 1 must reconcile an empty workspace with a convention requiring entities. Alternatives: omit context-data-model.md until a model exists (no invalid stub; registered location missing), or permit a canonical no-model notice (file exists; requires convention exception).

#### Decision Point: Initialization artifact creation
- Tag: ask
- Rationale/Resolution: Task 3 must decide whether initialization creates the extension. Alternatives: create an empty/conforming context-data-model.md (discoverable; needs empty-state format), or register it without creating it until refresh (simpler initialization; missing file edge case).

#### Decision Point: Registry reconciliation
- Tag: ask
- Rationale/Resolution: Task 3 must handle user changes to managed metadata. Alternatives: refresh restores all fields except Read/Update (enforces ownership; overwrites drift), or validator rejects drift and requires explicit repair (transparent; more user intervention).

#### Decision Point: Upgrade migration
- Tag: ask
- Rationale/Resolution: Task 3 must handle legacy contexts. Alternatives: initialize.py upgrade rewrites legacy References to the seeded registry (automatic; may discard references), or migration prompt performs semantic conversion (safer; extra migration step).

#### Decision Point: Legacy bibliographic references
- Tag: ask
- Rationale/Resolution: Task 1 changes References purpose. Alternatives: prohibit non-extension references (clean registry; loses bibliography), or permit them in a separate representation (preserves information; expands schema).

#### Decision Point: Invalid flag handling
- Tag: ask
- Rationale/Resolution: Task 4 must define case sensitivity. Alternatives: accept only lowercase yes/no (deterministic; strict), or normalize case variants (friendlier; mutation/ambiguity).

#### Decision Point: Validator compatibility
- Tag: ask
- Rationale/Resolution: Task 4 must decide rollout behavior. Alternatives: immediately reject old true/false values (clean cutover; existing workspaces fail), or temporarily accept both formats (migration window; weakens contract).

#### Decision Point: Refresh validation
- Tag: ask
- Rationale/Resolution: Task 2 needs post-refresh checks. Alternatives: add a dedicated data-model validator tool (deterministic; extra implementation), or require prompt-based convention review only (lower footprint; less enforceable).

#### Decision Point: Summary wording
- Tag: ask
- Rationale/Resolution: Task 5 needs the seeded Summary text. Alternatives: describe logical, physical, and analytical schemas and relationships (specific; longer), or use a short generic data-model description (compact; weaker relevance signal).

#### Decision Point: Documentation breadth
- Tag: ask
- Rationale/Resolution: Task 5 must choose documentation scope. Alternatives: update README and user guide plus context (complete user/developer coverage; broader diff), or update README and context only (smaller change; user guide becomes stale).
