# Analysis: R-20260615-1016

## 1. Overview

**Request ID:** R-20260615-1016

**Request title:** Eliminate requests_register.md and move state to input.md

### Background

The `requests_register.md` file maintains a flat Markdown table of all AIB requests (Active and Closed). Over time, this table grows indefinitely, but only the single Active row is operationally relevant — Closed rows are redundant because each request has a dedicated folder under `.aib_memory/requests/` that implicitly documents its existence and closure. The developer requests that the register file be eliminated entirely, with the active-request state migrated into a YAML frontmatter header in `input.md`. This makes `input.md` the single source of truth for active-request state, removing the need to maintain a separate flat-file database. The change requires creating a new tool for reading/writing the YAML header, updating all prompts and tools that currently read `requests_register.md`, removing dead code from `common.py`, and deleting or replacing `requests_register-convention.md`.

### Scope

- Modify `input.md` to carry a YAML frontmatter header containing: `request_id`, `title`, `state`, and `options` (e.g., `minimum_questions`)
- Create new tool `.aib_brain/tools/input-header.py` providing programmatic CRUD operations on the YAML header
- Update `aib-analyze.md`, `aib-implement.md`, `aib-refresh-context.md` to read the active request from the input.md YAML header via the new tool, not from `requests_register.md`
- Update tools: `create-request.py`, `close-request.py`, `finalize-input.py`, `move-request-artifacts.py`, `initialize.py`
- Update `common.py`: remove `requests_register_path` and `update_requests_register`; add YAML-header helper functions
- Remove `.aib_memory/requests_register.md` from the workspace
- Delete or replace `.aib_brain/conventions/requests_register-convention.md`
- Update `tests/` to reflect the changed architecture (extensive)
- Update `.aib_brain/README.md` and `.aib_memory/context.md`
- Add explicit step to `aib-implement.md` to copy `input.md` final content into the request folder before reset

### Out of scope

- Changes to the request folder naming convention (`R-YYYYMMDD-HHmi-<slug>`)
- Changes to `analysis-<ID>.md`, `plan-<ID>.md`, or `implementation.md` artifact conventions
- Changes to CI workflows or SemVer tooling
- Data migration of historical rows from `requests_register.md` (folder structure already provides full history)

### AI Interpretation

The developer requests a structural simplification of AIB's request-state mechanism. Currently, `requests_register.md` serves as the operational lookup table for the active request ID and state. The file grows indefinitely as requests are closed, but only the `Active` row is ever operationally relevant — historical rows are redundant because each request has a dedicated folder under `.aib_memory/requests/` that already implicitly documents its existence and closure.

The proposed change consolidates active-request state directly into `input.md` via a YAML frontmatter block. This makes `input.md` the single source of truth: it already serves as the developer's input channel, and adding structured frontmatter provides a machine-readable header without requiring a separate file. The YAML header captures: `request_id`, `title`, `state` (lifecycle phase: `idle`, `analysis_ready`, `questions_generated`), and `options` (e.g., `minimum_questions`).

A new dedicated tool `input-header.py` is required to provide controlled, atomic read/write access to the YAML header, preventing fragile ad-hoc text manipulation in multiple scripts. All existing prompts and tools that currently read/write `requests_register.md` must be migrated to use this new tool exclusively.

The `requests_register.md` file is eliminated from the workspace (no migration of historical data needed — folder structure provides full history). The `requests_register-convention.md` convention file loses its target and must be removed or replaced with a new convention describing the input.md YAML header.

Dead code in `common.py` (`update_requests_register`, `requests_register_path`, and the related `resolve_active_request_or_explicit` table-parsing function) must be removed after all callers are migrated. Tests that create or read `requests_register.md` must be updated to reflect the new architecture.

A new requirement clarified in the input: `input.md` with its final post-Q&A content must be copied into the request folder during the implement phase before being reset to the seed template for the next request.

### Industry Knowledge

1. **YAML frontmatter convention (Jekyll / Hugo / pandoc)** — Using `---` delimiters for YAML frontmatter at the top of Markdown files is well-established in the static site generation ecosystem (Jekyll, Hugo, 11ty) and documentation tooling (pandoc). The frontmatter block is parsed separately from the Markdown body, providing machine-readable metadata co-located with human-readable content. Applicability: high — follows existing `input.md` pattern of being both human-readable and machine-processable.

2. **Single source of truth (12-factor app, DRY principle)** — Duplicating state between `requests_register.md` (Active row) and `input.md` (`State:` line + `## Status` section) is an anti-pattern. Eliminating the register in favor of a YAML header in `input.md` removes duplication, reduces consistency risk, and is consistent with the 12-factor principle of storing config in a single, explicitly known location. Applicability: high — directly motivates and supports the request.

3. **Minimal YAML parsing without external deps (OSS community practice)** — Projects that require YAML-like configuration without external dependencies (e.g., minimal CI tools, embedded scripting environments) commonly implement a restricted parser for a known-safe subset: flat key-value pairs and one level of nesting. Python's `re` and `str` operations are sufficient for this subset. This approach avoids the `pyyaml` / `ruamel.yaml` dependency (not stdlib). Applicability: high — directly resolves the Python stdlib constraint since `tomllib` (Python 3.11+ stdlib) is read-only and TOML contradicts the user's explicit "YAML header" request.

4. **YAML null representation** — In YAML, `~` or `null` both represent a null value. `~` is idiomatic for "not set" fields in frontmatter. For `request_id: ~` and `title: ~` when no request is active, `~` provides clear visual distinction from empty string. Applicability: moderate — style choice for idle-state YAML header.

5. **File-based state machines (GitHub Actions, Make-based workflows)** — The current `State:` field in `input.md` (`idle`, `analysis_ready`, `questions_generated`) is a simple file-based state machine. Embedding this in YAML frontmatter alongside the request ID formalizes the state machine in a structured, parseable format, consistent with how GitHub Actions encodes workflow state in YAML workflow files. Applicability: moderate — confirms the design direction.

## 5. Decision Register

### Decision Points

#### Decision Point: YAML frontmatter format for input.md

- **Tag:** resolve-autonomously

- **Rationale/Resolution:** The developer input explicitly states "YAML header with current request ID, name, status, and all options." Standard YAML frontmatter between `---` delimiters is the established convention for machine-readable Markdown metadata (source: Jekyll documentation, Hugo documentation, pandoc). The proposed format is:

  ```yaml
  ---
  request_id: ~
  title: ~
  state: idle
  options:
    minimum_questions: 0
  ---
  ```

  The `state` field replaces the `State:` line currently in the `## Status` section. The `options` block replaces the `## Options` section. The `~` YAML null value is used for absent `request_id` and `title` when no request is active. All field names map directly to the developer's description "request ID, name, status, and all options." The `## Status` and `## Options` sections are removed from `input.md`; only `## Input` and (conditionally) `## Questions` sections remain.

#### Decision Point: YAML header parsing in Python without stdlib YAML parser

- **Tag:** resolve-autonomously

- **Rationale/Resolution:** Python stdlib contains no YAML parser (`pyyaml` / `ruamel.yaml` are not stdlib). AIB constraint: "Tool scripts implemented in Python using only standard library" (source: `.aib_memory/context.md` TS area, statement text: "Tool scripts implemented in Python using only standard library."). The frontmatter structure needed is strictly bounded: up to four top-level keys (`request_id`, `title`, `state`) plus one nested dict (`options`). A minimal parser using `re` and `str` operations is sufficient. The new `input-header.py` tool will implement `parse_yaml_header(content)` and `write_yaml_header(content, header_dict)` functions using this approach. `tomllib` (Python 3.11+ stdlib) is not used because it is read-only and TOML contradicts the user's explicit "YAML" requirement.

#### Decision Point: requests_register-convention.md disposition

- **Tag:** ask

- **Rationale:** The developer input states the file "must be deleted or replaced — it will have no valid target after this change." This leaves both options open. Option A: delete the file outright (no replacement). Option B: replace it with `input-header-convention.md` that describes the YAML header format, valid field values, lifecycle states, and normative rules for reading/writing (maintaining the convention-per-artifact pattern already used for analysis, plan, context, etc.). The workspace follows a convention-over-configuration principle where every major artifact has a dedicated convention file (`.aib_brain/conventions/analysis-convention.md`, `plan-convention.md`, `context-convention.md`, `q-block-convention.md`). `input.md` does not yet have its own convention file. Option B aligns with this pattern; Option A removes the normative spec for the header format.

#### Decision Point: Removal scope of dead code in common.py

- **Tag:** resolve-autonomously

- **Rationale/Resolution:** The developer listed `update_requests_register` and `requests_register_path` for removal. Based on workspace scan, `resolve_active_request_or_explicit()` is also dead code after migration — it only serves register-table-based callers. All three functions will be removed as part of the cleanup. Source: developer input "A clean removal of these functions is needed to prevent confusion" combined with workspace scan confirming `resolve_active_request_or_explicit` has no callers outside the register-based scripts.

#### Decision Point: input.md copy timing in implement workflow

- **Tag:** resolve-autonomously

- **Rationale/Resolution:** The developer input states "When executing implement - make sure input.md is copied in the request folder with its final content before to be initialized with the stub for the next request." The `aib-implement.md` prompt Step 9 currently invokes `move-request-artifacts.py` then `close-request.py`. The `finalize-input.py` script is invoked by `aib-analyze.md` Step S07 but not by `aib-implement.md`. Adding an explicit invocation of `finalize-input.py` in `aib-implement.md` Step 9 (before `move-request-artifacts.py`) ensures the final input.md content is archived into the request folder before the reset. This is the minimal change required. The existing archive mechanism in `finalize-input.py` already writes to `<request-folder>/inputs/input-archive-<timestamp>.md`.
