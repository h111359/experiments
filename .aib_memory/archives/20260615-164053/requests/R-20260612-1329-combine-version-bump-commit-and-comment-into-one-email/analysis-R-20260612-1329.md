# Analysis: R-20260612-1329

## Overview

- **Request ID:** R-20260612-1329
- **Request title:** Combine version bump commit and comment into one email

### Background

When a pull request targeting `main` triggers the AIB SemVer-bump workflow (`aib-semver-patch-bump-and-log.yml`), `github-actions[bot]` performs two sequential actions: (1) pushes a `chore: bump to vX.Y.Z` commit to the PR branch, and (2) posts a PR comment containing the formatted changelog body. GitHub treats these as two separate timeline events — `pull_request.synchronize` and `issue_comment.created` — resulting in two distinct notification emails sent to all PR subscribers. The developer requires that subscribers receive a single notification email conveying both the version-bump commit and the changelog content.

### Scope

- The GitHub Actions workflow file `.github/workflows/aib-semver-patch-bump-and-log.yml`
- The notification behaviour experienced by PR subscribers when CI performs version-bump automation
- The relationship between the commit push step and the PR comment step in the workflow

### Out of scope

- Changes to `scripts/release_bookkeeping.py` logic (version computation, log generation)
- GitHub's email notification infrastructure or user notification settings
- Non-email notification channels (GitHub mobile, web inbox)
- Manual version bump overrides (MINOR/MAJOR)

## Input Interpretation

### User Original Inputs

The developer describes that the CI workflow triggers two separate GitHub notification emails when a PR targets `main`: one for the `chore: bump to vX.Y.Z` commit push (`pull_request.synchronize`) and another for the changelog PR comment (`issue_comment.created`). The goal is to consolidate these into a single notification email. The developer requests alternative approaches be proposed as questions with trade-offs for an informed decision.

### AI interpretation

The request concerns reducing notification noise for PR subscribers during the automated release bookkeeping workflow. GitHub generates one notification email per distinct timeline event. The current workflow produces exactly two events: a commit push (triggering `synchronize`) and a PR comment creation. Since GitHub provides no native mechanism to batch multiple event types into a single email notification, the solution must restructure the workflow to produce only one notification-generating event while preserving all information (version bump + changelog) in a single accessible location. The developer explicitly requests that solution variants be presented as decision questions before implementation proceeds.

## Research Results

### Workspace Pattern Scan

The current workflow (`aib-semver-patch-bump-and-log.yml`) already embeds `CHANGES_BODY` in the commit message body (lines 105-112: `printf '%s\n\n%s\n' "$commit_subject" "$CHANGES_BODY" > "$msg_file"` followed by `git commit --file "$msg_file"`). This means the changelog content is already present in the commit that triggers the `synchronize` event. The separate PR comment step (lines 121-127) duplicates this information as a distinct PR timeline entry for visibility purposes.

Key observations:
- The `"Post changelog comment"` step uses `continue-on-error: true`, indicating it is non-critical
- The commit message already contains the full changelog as its body
- The workflow uses `concurrency` grouping, so only one run executes per PR at a time
- The `if` guard (`github.actor != 'github-actions[bot]'`) prevents infinite trigger loops

### Industry Knowledge

1. **GitHub notification model (GitHub Docs):** GitHub sends one notification per distinct timeline event. There is no API-level mechanism to suppress or batch notifications across event types. The only way to reduce emails is to reduce the number of notification-generating events.

2. **Commit message as changelog carrier (Conventional Commits / Keep a Changelog):** Industry best practice in projects using conventional commits or automated changelogs is to embed release notes in the commit message body (or tag annotation). This makes the change self-documenting without requiring a separate comment. Many major OSS projects (Angular, Lerna, semantic-release) rely solely on commit messages for release information.

3. **PR body as non-notification update channel (GitHub Actions community patterns):** Updating the PR description body does NOT trigger a notification email. Multiple CI tools (Terraform plan bots, coverage reporters) exploit this by updating the PR body instead of posting comments to avoid notification spam. This is an established pattern for conveying CI output without extra emails.

4. **Post-merge workflow pattern (release-please, semantic-release):** Some tools defer version bumping entirely to a post-merge trigger (`push` to `main`), creating a separate "release PR" or tag. This eliminates in-PR push events but fundamentally changes the release workflow architecture.

### AI Agent Critique

- The workflow's `continue-on-error: true` on the comment step masks failures silently; if the comment is the only user-facing changelog notification and it fails, no one is informed
- The `CHANGES_BODY` is duplicated: once in commit message body, once in PR comment — this redundancy is the direct cause of the dual-notification issue
- The concurrency setting uses `cancel-in-progress: false`, meaning queued runs execute sequentially rather than cancelling stale runs — this is correct for release bookkeeping but could delay notification in rapid-push scenarios
- The `if` condition `github.actor != 'github-actions[bot]'` correctly prevents recursive triggers but means manually-pushed `chore:` commits by the bot are also excluded
- context.md states "CI-automated SemVer PATCH bumps with manual override for MINOR and MAJOR" but does not describe the notification contract or user-facing changelog delivery method — this is a documentation gap
- The `scripts/release_bookkeeping.py` outputs `changes_body` via `GITHUB_OUTPUT` but this output is only consumed by the workflow — if the comment step is removed, `changes_body` output becomes unused (dead output unless commit message continues to use it)

## Decision Register

### Decision Points

#### Decision Point: Notification consolidation approach

- **Tag:** `ask`
- **Context:** The workflow currently produces two notification-generating events (commit push + PR comment). Multiple approaches exist to reduce this to one, each with different trade-offs in visibility, implementation complexity, and information accessibility.

**Alternatives:**

1. **Remove PR comment step (rely on commit message body)**
   - Description: Delete the "Post changelog comment" step entirely. The changelog is already embedded in the commit message body.
   - Benefits: Zero additional code; simplest change (delete ~8 lines). Single `synchronize` email contains commit with full changelog in message body.
   - Drawbacks: Changelog no longer appears as a separate PR timeline comment; subscribers must click into the commit to see the full message body. Less immediately visible in the PR conversation tab.
   - Codebase impact: Remove the final step from the workflow YAML.

2. **Replace PR comment with PR body/description update**
   - Description: Instead of posting a comment, append or prepend the changelog to the PR description. PR body edits do not trigger notifications.
   - Benefits: Single `synchronize` email. Changelog is highly visible at the top of the PR page. No extra click needed to read it.
   - Drawbacks: Modifies the PR description which may contain user-authored content; requires careful append/prepend logic. Slightly more complex implementation. If PR body is long, changelog may be buried.
   - Codebase impact: Replace `gh pr comment` with `gh pr edit --body` logic (prepend/append pattern); moderate workflow change.

3. **Move version bump to post-merge workflow (eliminate in-PR push entirely)**
   - Description: Remove the version bump from the PR workflow. Instead, trigger a separate workflow on `push` to `main` (after merge) that creates the bump commit directly on `main` and optionally creates a GitHub Release with the changelog.
   - Benefits: Zero notification emails during PR review. Version bump appears as a post-merge commit. GitHub Release provides a dedicated changelog display.
   - Drawbacks: Fundamentally restructures the release workflow. Version bump no longer visible in PR branch before merge. Conflicts with current architecture where PR branch contains final version state. Requires rethinking how `logs/` and `versions/` artifacts are tracked.
   - Codebase impact: Major workflow restructuring; new workflow file; changes to when/how bookkeeping runs.

4. **Post comment FIRST, then push commit with `[skip actions]` in message**
   - Description: Reorder steps: post the changelog comment before pushing the commit. Add `[skip actions]` to the commit message to prevent re-triggering workflows (though this does NOT suppress notifications to subscribers).
   - Benefits: N/A — does not actually solve the problem. Push still triggers `synchronize` notification regardless of `[skip actions]`.
   - Drawbacks: Does not reduce emails. `[skip actions]` only suppresses workflow triggers, not subscriber notifications. Introduces ordering dependency.
   - Codebase impact: Minimal, but ineffective.

- **Resolution:** Developer choice required. The input explicitly requests variants be presented as questions. Alternatives 1 and 2 are the only technically viable single-email solutions that preserve the current workflow architecture. Alternative 3 is viable but represents a major architectural change. Alternative 4 is technically ineffective.
