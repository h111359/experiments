# Analysis: R-20260611-1720

## Overview

- **Request ID:** R-20260611-1720
- **Request title:** Combine version bump commit and comment into one email

### Background

When a pull request targeting the `main` branch is opened, re-opened, or updated, the workflow `.github/workflows/aib-semver-patch-bump-and-log.yml` fires. The workflow runs `scripts/release_bookkeeping.py`, which bumps the SemVer marker, writes a per-version log under `logs/`, archives `.aib_brain/`, commits all changes to the PR branch, and pushes. After the push, a separate step posts a PR comment with the changelog body. Each of these two workflow actions — the git push and the PR comment — triggers an independent GitHub notification email. PR subscribers therefore receive two emails for every workflow execution: one for the new commit (synchronize event) and one for the PR comment (issue_comment event). The developer wants to reduce this to a single email.

### Scope

- Workflow file `.github/workflows/aib-semver-patch-bump-and-log.yml`: restructuring or removing the "Post changelog comment" step, or reordering steps to collapse notifications.
- Supporting investigation into GitHub's notification batching behavior for `pull_request.synchronize` and `issue_comment.created` events on the same PR.

### Out of scope

- `scripts/release_bookkeeping.py`: no changes to the bookkeeping logic itself.
- GitHub account-level or organization-level notification preferences: those are user-controlled and outside the workflow.
- Any other GitHub Actions workflow files.
- Changing the SemVer bump mechanism or the version log format.

## Input Interpretation

### User Original Inputs

> When merging to main branch is triggered GitHub action `.github\workflows\aib-semver-patch-bump-and-log.yml` which causes two emails to be sent to the users - one for the comment and another for the commit.
>
> I want the users to receive only one email with the comment and the chore commit for the version bump together.

### AI Interpretation

When a PR targeting `main` triggers the AIB SemVer-bump workflow, `github-actions[bot]` performs two distinct actions in sequence: (1) pushes a `chore: bump to vX.Y.Z` commit to the PR branch, and (2) posts a PR comment containing the formatted changelog body. GitHub treats these as two separate timeline events — `pull_request.synchronize` and `issue_comment.created` — and sends one notification email per event to all PR subscribers. The developer requires that PR subscribers receive a single notification email that conveys both the version-bump commit and the changelog comment content, rather than two separate emails.

## Research Results

### Workspace Pattern Scan

- The workflow is defined in `.github/workflows/aib-semver-patch-bump-and-log.yml`.
- The "Commit and push (if changed)" step uses `git commit --file "$msg_file"` where `msg_file` is populated with both `commit_subject` and `CHANGES_BODY`. The commit message body therefore already contains the full changelog content.
- The "Post changelog comment" step runs `gh pr comment "${{ github.event.pull_request.number }}" --body "${CHANGES_BODY}"` unconditionally when `steps.bookkeeping.outputs.changes_body != ''`.
- The guard `github.actor != 'github-actions[bot]'` prevents infinite re-triggering when the bot pushes the bump commit back to the PR branch.
- No existing test exercises the two-email-per-run behavior; `tests/test_release_bookkeeping.py` covers only `release_bookkeeping.py` logic.

### Industry Knowledge

1. **GitHub notification event types are non-mergeable at the API level** (GitHub Docs — Notifications, REST Events API): GitHub dispatches `pull_request.synchronize` and `issue_comment.created` as independent webhook events. There is no API parameter that bundles two different event types into a single notification email. This is a fundamental GitHub platform constraint.

   *Applicability:* High. This rules out any approach that relies on GitHub emitting a single email for the push + comment pair via API instruction.

2. **GitHub notification digest/batching is user-controlled, not workflow-controlled** (GitHub Docs — Managing notification delivery): GitHub's "email digests" consolidate notifications into batches, but this is a per-user account setting. The workflow has no mechanism to influence how GitHub's notification pipeline groups events for individual subscribers.

   *Applicability:* High. Confirming that eliminating the second email requires removing or replacing one of the two notification-generating actions from the workflow, not reordering them.

3. **PR description updates do not generate notification emails** (GitHub community discussion, confirmed by GitHub event documentation): The `gh pr edit --body "..."` command updates the pull request description via the REST API (`PATCH /repos/{owner}/{repo}/pulls/{pull_number}`). This event is NOT in the set of events that trigger subscriber email notifications. Only `issue_comment.created` (new PR comment) and `pull_request.synchronize` (new push) generate emails.

   *Applicability:* Medium. This opens the viable alternative of moving the changelog from a PR comment to the PR description, keeping the push as the sole notification-generating event.

### AI Agent Critique

- **[Workflow — redundant changelog delivery]** `CHANGES_BODY` appears in both the git commit message body and the PR comment body. This duplication is the root cause of the two-email problem. If one delivery channel is removed, the information is still fully available via the other.

- **[Workflow — accumulating PR comments]** The "Post changelog comment" step creates a NEW comment on every `synchronize` run (re-push, new commit added). For long-lived PRs with multiple round-trips, this generates a growing list of bot comments on the PR, which is visual noise.

- **[Workflow — `continue-on-error: true` on comment step]** The comment step carries `continue-on-error: true`. A comment posting failure is silently swallowed. If the comment IS considered important enough to warrant an email, failing silently contradicts that importance.

- **[Workflow — no deduplication of changelog comments]** There is no mechanism to edit the last existing bot comment on the PR instead of creating a new one. The `gh pr comment --edit-last` flag could address this but is not used.

- **[Workflow — comment step not guarded by `changed` output]** The "Post changelog comment" step is guarded by `steps.bookkeeping.outputs.changes_body != ''`, which is correct. The "Commit and push" step is guarded by `steps.bookkeeping.outputs.changed == 'true'`. The two conditions are logically consistent.

- **[Analysis — cannot achieve "one email WITH the comment AND the commit" as stated]** The developer's literal request — "one email with the comment and the chore commit for the version bump together" — is technically unachievable on the GitHub platform. Push-notification emails and PR-comment emails are distinct event types that GitHub never consolidates. The achievable outcomes are: (a) one email for the push only (remove comment step), or (b) one email for the push only (replace comment with PR description update, which does not email). A clarifying question is needed to determine the acceptable form.

## Decision Register

### Decision Points

#### Decision Point: DP-01 — Approach to eliminate the second email (approach-selection)

- **Tag:** ask

- **Context:** The developer wants PR subscribers to receive one email instead of two when the AIB SemVer-bump workflow runs. The two emails originate from distinct GitHub event types: `pull_request.synchronize` (commit push) and `issue_comment.created` (PR comment). GitHub does not merge distinct event type notifications at the platform level. The only way to reduce to one email is to eliminate one of the two notification-generating actions from the workflow. Multiple valid approaches exist, each with different trade-offs in information visibility and workflow complexity.

- **Alternatives:**

  - **Alt A — Remove the "Post changelog comment" step**
    - Description: Delete the `Post changelog comment` step from the workflow. The changelog content is already present in the commit message body (`CHANGES_BODY` is written to the commit), so no information is lost from VCS. Users receive a single notification: the push email.
    - Benefits: Minimal code change (one step removed). Changelog still present in git history via commit message body. Zero new dependencies.
    - Drawbacks: No changelog visible inline in the PR conversation timeline. Users who view PRs without looking at individual commits may not see the changelog. The PR comment thread loses the bot's summary entry.
    - Impact: Remove one `- name: Post changelog comment` step block from the workflow YAML.

  - **Alt B — Replace the PR comment with a PR description update**
    - Description: Replace `gh pr comment ... --body "${CHANGES_BODY}"` with `gh pr edit ${{ github.event.pull_request.number }} --body "${CHANGES_BODY}"` (or append to existing body). PR description updates do not generate email notifications. Users receive a single notification: the push email.
    - Benefits: Changelog remains visible in the PR — prominently in the PR description header. One email for push.
    - Drawbacks: PR description is typically user-authored; overwriting it with the changelog may destroy the developer's custom PR description on each workflow run. Append-only variant requires parsing and updating description carefully.
    - Impact: Replace one `gh pr comment` call with `gh pr edit` in the workflow YAML; potentially add logic to preserve user-written PR description content.

  - **Alt C — Replace the PR comment with a GitHub Actions job summary**
    - Description: Write `CHANGES_BODY` to `$GITHUB_STEP_SUMMARY` instead of posting a PR comment. The summary appears in the Actions run detail page for that workflow execution. No email is generated for job summaries.
    - Benefits: Changelog visible in the Actions UI per run. One email for push. No PR comment clutter.
    - Drawbacks: Changelog only accessible in the Actions tab — not visible in the PR conversation timeline or PR description. Slightly less discoverable for reviewers who don't check CI details.
    - Impact: Replace `gh pr comment ... --body "${CHANGES_BODY}"` with `echo "${CHANGES_BODY}" >> "$GITHUB_STEP_SUMMARY"` in the workflow YAML.

- **Rationale for `ask` classification:** The developer's input states "one email with the comment and the chore commit for the version bump together," implying the comment should remain visible as part of the PR experience. However, it is technically impossible to deliver a single email that bundles a push notification and a comment notification at the GitHub platform level. The three viable alternatives (A, B, C) each achieve one email but differ in where the changelog content is visible (git commit body, PR description, or Actions summary). No workspace convention or explicit input statement resolves which placement is acceptable. Per Appendix B §B.2, the decision point is tagged `ask`.
