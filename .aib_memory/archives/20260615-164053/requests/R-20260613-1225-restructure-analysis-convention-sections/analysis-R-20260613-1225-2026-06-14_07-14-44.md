# Analysis: R-20260613-1225

## Overview

- **Request ID:** R-20260613-1225
- **Request title:** Restructure analysis convention sections

### Background

The developer reports that analysis documents produced under the current `analysis-convention.md` schema are dense and hard to skim. Concrete pain points raised in `input.md`: (1) the Requirements Gate Evaluation table renders eight rows even when every category passes, dominating vertical space without conveying actionable information; (2) the mandatory `## Files Read During This Analysis Run` section consumes screen real estate that has no decision-support value; (3) the document describes findings (Research Results) and decisions (Decision Register) but never states the AI's intended solution in plain English, forcing readers to reconstruct it from alternatives; (4) the analysis lacks a learning-oriented rationale for junior developers or contributors new to the codebase; (5) downstream prompt `aib-analyze.md` Step 9 reads the analysis to generate a self-sufficient plan, but the technical detail it needs is intermixed with prose intended for humans rather than separated for machine consumption. The change targets `analysis-convention.md` (mandatory section list and per-section rules), `aib-analyze.md` (Step 5 generation instructions and Requirements Gate Evaluation language), and the regression test suite that pins the convention's structural contract.

### AI interpretation

The developer requests a restructuring of the analysis document schema with two complementary objectives. **Readability for humans:** compress information that is uniformly green (the Requirements Gate when all checks pass) and remove information that has no decision-support value at read time (Files Read), while introducing a plain-English `## Proposed Solution` block that states the AI's intended approach, the runtime execution sequence, and the files to be modified, accompanied by a `### Why this approach?` rationale that maps the proposal to existing project patterns to support junior contributors. **Machine-readability for the next AI:** introduce a terminal `## Technical Context (For Planner Agent)` section that captures dense, terse, technical detail (file relationships, edge cases, internal data shapes) consumed by `aib-analyze.md` Step 9 when generating the self-sufficient plan, and lift the Edge Cases discussion into Research Results so it lives alongside the workspace pattern scan and AI Agent critique. The contract change cascades into `aib-analyze.md` Section 5 (which must instruct the AI to populate the new sections and condense the gate table), into `context.md` (which records the section count), and into `tests/test_analysis_prompt_structure.py` (which asserts the convention's mandatory section names). Existing closed analyses are not migrated; the new schema applies to forward analyses only.

### Industry Knowledge

1. **Architecture Decision Record (ADR) — Michael Nygard / MADR template.** ADRs separate Context, Decision, Consequences, and Status. Mature variants (MADR 3.0) add a "Considered Options" block parallel to "Decision". The proposed `## Proposed Solution` + `## Decision Register` split mirrors this separation: solution states the chosen direction in plain English; the decision register enumerates alternatives that might still need user input. Applicability: high — the AIB analysis already uses Decision Points; adding Proposed Solution closes the "what was actually chosen" gap that ADRs codify.
2. **Progressive disclosure / collapsed-on-success pattern (GitHub Actions UI, CI dashboards, Jest/pytest reporters).** When all checks are green, modern CI reporters render a one-line summary ("8 categories — all PASS"); failures expand into per-row detail. This pattern reduces vertical space when the common case is success while preserving auditability when it is not. Applicability: high — directly addresses the developer's complaint about the eight-row gate table; can be achieved in Markdown with a compact summary line plus an optional details block (HTML `<details>` or per-failure bullets).
3. **Two-audience documents — AWS Well-Architected and Diátaxis "Reference vs Explanation" split.** Specifications written for both human review and downstream tooling explicitly tag sections by audience to reduce mixed-purpose ambiguity. The proposed `## Technical Context (For Planner Agent)` follows this pattern by labelling the audience in the heading itself. Applicability: high — directly justifies the user's machine-readability requirement and aligns with the existing convention rule that "implement MUST NOT read $AD" (audience scoping is already part of the framework's design language).
4. **Plain-English summary first, evidence after — IEEE 29148 §6, BABOK BA Planning.** Requirements specifications are recommended to lead with a goal/approach statement in natural language before detailed analysis. The proposed `## Proposed Solution` heading is consistent with this. Applicability: medium — the existing `## Overview` already provides a goal/scope summary; Proposed Solution complements rather than duplicates it by stating the *approach*, not the *intent*.
5. **"Why this approach?" rationale block — Conventional Comments, Google Eng Practices code review style.** Public engineering style guides recommend that authors of non-trivial design choices document why the chosen approach beats the discarded ones, immediately after stating the approach, to support reviewers without prior context. Applicability: high — directly addresses the developer's "for inexperienced devs" requirement.

The convention rule fires only after answers arrive; before answers, alternatives remain. Wording could be clearer.

Codifying the new compressed render belongs in either `aib-analyze.md` §S05.5 or `analysis-convention.md` §4.4 — placement decision needed.

### Edge Cases

- **First-run analysis (no prior file):** Step S05.0 backup logic must not fail; new sections (Proposed Solution, Technical Context) must still be generated when there is no previous version to reference.
- **Re-run after Q-block answers (analysis exists):** §S05.3.2 requires partial edits. The new sections must accept partial edits without their structural contract being broken. Specifically, an existing `## Proposed Solution` must be able to absorb answer-driven changes to alternatives without losing its `### Why this approach?` subsection.
- **All-PASS Requirements Gate:** Compact rendering must still allow a downstream auditor to verify the gate ran. A bare "PASS" word is too thin; the compact form should at minimum identify the eight evaluated categories (e.g., one bullet per category) or assert each numbered category by ID.
- **Mixed PASS/FAIL Requirements Gate:** Rendering must show failed categories with their notes, while passing categories may stay collapsed. The convention should specify both the "all pass" and "any fail" rendering branches.
- **Empty Decision Register (no decision points):** The current convention §4.5 already handles `[no $DPs identified] -> single entry`. Proposed Solution then has no alternatives to refer to; it states the chosen approach without a "considered alternatives" pointer.
- **Already-closed request analyses:** Old files MUST NOT be migrated; the convention §3 makes them immutable post-archival. The plan must explicitly forbid touching files under `.aib_memory/requests/<closed>/`.
- **Analysis files referenced in tests:** Regression tests pin section names (Overview, Input Interpretation, Decision Register, AI Agent critique). Changing the mandatory list adds new test assertions but MUST NOT break existing ones.
- **`context.md` atomic statement format:** The "five mandatory sections" statement is a short atomic statement under `## FN`; replacing the number requires an exact-text `--operation delete` followed by `--operation insert` per `context-convention.md` rules — paraphrasing or partial-text matching will fail `verify-context.py`.

## Decision Register

### Decision Points

#### Decision Point: Compressed render format for the Requirements Gate Evaluation

- **Tag:** `ask`
- **Context:** §S05.5 requires a Requirements Gate Evaluation in every analysis. Today this renders as an eight-row Markdown table, which the developer flagged as wasteful when all categories pass. Several render styles satisfy the auditability requirement with less vertical space.

**Alternatives:**

1. **Conditional render: one-line summary on all-PASS, full table on any FAIL.**
   - Description: When every category is PASS, emit a single line such as `Requirements Gate: 8/8 PASS — all categories satisfied.`. When any category is non-PASS, emit the full eight-row table.
   - Benefits: Maximum compression in the common case; full detail when it matters; deterministic output rule.
   - Drawbacks: Two render branches in the convention; the convention must specify both.
   - Codebase impact: Minor wording in `analysis-convention.md` and `aib-analyze.md` §S05.5; no tooling change.
2. **Always compact, FAIL rows expanded inline.**
   - Description: Always emit a one-line summary listing the eight category IDs, followed by an expanded bullet list ONLY for non-PASS categories.
   - Benefits: Single render branch; consistent regardless of gate result; failed rows are unambiguous.
   - Drawbacks: All-PASS render carries a list of category names that the developer wanted to compress further.
   - Codebase impact: Minor wording in `analysis-convention.md` and `aib-analyze.md` §S05.5.
3. **HTML `<details>` collapsible block.**
   - Description: Render the full eight-row table inside a `<details><summary>Requirements Gate: PASS (8/8)</summary>...table...</details>` block so it is collapsed by default in Markdown viewers that support it.
   - Benefits: Auditability fully preserved; visual compression when rendered.
   - Drawbacks: `analysis-convention.md` §5 currently forbids HTML (`NO: [HTML | non-deterministic output]`); this would require a convention exception.
   - Codebase impact: Convention rule loosening + render template change.
4. **Drop the table entirely on all-PASS; emit only a one-liner.**
   - Description: When all PASS, emit `Requirements Gate: PASS.` with no per-category enumeration. Failure path retains full table.
   - Benefits: Maximum compression.
   - Drawbacks: Auditor cannot tell from the doc which eight categories were evaluated; couples downstream readers to `requirements-analysis-convention.md` for the list.
   - Codebase impact: Minor wording change.
