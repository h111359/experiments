# Analysis: R-20260702-1333

## Overview

**Request ID:** R-20260702-1333

**Request title:** Improve AIB upgrade workflow with state tracking

### Background

After `initialize.py --upgrade` completes, `menu.py` resumes the normal interactive menu. This gives the user the impression that the upgrade is fully complete, when in fact a mandatory follow-up step still remains: executing `.aib_brain/prompts/aib-modify.md` to reconstruct `context.md` from the archived legacy memory. If the user closes the terminal before completing this step, the partially-migrated workspace has no record of the pending action, so the menu simply shows normally on the next launch, silently ignoring the migration.

Additionally, the archive subfolder used by `initialize.py` was renamed from `.aib_memory/archives/` (plural, used by pre-v1.3 workspace deployments) to `.aib_memory/archive/` (singular) in the R-20260702-0903 implementation. The user has confirmed this rename was incorrect and wants to revert back to `archives/` as the canonical name.

### Scope

- Add `memory_version_compatibility` field to `.aib_memory/aib-setup.yaml` with three allowed values (`compatible`, `not-compatible`, `initialized-not-populated`).
- `initialize.py`: seed the new field as `compatible` in fresh installations; set it to `initialized-not-populated` at the end of `_run_upgrade()`.
- `menu.py`: read the field on startup; when `initialized-not-populated`, show a dedicated migration-completion screen (not the normal menu) offering "Confirm Completed" and "Exit" options; on confirm, set the field back to `compatible` and proceed to the normal menu.
- Rename the upgrade archive folder from `.aib_memory/archive/` (singular) back to `.aib_memory/archives/` (plural) in all code, tests, and documentation.
- `common.py`: add a `set_setup_option` helper for updating a single key in `aib-setup.yaml`, used by both `initialize.py` and `menu.py`.
- Update `tests/test_initialize.py` and `tests/test_menu.py` to reflect the `archives/` rename and the new `memory_version_compatibility` behaviour.
- Update `.aib_brain/README.md` and `.aib_brain/user_guide.html` to document the new workflow and corrected archive path.
- Update `.aib_memory/context.md` File Structure and Solution sections.

### Out of scope

- Verification of migration completeness before accepting user confirmation (user trust model as stated in input).
- Changes to `aib-modify.md`, `aib-analyze.md`, or any other prompt file.
- Migration or movement of content already present in `.aib_memory/archive/` (the singular folder); cleanup is manual.
- Any changes to request lifecycle workflow outside the upgrade path.
- Backward compatibility support for workspaces still using `archive/` (singular); input explicitly states no backward compatibility is required.

### AI Interpretation

The upgrade workflow must become a durable two-phase process. Phase one (initialisation) is the existing `initialize.py --upgrade` which seeds fresh memory and generates migration instructions. Phase two (migration confirmation) is new: the developer executes `aib-modify.md` and then confirms completion in the menu.

The `memory_version_compatibility` field acts as a persistent handoff token in `aib-setup.yaml`. It is written by `initialize.py` (`initialized-not-populated`) and cleared by `menu.py` after user confirmation (`compatible`). The field value at menu startup determines which screen the developer sees, making the workflow resilient to terminal restarts.

The archive folder rename is a straightforward path constant change in `initialize.py` and corresponding updates to tests, documentation, and `context.md`. No migration of existing `archive/` content is required.

### Industry Knowledge

**1. Persistent state for wizard-style workflows (BABOK / wizard pattern):**
Industry-standard practice for multi-step interactive processes is to persist intermediate state durably (database, config file, or lock file) rather than relying on in-process flags. This pattern ensures that process interruption (crash, terminal close) does not silently lose the workflow position. The AIB design choice to use `aib-setup.yaml` as the state store aligns with this practice: it is version-controlled, human-readable, and already read at menu startup.

*Applicability:* Directly applicable; the `memory_version_compatibility` field is exactly this kind of durable progress token.

**2. Trust-based completion gates (UX practice for developer tooling):**
Developer tools (e.g. Homebrew post-install notes, npm `postinstall` scripts) commonly present important follow-up instructions but do not automatically verify execution — they trust the developer. Verification gates add complexity without proportional value when the cost of incorrect confirmation is low and recoverable. The input explicitly adopts this model ("AIB trusts the user").

*Applicability:* Directly applicable; the migration screen does not verify `aib-modify.md` execution; it displays instructions and accepts a confirmation key.

**3. Blocking vs. warning patterns in CLI tools (CLI UX convention):**
When a tool detects a required precondition that has not been met (e.g., pending migration), established CLI UX recommends blocking the main flow rather than displaying a warning alongside normal functionality. This prevents the user from inadvertently using a partially-migrated workspace as if it were fully ready. Examples: `git rebase` blocks other git operations while a rebase is in progress; `npm audit fix` blocks package commands when a required resolution step is pending.

*Applicability:* Directly applicable; the menu must not show normal actions while `initialized-not-populated`, providing a blocking dedicated screen instead.

### AI Agent Critique

- `initialize.py` — `_update_memory_version_in_setup` appends a new `memory_version:` line when the key is absent, without checking whether `memory_version_compatibility` is also absent. The proposed `set_setup_option` in `common.py` must implement the same pattern for any flat key, not just `memory_version`.

- `menu.py` — `check_version_compatibility` currently combines version detection, user prompting, and upgrade invocation in a single function. Extending it to also read `memory_version_compatibility` and conditionally show a migration screen would overload its responsibility. The proposed design correctly separates these: `check_version_compatibility` handles the upgrade path; a new `_show_migration_completion_screen` handles the post-upgrade confirmation.

- `menu.py` — When `check_version_compatibility` runs `initialize.py --upgrade` via `subprocess.run`, the upgrade script will now write `memory_version_compatibility: initialized-not-populated` to `aib-setup.yaml`. After this, the function should still return `True` (caller continues), but `main()` must read the field again and route to the migration screen rather than the normal menu.

- `tests/test_menu.py` — The existing mock in `test_upgrade_choice_continues_menu` does not simulate the `initialize.py --upgrade` writing `initialized-not-populated` to `aib-setup.yaml`. After the request, if the test still uses a `subprocess.run` mock without modifying `aib-setup.yaml`, the new menu logic may not trigger the migration screen during tests. The test must be updated to either: (a) write `memory_version_compatibility: initialized-not-populated` to the test workspace's `aib-setup.yaml` when mocking a successful upgrade, or (b) call the real `initialize.py --upgrade` on a temp workspace.

- `aib-setup.yaml` in the live workspace currently lacks `memory_version_compatibility`. After implementation, running `initialize.py` without `--force` will not add the key (idempotent init skips existing files). The context update task must add the key directly to the live `aib-setup.yaml` as part of implementation, or `get_setup_option` must be used with a safe default of `"compatible"` when the key is absent (backward compatibility for workspaces upgraded to this version before the key was introduced).

- The `archives/` folder name was the original convention used in pre-v1.3 workspaces (evidenced by the 16 timestamped subfolders in `.aib_memory/archives/`). The R-20260702-0903 implementation renamed it to `archive/` (singular). Reverting back preserves continuity with existing archive content.

- `test_menu.py` line 634 already uses `"archives"` (plural) in an assertion: `assert not (workspace / ".aib_memory" / "archives").exists()`. This is currently incorrect with the singular `archive` implementation and will become correct after the rename.

### Edge Cases

- **Workspace without `memory_version_compatibility` key:** Workspaces upgraded to this version before the key was introduced will not have the key in `aib-setup.yaml`. Reading via `get_setup_option` returns `None`; the menu must treat `None` as `compatible` to avoid blocking normal operation on already-migrated workspaces.

- **User confirms completion without running `aib-modify.md`:** The trust model means no verification occurs. If the user confirms prematurely, `context.md` will remain as a placeholder. This is acceptable per design; the user can always re-run `aib-modify.md` manually.

- **`initialize.py --upgrade` fails after archive creation but before writing `initialized-not-populated`:** The field would remain at its previous value (e.g., `compatible` or absent). On next menu start, the version mismatch would be detected again and the upgrade prompt re-shown. This is safe; the archive is already present and the user can retry.

- **Multiple upgrades without confirming:** If the user runs `initialize.py --upgrade` again while `initialized-not-populated` is set, the new upgrade creates a second archive and overwrites the state back to `initialized-not-populated`. The migration screen appears on next menu start, pointing to the latest `input.md` instructions. Acceptable.

- **`aib-setup.yaml` is absent or unreadable when migration screen runs:** `get_setup_option` returns `None`; treated as `compatible`; normal menu shown. Edge case is benign since the workspace would be in an inconsistent state regardless.

- **`archives/` folder already exists alongside `archive/` (current workspace state):** Code change only affects what new upgrade operations use as the target folder. Existing `archive/legacy_*/` content is not moved. Existing `archives/` content from pre-v1.3 is not affected. The two coexist until manually cleaned up.

## Proposed Solution

### High-Level Concept

Extend `aib-setup.yaml` with a `memory_version_compatibility` field that `initialize.py` sets to `initialized-not-populated` after each upgrade, causing `menu.py` to display a migration-completion screen on next startup instead of the normal menu until the user confirms completion. Simultaneously, rename the upgrade archive folder from `archive/` to `archives/` throughout the codebase.

  - Displays explanation: migration instructions are in `input.md`; execute `.aib_brain/prompts/aib-modify.md`.

If the value is `None`, `"compatible"`, or anything other than `"initialized-not-populated"`, proceed to the normal menu loop.

## Decision Register

### Decision Points

#### Decision Point: set_setup_option placement (resolve-autonomously)

- **Tag:** resolve-autonomously
- **Context:** Both `initialize.py` and `menu.py` need to update a single key in `aib-setup.yaml`. The logic can live in `common.py` (shared) or be duplicated in each file.
- **Alternatives:**
  - Option A — Add `set_setup_option` to `common.py`: consistent with `get_setup_option` already present; no code duplication; both files import from `common`.
  - Option B — Duplicate update logic in each file: simpler per-file change but violates DRY; `_update_memory_version_in_setup` in `initialize.py` already handles one key.
- **Resolution:** Option A — `common.py` already exports `get_setup_option`; the symmetrical `set_setup_option` is the natural counterpart. Cited source: `common.py` line 134 — `get_setup_option(directory, option)` pattern; adding the write counterpart in the same module is the AIB convention for shared tooling utilities.

#### Decision Point: migration-screen placement in menu.py (resolve-autonomously)

- **Tag:** resolve-autonomously
- **Context:** The migration-completion screen must block the normal menu. It can be implemented inside `check_version_compatibility`, in `main()`, or in a separate helper function.
- **Alternatives:**
  - Option A — New `_show_migration_completion_screen()` function called from `main()`: single responsibility; `check_version_compatibility` remains focused on upgrade detection; `main()` reads field and routes accordingly.
  - Option B — Extend `check_version_compatibility` to also check `memory_version_compatibility` and show the migration screen: one function handles all compatibility concerns but grows large.
- **Resolution:** Option A — cited source: input.md scope section "Upgrade Completion Workflow" defines a separate screen with distinct options (`Confirm Completed`, `Exit`); the distinct screen intent supports a dedicated function with single responsibility.

#### Decision Point: backward compatibility for absent `memory_version_compatibility` key (resolve-autonomously)

- **Tag:** resolve-autonomously
- **Context:** Workspaces upgraded to this version without the new field must not be blocked. `get_setup_option` returns `None` for absent keys.
- **Alternatives:**
  - Option A — Treat `None` as `"compatible"` in menu.py: existing workspaces proceed normally; field is added on next `initialize.py` run or by direct edit.
  - Option B — Block on `None` and force re-initialization: safe but disruptive for users who just upgraded without this feature.
- **Resolution:** Option A — cited source: `common.py` `get_setup_option` returns `None` on absent key; treating absent as `compatible` is the least-surprise default that does not break existing deployments.

#### Decision Point: archive folder migration for existing `archive/` content (resolve-autonomously)

- **Tag:** resolve-autonomously
- **Context:** The current workspace has both `.aib_memory/archive/legacy_20260702-111731/` and `.aib_memory/archives/` (with pre-v1.3 content). The rename affects only new upgrade runs.
- **Alternatives:**
  - Option A — Update code only; leave existing `archive/` content in place: simplest; no migration risk; developer can clean up manually if desired.
  - Option B — Add migration logic to `initialize.py` that moves `archive/` content to `archives/`: complex; not requested; input states "no backward compatibility required."
- **Resolution:** Option A — cited source: input.md scope section "Archive Folder Simplification": "No backward compatibility is required because there are currently no active users."
