# Analysis: R-20260629-1553

## Overview

- Request ID: R-20260629-1553
- Request title: Replace semver file with YAML setup file in .aib_memory

### Background

Currently, AIB tracks the memory version by placing an empty file named after the SemVer string (e.g., `v1.5.0`) inside `.aib_memory/`. This convention is opaque, not human-readable, and cannot carry additional workspace-level configuration values. The developer requests that this empty marker file be replaced by a structured YAML setup file that (a) encodes the memory version as a named option, (b) can be edited by the human to adjust other workspace-level settings, and (c) provides a dedicated tool so prompts never read the file directly.

### Scope

- Replace `.aib_memory/v1.5.0` (empty semver marker) with a YAML setup file inside `.aib_memory/`.
- Add `memory_version` option to the setup file (same functionality as the file-name convention).
- Add `default_questions_number` option to the setup file; use this value when initializing `input.md` so `minimum_questions` is sourced from the setup file.
- Update `common.py`, `initialize.py`, and `menu.py` to read memory version from the setup file instead of scanning for `v*.*.*` files.
- Update `finalize-input.py` and `_INPUT_SEED_TEMPLATE` handling to respect `default_questions_number`.
- Add new tool `.aib_brain/tools/read-setup.py` for option-specific retrieval of setup values.
- Update existing tests and add new tests covering the setup-file workflow.
- Update `context.md` to reflect the new setup file mechanism.
- Update `.aib_brain/README.md` per `instructions.md` directive.

### Out of scope

- The brain's SemVer marker file (`.aib_brain/v1.5.0`) and the CI `release_bookkeeping.py` workflow are not affected; CI continues to read the brain directory for version information.
- No changes to the YAML frontmatter structure of `input.md` itself (only the seeding logic changes).
- No changes to `edit-context.py`, `create-request.py`, `close-request.py`, `log-entry.py`, `move-request-artifacts.py`, `verify-input.py`, or `verify-context.py`.
- No changes to prompt files (prompts call tools; they do not read setup files directly).

### AI interpretation

The developer wants to replace the opaque empty-file version-marker convention in `.aib_memory/` with a human-editable YAML configuration file. The file acts as the workspace setup registry: it encodes the memory version (the value that was previously embedded in the file name) and the default number of questions that should be pre-populated in new `input.md` headers. Going forward, any prompt that needs a setup value must invoke the new `read-setup.py` tool with a specific option key rather than reading the YAML directly — this enforces mediation and keeps prompts decoupled from the file's internal structure.

The change is scoped exclusively to `.aib_memory/`; the brain's semver marker file and the CI release pipeline remain untouched. The setup file is human-owned and human-editable, which is a notable difference from the old silent empty-file convention. Extensibility is an explicit stated concern: the YAML structure should accommodate future options without requiring tool changes.

## Research Results

### Workspace Pattern Scan

- **Semver file creation**: `initialize.py._seed_semver()` (lines 82–112) creates `{memory_root}/{brain_semver}` as an empty file. It removes stale markers before writing the new one.
- **Semver file reading (memory)**: `common.get_semver(directory)` (lines 75–95) globs `v[0-9]*.[0-9]*.[0-9]*` in the given directory and returns the single match name. Used by `menu.py:check_version_compatibility()` to obtain both `brain_semver` and `memory_semver`.
- **Semver file reading (brain)**: Same `get_semver()` function called with `brain_dir`; brain semver unchanged.
- **Upgrade path**: `initialize.py._run_upgrade()` (line 269) calls `_seed_semver(brain_dir, memory_root, force=True)` to plant the new version marker after archiving the old memory.
- **Input.md seeding**: `_INPUT_SEED_TEMPLATE` constant in `common.py` (lines 21–35) hardcodes `minimum_questions: 5`. Both `initialize.py._seed_memory()` and `finalize-input.py` use this constant. `finalize-input.py` (line 184) preserves the existing `minimum_questions` from the current header on reset.
- **Menu version check**: `menu.py:check_version_compatibility()` (lines 773–844) calls `get_semver(brain_dir)` and `get_semver(memory_dir)`; compares strings; shows upgrade banner on mismatch.
- **Tests affected**: `tests/test_initialize.py` — `TestSemverSeeding` class (six tests) all assume `v1.2.8` file existence. `tests/test_menu.py` may reference version check behavior.
- **Tool list in context.md**: Lists all tools in `File Structure`; new `read-setup.py` must be added.

### Industry Knowledge

- **Configuration-as-a-file (12-factor app)**: Storing configuration in a dedicated file (YAML, TOML, INI) is universally preferred over encoding config in file names or empty markers because it is human-readable, versionable in VCS, and programmatically parseable. This pattern is used by tools like `pyproject.toml`, `.pre-commit-config.yaml`, and `mkdocs.yml`.
  Applicability: High — directly applicable to this request.

- **YAML flat vs. grouped schema**: Flat key–value YAML (`key: value`) is simpler to parse, to extend (just add a key), and to validate. Grouped schemas (nested dicts) add hierarchy that is only beneficial when logical grouping meaningfully aids human readability — not warranted for a small settings file with under 10 keys. This matches how `.github/dependabot.yml` and similar simple config files are structured.
  Applicability: High — guides the default schema decision.

- **Thin tool layer over config (Unix philosophy)**: Providing a single-purpose CLI tool (e.g., `read-setup.py --option X`) to abstract file reads — rather than requiring callers to parse YAML themselves — reduces coupling and improves testability. Pattern seen in `git config --get`, `jq`, `yq`, and AIB's own `input-header.py`.
  Applicability: High — validates the `read-setup.py` tool design requested by the developer.

### AI Agent Critique

- `_INPUT_SEED_TEMPLATE` in `common.py` hardcodes `minimum_questions: 5`; this is a magic number with no explanation. The new request gives it a proper home in `setup.yaml`, but the constant will still need a fallback for workspaces that do not yet have `setup.yaml`.
- `finalize-input.py` (line 184) explicitly preserves `minimum_questions` from the current header rather than re-reading a default — this is correct behaviour for an in-flight request, but the initial seed value for a fresh workspace will come from `default_questions_number` in `setup.yaml`.
- `initialize.py._seed_semver()` removes all stale `v*.*.*` files before touching the new one (line 107–109). This side-effectful clean-up logic must be replicated or adapted for the YAML setup file migration case.
- `common.get_semver()` is called with *both* brain and memory directories in `menu.py`. After this change, the memory call must change but the brain call must remain; the function's dual use must be handled carefully.
- `test_initialize.py:TestSemverSeeding` (six tests) will all break after this change because they assert the existence of `v1.2.8` as a plain file. These tests must be reworked to assert `setup.yaml` content instead.
- `context.md Solution` section (line 69) states: "SemVer marker file in .aib_brain/ encodes active product version as empty file named vMAJOR.MINOR.PATCH." The `.aib_memory/` half of this statement will be incorrect after the change and must be updated.
- `context.md File Structure` section does not list `read-setup.py` in the tools directory; it must be added after implementation.
- `instructions.md` specifies that `.aib_brain/README.md` must be reviewed and updated after each implementation run. This directive applies here.
- `context.md Solution` mentions `edit-context.py supports CRUD operations on Product, Concepts, Requirements, and Solution` — this is unrelated to the current request but is accurate.
- `test_semver_workflow_structure.py` tests the CI GitHub Actions workflow, not the memory semver file. It is not affected by this change.

### Edge Cases

- **Fresh workspace (no `setup.yaml` yet)**: `initialize.py` run with no existing `.aib_memory/` must create `setup.yaml` correctly from scratch.
- **Re-init (idempotency)**: Running `initialize.py` again on a workspace that already has `setup.yaml` must not overwrite it (same idempotency guarantee as the old `v*.*.*` file).
- **Force overwrite (`--force`)**: `initialize.py --force` must replace `setup.yaml` with the brain-derived defaults, matching the old `--force` semantics for the semver file.
- **`--upgrade` path**: When upgrading, old `v*.*.*` empty files in `.aib_memory/` (archived from the old version) must be treated gracefully; the new `setup.yaml` is seeded after archiving.
- **Missing `setup.yaml` during menu version check**: `menu.py:check_version_compatibility()` must handle absent `setup.yaml` gracefully (treat as unknown version, show upgrade prompt).
- **Missing `setup.yaml` during `read-setup.py`**: Tool must return a defined response (error or empty) rather than crashing.
- **Unknown option key in `read-setup.py`**: Requesting an option not present in `setup.yaml` must produce a predictable, documented response.
- **Corrupt or non-YAML `setup.yaml`**: Tool must fail with a clear error rather than a Python traceback.
- **`finalize-input.py` and `default_questions_number`**: On reset, the tool currently preserves `minimum_questions` from the existing header. When `setup.yaml` exists, the question is whether to read `default_questions_number` from setup or continue preserving the in-flight value.

## Proposed Solution

### High-Level Concept

Replace the empty `v*.*.*` marker file in `.aib_memory/` with a human-editable YAML configuration file (name subject to Decision Point `setup-file-name`) containing at minimum `memory_version` and `default_questions_number` options; update all tools that currently scan for the empty marker to read from this file instead, and add a new `read-setup.py` tool that retrieves one named option per invocation so prompts never read the file directly.

### Execution Steps

#### Task 1: Introduce setup-file reading helper in `common.py`

- `.aib_brain/tools/common.py`: Add a new function `get_setup_option(directory: Path, option: str) -> str | None` that opens `{directory}/setup.yaml` (name pending Decision Point `setup-file-name`), parses YAML, and returns the string value for `option` or `None` when absent or file missing.
- `.aib_brain/tools/common.py`: Keep `get_semver(directory)` unchanged for brain-directory use; update its callers in `menu.py` and `initialize.py` to distinguish brain vs. memory paths.

#### Task 2: Replace `_seed_semver` with `_seed_setup` in `initialize.py`

- `.aib_brain/tools/initialize.py`: Replace `_seed_semver(brain_dir, memory_root, force)` with `_seed_setup(brain_dir, memory_root, force)` that creates `setup.yaml` in `memory_root` with `memory_version` set to the brain's semver string and `default_questions_number` set to the default value.
  - Sub-note: During `--upgrade`, the existing stale `v*.*.*` empty files in the archived memory must be noted but are handled by the archive step naturally; no additional clean-up is needed in the fresh memory.
- `.aib_brain/tools/initialize.py`: Update `_run_upgrade()` call from `_seed_semver` to `_seed_setup`.
- `.aib_brain/tools/initialize.py`: Update `_seed_memory()` to read `default_questions_number` from `setup.yaml` (if already created in the same `initialize` run) and pass it to `_INPUT_SEED_TEMPLATE` generation or input.md seeding so `minimum_questions` reflects the setup value.

#### Task 3: Update `menu.py` version check

- `.aib_brain/tools/menu.py`: Update `check_version_compatibility()` to read memory version using `get_setup_option(memory_dir, "memory_version")` instead of `get_semver(memory_dir)`.
  - Sub-note: Brain version check continues to use `get_semver(brain_dir)` unchanged.

#### Task 4: Create new tool `read-setup.py`

- `.aib_brain/tools/read-setup.py`: Create a new script that accepts `--workspace .` and `--option <key>` arguments, reads `setup.yaml`, and prints just the value for the requested option to stdout. Exit code and behavior when option is absent are pending Decision Points `tool-option-not-found` and `tool-output-format`.

#### Task 5: Update `finalize-input.py` integration

- `.aib_brain/tools/finalize-input.py`: Review whether the reset path should read `default_questions_number` from `setup.yaml` when no `minimum_questions` override is available. Behaviour is pending Decision Point `finalize-input-integration`.
  > Pending: depends on Decision Point finalize-input-integration

#### Task 6: Update tests

- `tests/test_initialize.py`: Rewrite `TestSemverSeeding` class to assert `setup.yaml` content rather than `v1.2.8` file existence; add tests for `setup.yaml` idempotency, `--force` overwrite, and `--upgrade` seeding.
- `tests/test_menu.py`: Update version-check tests (if any) to use `setup.yaml` in place of `v*.*.*` mock files.
- `tests/`: Add `test_read_setup.py` covering tool invocation, missing option, missing file, and corrupt YAML.

#### Task 7: Context and documentation update

- `.aib_memory/context.md`: Update `Solution` statement about `SemVer marker file in .aib_brain/` to clarify that `.aib_memory/` now uses a `setup.yaml` file. Add new `Solution` entry describing `read-setup.py`. Update `File Structure` to list `read-setup.py` in tools.
- `.aib_brain/README.md`: Review and update to reflect the new setup-file mechanism and `read-setup.py` tool.

## Decision Register

### Decision Points

#### Decision Point: setup-file-name

- Tag: ask
- Rationale/Resolution: The developer specified "YAML setup file" but did not name the file. Options include `setup.yaml`, `aib-setup.yaml`, `memory.yaml`, and `aib-memory.yaml`. The choice affects how the file appears in directory listings, conventions documentation, and future references. No workspace source resolves this explicitly.
- Alternatives:
  - Option A: `setup.yaml` — short, generic name consistent with conventions like `pyproject.toml`; easy to type.
  - Option B: `aib-setup.yaml` — prefixed with `aib-` to signal ownership; reduces ambiguity if workspace has other `setup.yaml` files.
  - Option C: `memory.yaml` — mirrors the `.aib_memory/` folder name; intuitively co-located.

#### Decision Point: yaml-schema-structure

- Tag: ask
- Rationale/Resolution: The developer says "options with their values" and "extensible". This is compatible with flat YAML but also with grouped. No workspace convention mandates one over the other.
- Alternatives:
  - Option A: Flat top-level keys — `memory_version: v1.5.0` and `default_questions_number: 5` at root level. Simplest to parse and extend by adding keys.
  - Option B: Grouped under an `options:` mapping — mirrors `input.md` YAML frontmatter `options:` group; consistent with AIB's existing YAML style.
  - Option C: Grouped under named sections (e.g., `versioning:`, `defaults:`) — maximally extensible but adds structure overhead for only two initial keys.

#### Decision Point: tool-option-not-found

- Tag: ask
- Rationale/Resolution: When `read-setup.py --option X` is called and key `X` does not exist in `setup.yaml`, the tool's behaviour is not specified. The choice affects how calling prompts detect missing options and whether silent fallback is safe.
- Alternatives:
  - Option A: Exit with code 1 and print an error to stderr — fails loudly; calling prompt must check exit code.
  - Option B: Exit with code 0, print empty string to stdout — silent fallback; calling prompt can default on empty output.
  - Option C: Exit with code 0, print a configurable default value when specified via `--default` flag — flexible but adds complexity to the tool interface.

#### Decision Point: tool-output-format

- Tag: ask
- Rationale/Resolution: The tool output is consumed by prompts. Prompts currently parse `input-header.py` output as `key=value` lines. Whether `read-setup.py` should match that format or emit just the bare value affects prompt parsing.
- Alternatives:
  - Option A: Print bare value only (e.g., `v1.5.0\n`) — simplest for direct shell substitution and comparison.
  - Option B: Print `key=value` line (e.g., `memory_version=v1.5.0`) — consistent with `input-header.py` output style used by existing prompts.

#### Decision Point: setup-yaml-template

- Tag: ask
- Rationale/Resolution: `initialize.py` can generate `setup.yaml` from inline defaults baked into the script, or from a template file stored in `.aib_brain/`. A `.aib_brain/` template would be included in the versioned zip archive and distributed with AIB, allowing updates without changing Python code.
- Alternatives:
  - Option A: Generate `setup.yaml` inline in `initialize.py` — no extra file; defaults are code-defined; changing defaults requires a code change.
  - Option B: Provide a `setup.yaml.template` (or `setup.yaml`) in `.aib_brain/` that `initialize.py` copies — template is human-readable in the distribution; updating defaults is a template edit, not a code change.

#### Decision Point: finalize-input-integration

- Tag: ask
- Rationale/Resolution: `finalize-input.py` resets `input.md` after each analysis run. Currently it preserves the existing `minimum_questions` value from the in-flight request header. The question is whether after this change the reset should also consult `default_questions_number` from `setup.yaml`.
- Alternatives:
  - Option A: Preserve existing `minimum_questions` from the current header (current behaviour, unchanged) — safe; user-set values are never overridden on reset.
  - Option B: Read `default_questions_number` from `setup.yaml` and always reset `minimum_questions` to this value on `finalize-input.py` run — every reset reflects the current workspace default; user in-flight overrides are lost.

#### Decision Point: upgrade-preserve-setup

- Tag: ask
- Rationale/Resolution: When `initialize.py --upgrade` runs, it archives old `.aib_memory/` and re-seeds a fresh one. If the user has customised `setup.yaml` (e.g., changed `default_questions_number`), this customisation may be overwritten. The current upgrade behaviour restores `instructions.md` and `input.md` but not version files.
- Alternatives:
  - Option A: Always overwrite `setup.yaml` with fresh brain defaults on upgrade — simple; user loses customisations; consistent with current semver file replacement semantics.
  - Option B: Restore `setup.yaml` from the archive if present (like `instructions.md`) — preserves user customisations; user does not have to re-apply after upgrade.
  - Option C: Merge: copy archive `setup.yaml` but update `memory_version` from brain defaults — preserves custom options while keeping version current.

#### Decision Point: seed-template-fallback

- Tag: ask
- Rationale/Resolution: `_INPUT_SEED_TEMPLATE` in `common.py` hardcodes `minimum_questions: 5`. After this change, the canonical default is `default_questions_number` in `setup.yaml`. If `setup.yaml` is absent (e.g., very first `finalize-input.py` run before `initialize.py` has been re-run), a fallback is needed.
- Alternatives:
  - Option A: Keep hardcoded `minimum_questions: 5` in `_INPUT_SEED_TEMPLATE` as fallback — backward-compatible; no crash on missing setup.yaml; default stays accurate for legacy workspaces.
  - Option B: Remove hardcoded default; require `setup.yaml` to be present — cleaner; fails explicitly if setup file is missing, prompting the user to run initialize.

#### Decision Point: tool-schema-validation

- Tag: ask
- Rationale/Resolution: `read-setup.py` can either accept any key from any YAML file structure, or it can validate that the file matches the expected schema (known keys, correct types). Validation helps detect corrupt or manually mis-edited files early.
- Alternatives:
  - Option A: No schema validation — just read the file and return the requested key's value; unrecognised keys do not produce errors.
  - Option B: Validate known keys and types on every invocation — fails fast on invalid setup.yaml; reduces silent misbehaviour.
  - Option C: Validate only on explicit `--validate` flag — validation is opt-in; default behaviour is lenient.

#### Decision Point: brain-semver-unchanged

- Tag: resolve-autonomously
- Rationale/Resolution: The developer's `## Input` explicitly states "the semver file to be replaced with a YAML setup file" in context of ".aib_memory/ folder". The brain semver file (`.aib_brain/v1.5.0`) is not in `.aib_memory/` and is explicitly used by CI (`release_bookkeeping.py`). Changing it is therefore out of scope. Source: `input.md ## Input` — "Instead of empty semver file in .aib_memory/ folder".
- Chosen alternative: Brain semver file (`.aib_brain/v1.5.0`) and `release_bookkeeping.py` remain unchanged.

#### Decision Point: default-questions-field-name

- Tag: resolve-autonomously
- Rationale/Resolution: Developer's `## Input` uses the exact phrase "Add default questions number as setup option". The natural snake_case rendering is `default_questions_number`. Source: `input.md ## Input` — "Add default questions number as setup option in the setup file."
- Chosen alternative: The YAML option key is `default_questions_number`.

#### Decision Point: test-update-scope

- Tag: resolve-autonomously
- Rationale/Resolution: `TestSemverSeeding` in `test_initialize.py` explicitly tests the empty-file convention that is being removed. Keeping these tests passing requires updating them; not updating them would leave failing tests. This is an unavoidable consequence of the implementation. Source: `test_initialize.py` lines 60–104 show direct assertions on `v1.2.8` file existence.
- Chosen alternative: Rewrite `TestSemverSeeding` to test `setup.yaml` creation and content; add new test class `TestSetupFileSeeding`; add `test_read_setup.py`.
