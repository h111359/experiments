# Analysis: R-20260619-1038

- Request ID: R-20260619-1038
- Request Title: Refactor context.md structure and update related tools

## Overview

### Background

The current AIB context.md format uses 22 valid area names with atomic statements following the `- TYPE: text` pattern where TYPE is one of 9 single-letter type codes (N, R, C, D, etc.). This granular 22-area structure has accumulated over successive requests and presents cognitive overhead for both human and AI consumers. The developer requests a simpler 6-section structure (Product, Concepts, Requirements, Solution, File Structure, References) that consolidates areas by purpose and introduces a cleaner statement format. The new Requirements section adopts RFC 2119 modality vocabulary (`[MUST|MUST NOT|OPTIONAL]`), while other sections use plain text bullets.

### Scope

- Redefine context.md structure to 6 sections: Product, Concepts, Requirements, Solution, File Structure, References
- Rewrite `context-convention.md` to define the new structure, statement formats, and quality gates
- Rewrite `verify-context.py` to validate the new 6-section structure
- Update `aib-refresh-context.md` to generate the new format and detect/fix deviations
- Revise `aib-analyze.md` to reference new section names in context update analysis and plan generation
- Revise `aib-implement.md` to record decisions in new context sections using tools
- Migrate existing `context.md` content to the new 6-section structure
- Update automated test files that assert on the old format

### Out of scope

- CI scripts (`scripts/release_bookkeeping.py`) — no structural context change needed
- Other convention files (`coding-*.md`, `q-block-convention.md`, `analysis-convention.md`, `plan-convention.md`, `requirements-analysis-convention.md`) — not referenced in request
- AIB tool scripts not coupled to context structure: `close-request.py`, `create-request.py`, `finalize-input.py`, `input-header.py`, `menu.py`, `move-request-artifacts.py`, `file-inventory.py`
- Documentation under `docs/` and `recordings/`
- Product feature logic changes — this is a pure format refactor

## Input Interpretation

### User Original Inputs

MUST: The whole context to be in form of statements.

Refactor the structure. The new structure should have the following sections:
1. `## Product` — purpose, stakeholders, scope; format: `- <text>`
2. `## Concepts` — general information: domain, terms, facts; format: `- <text>`
3. `## Requirements` — product-specific directives: user needs, constraints, preferences, product-specific definitions; format: `- [MUST|MUST NOT|OPTIONAL]: <text>`
4. `## Solution` — decisions on how to realize the requirements; format: `- <text>`
5. `## File Structure` — keep same format and content
6. `## References` — links to other documents; format: `### File Name / Location: <path> / Summary: <text>`

Mapping from current to new:
- Product Identity, Project overview → Product
- Change Management → Solution
- Domain → Concepts
- Best Practices → Requirements or Concepts
- Functionality → Requirements
- Technical Design, Technology Stack, Networking and Connectivity, Data Structures, Data Flow, Development, Deployment → Solution
- Processes, User Interface, Security, Operations, Durability, Observability, Documentation → Requirements or Solution

Also modify: context-convention.md, verify-context.py, aib-refresh-context.md, aib-analyze.md, aib-implement.md.

### AI Interpretation

This request simplifies the AIB context system from a granular 22-area classified-statement model to a purpose-oriented 6-section model. The core semantic changes are:

1. **Section consolidation**: 22 operational areas collapse to 4 content sections (Product/Concepts/Requirements/Solution) plus File Structure and References.

2. **Statement format simplification**: The single-letter type prefix (N, R, C, D, etc.) is replaced by: plain bullets `- <text>` for Product, Concepts, Solution; modality prefix `- [MUST|MUST NOT|OPTIONAL]: <text>` for Requirements.

3. **Tool cascade**: context-convention.md defines truth → verify-context.py enforces it → edit-context.py enables CRUD → aib-refresh-context.md generates it → aib-analyze.md and aib-implement.md consume the new section names.

4. **Content migration**: All existing context.md statements must be remapped to the new 6 sections using the developer-provided mapping table before verification will pass.

This is an internal AIB framework maintenance request. Primary actors: AIB developers and the AI automation agent.

### Industry Knowledge

1. **Viewpoint-based architecture documentation** (IEEE 1471 / ISO 42010): Organizing context into purpose-oriented sections (stakeholder intent → requirements → solution decisions) is an established pattern in architecture documentation. The Product/Requirements/Solution triad maps directly to the stakeholder, needs, and system viewpoints defined in ISO 42010. Applicability: HIGH — the proposed 6-section model directly applies this pattern to AIB context management.

2. **RFC 2119 modality vocabulary** (IETF BCP 14): Using MUST/MUST NOT/OPTIONAL as explicit modality prefixes in the Requirements section is consistent with the normative language AIB already uses in all convention files. Adopting this vocabulary in context.md statements creates a consistent, machine-parseable signal for requirement strength. Applicability: HIGH — AIB tooling already parses RFC 2119 terms; this extends that convention to context content.

3. **AI context engineering separation** (Anthropic prompting guidance, emerging LLM context management patterns): Separating what-a-product-IS (Product/Concepts) from what-it-REQUIRES (Requirements) from HOW-it-works (Solution) matches the problem-space vs. solution-space distinction recommended in AI context management literature. Flat, undifferentiated context degrades LLM reasoning quality. Applicability: HIGH — this is the primary motivation for the refactor; cleaner categorical separation improves AI agent prompt accuracy.

### AI Agent Critique

Issues found across all files read in this analysis run:

- [misalignment] `aib-refresh-context.md` Phase 1 step 4 and Phase 4.3 describe a hash-based index format (`AREA-TYPE-HASH`) that does not match the actual current `context.md` format (`- TYPE: text`). The prompt was not updated when the hash scheme was removed.

- [contradiction] `aib-implement.md` Step 4 says "Read `.aib_memory/analysis-<request_id>.md`" but the Rules section explicitly says "Must not read the Analysis." These directives conflict.

- [inconsistency] `aib-refresh-context.md` Phase 4.2 says "free-form prose content" for Product Identity, while Phase 4.3 says "atomic statements." `context-convention.md` says "atomic statements when possible, prose allowed when needed." Three documents give three different guidance levels.

- [redundancy] `aib-refresh-context.md` Phase 4b Pass 1 re-reads the input.md YAML header to resolve request_id, but request_id is already resolved in Phase 1 Preflight.

- [format drift] `aib-refresh-context.md` has phases numbered 1, 2, 4, 4b, 5, 6, 7 — Phase 3 is absent, creating a numbering gap.

- [misplaced content] `aib-analyze.md` contains both `### 5.6 Step 6 — Context Review (legacy anchor)` and `### S06. Step 6 — Context Review` as separate headings at the same level, creating a duplicate that could confuse execution.

- [inconsistency] `context.md` uses `## Data structures` and `## Data flow` (lowercase second word) while the VALID_AREAS set in both tools uses `"Data structures"` and `"Data flow"` — the casing matches, but the request's mapping table uses `Data Structures` (capital S) and `Data Flow` (capital F), creating a potential confusion point.

- [redundancy] `context-convention.md` lists "Concepts" as one of the 22 VALID_AREAS, and the new requested format also defines `## Concepts` as a primary section. While the names coincide, their meaning is different: the old area "Concepts" was a sub-area for definitions; the new `## Concepts` is a primary section covering all general knowledge.

- [unclear wording] `context-convention.md` Section 1 says `## 1. Product Identity` is required but `## Files` is implicitly required (always present in all examples). The convention does not explicitly state `## Files` is mandatory.

- [logical error] `verify-context.py` `_get_area_sections` skips heading `"1. Product Identity"` and `"Files"` but does not skip `"1. Product Identity"` in `check_area_headings_valid`; instead that function separately excludes it. The two exclusion mechanisms are slightly inconsistent.

### Edge Cases

- **Empty References section**: If `## References` exists with no sub-entries, verify-context.py must handle gracefully without treating the section as non-empty (since it's optional).

- **MUST/MUST NOT/OPTIONAL format in Requirements**: Lines in `## Requirements` that start with `- ` but lack the modality prefix should fail format validation. Non-bullet lines (blank or comment) must be handled without false positives.

- **File Structure tree format**: `## File Structure` uses an indented tree format, not bullet statements. verify-context.py must NOT enforce statement format (`- <text>`) in this section.

- **context.md migration timing**: After updating context-convention.md and verify-context.py, existing context.md will fail verify-context.py. Migration MUST occur before any verify-context.py invocation against the live context.md.

- **edit-context.py area name mismatch**: If edit-context.py is not updated, any plan task in future requests referencing new section names will fail with "Invalid area name." This blocks all future context update tasks until resolved.

- **aib-refresh-context.md Phase 6 re-validation**: Phase 6 currently validates against `## 1. Product Identity`, `## 2. Statements`, `## 3. Workspace File Inventory`. If not updated to the new 6-section headings, it will revert every generated context.md to non-conformance.

- **Test VALID_CONTEXT fixture**: The baseline fixture in `test_verify_context.py` uses `## Functionality` and `## Project overview` headings. After update, these will be invalid area names; the fixture must use `## Product`, `## Concepts`, etc.

## Proposed Solution

### High-Level Concept

Replace the 22-area classified-statement context model with a 6-section model (Product, Concepts, Requirements, Solution, File Structure, References) by rewriting the convention file, updating all dependent tools and prompts to enforce and generate the new format, and migrating the existing context.md content using the developer-provided mapping.

### Execution Steps

1. Rewrite `.aib_brain/conventions/context-convention.md` to define the 6-section structure, new statement formats (`- <text>` for Product/Concepts/Solution, `- [MUST|MUST NOT|OPTIONAL]: <text>` for Requirements), File Structure tree format retention, References sub-heading format, and updated quality gates.
2. Rewrite `.aib_brain/tools/verify-context.py` replacing the 22-item VALID_AREAS set and all 10 check functions with logic validating the new 6-section structure and format rules.
3. Update `.aib_brain/tools/edit-context.py` VALID_AREAS and AREA_ORDER to the 4 content section names (Product, Concepts, Requirements, Solution); adapt statement insertion and type handling for the new format.
4. Rewrite the synthesis phases of `.aib_brain/prompts/aib-refresh-context.md` to generate the 6-section output format; update Phase 6 validation against new section headings; update Phase 7 tool invocation.
5. Migrate `.aib_memory/context.md` content using the developer's mapping table: map existing statements to Product, Concepts, Requirements, or Solution; preserve File Structure content; populate References if applicable.
6. Run `verify-context.py` against migrated context.md; resolve any format failures.
7. Revise `.aib_brain/prompts/aib-analyze.md` — update S05.8 (Context Update Analysis) and S09.2 (plan generation) to reference new section names; correct legacy heading duplicate at S06.
8. Revise `.aib_brain/prompts/aib-implement.md` — update documentation requirements to reflect new section names; correct Step 4 vs. Rules contradiction.
9. Update `tests/test_verify_context.py` to use new section names in VALID_CONTEXT fixture and assert the new check count.
10. Update `tests/test_context_formatting_rules.py` to assert the new 6-section structure and format rules.
11. Run full test suite; resolve any failures.

### Why this approach?

AIB follows a convention-first architecture: the convention file is the single source of truth, and all tools and prompts derive their behavior from it. Updating context-convention.md first establishes the new truth before any enforcer or generator is changed. Updating verify-context.py second enables immediate validation of generated output. Updating edit-context.py third ensures context update tasks in the plan can reference new section names. This top-down sequence mirrors the successful approach taken in R-20260528-0859 (the prior context format change).

#### Decision Point: edit-context.py Update Scope

- Tag: `resolved-by-user`

#### Decision Point: Type Letter Handling

- Tag: `resolved-by-user`

The `--type` argument is removed from edit-context.py for non-Requirements sections. verify-context.py validates modality prefix only in Requirements statements. This is a clean break with the old type-letter model.

#### Decision Point: Test Suite Updates

- Tag: `resolved-by-user`

The developer selected Option A: Update all affected tests as part of this request. The VALID_CONTEXT fixture in `test_verify_context.py` will be updated to use new section names; expected check count will be updated; all convention-content assertions in `test_context_formatting_rules.py` will be replaced with assertions for the 6-section structure. #### Decision Point: Context.md Migration Strategy

- Tag: `resolved-by-user`

The developer selected Option A: Migrate context.md manually as an explicit plan task. The implement agent will read the developer-provided mapping table and current context.md, then rewrite context.md section by section in the new 6-section format. Ambiguous items (e.g., Best Practices → Requirements or Concepts) will be placed based on content inspection. This gives precise control over content placement and produces an auditable migration artifact in the plan.

#### Decision Point: References Section Validation

- Tag: `resolved-by-user`

The developer selected Option A: Validate References section structure strictly. verify-context.py will check that each entry under `## References` is a `###` sub-heading followed by a line containing `Location:` and a line containing `Summary:`. Malformed entries will cause the check to fail. An empty `## References` section (no sub-entries) is treated as valid since the section is optional by nature.
