# Analysis: R-20260626-1722

## Overview

**Request ID:** R-20260626-1722

**Request title:** Add input.md frontmatter groups, logging, and prompt CLI options

### Background

The AIB framework's input.md YAML frontmatter currently uses a flat structure mixing tool-managed state fields with user-configurable option fields. This creates confusion about which fields users should modify. Additionally, there is no per-request audit trail of prompt execution activity, making it difficult to trace what happened during a request lifecycle. Finally, aib-analyze.md and aib-implement.md do not support runtime modifier flags that would allow developers to skip phases or run in fast-path modes, forcing full execution even in scenarios where shorter paths would suffice.

### Scope

- Restructure `.aib_memory/input.md` YAML frontmatter into two clearly named groups: one for tool-managed state, one for user-configurable options.
- Update all tools and tests that read or write the frontmatter to support the new structure.
- Create a new Python tool `.aib_brain/tools/log-entry.py` that appends timestamped entries to `.aib_memory/log_<request_id>.md` and emits them to stdout.
- Create `.aib_brain/conventions/log-convention.md` as the normative specification for the log format and usage.
- Modify `.aib_brain/prompts/aib-analyze.md`, `.aib_brain/prompts/aib-implement.md`, and `.aib_brain/prompts/aib-refresh-context.md` to invoke the log tool at key points.
- Add `--plan-only` modifier to aib-analyze.md that skips analysis generation and questions and jumps directly to plan generation with autonomous decision-making.
- Add `--exec-input` modifier to aib-implement.md that skips reading the plan file and executes implementation based solely on the `## Input` section of input.md.

### Out of scope

- Changes to any existing conventions other than input-convention.md, and the new log-convention.md.
- Changes to aib-refresh-context.md beyond adding logging invocations.
- Changes to the Q-block format or Q-block convention.
- Changes to context.md format or context-convention.md.
- Changes to CI workflows or release bookkeeping scripts.
- Adding log-entry.py to the menu.py UI.

## Input Interpretation

### User Original Inputs

Goal 1: Restructure input.md frontmatter into two groups. State group (tool-managed): request_id, title, state (renamed from status), input_verification_result, context_verification_result. Options group (user-configurable): minimum_questions, input_verification_enabled, context_verification_enabled. Modify the flat YAML structure into two nested groups.

Goal 2: Create a request-specific log tool. New Python script in .aib_brain/tools/. Creates `.aib_memory/log_<request_id>.md` if not existing, appends entries in format `YYYYMMDD-HHmmss: log message` (UTC). Tool accepts only the log message; reads request_id from input.md automatically. Errors if no active request. All three prompts (aib-analyze.md, aib-implement.md, aib-refresh-context.md) must be updated to log their actions.

Goal 3: Add `--plan-only` modifier to aib-analyze.md. If the user chat message contains `--plan-only`, skip analysis file generation, skip clarifying questions, jump to plan generation, and generate recommended answers/assumptions for any decision points encountered.

Goal 4: Add `--exec-input` modifier to aib-implement.md. If the user chat message contains `--exec-input`, do not read the plan file; execute entirely based on the `## Input` block in input.md.

### AI Interpretation

The request addresses four independent but thematically related improvements to the AIB framework infrastructure:

**Frontmatter restructuring:** The current flat YAML schema in input.md conflates two conceptually distinct categories of fields — workflow state managed exclusively by prompts and tools, and developer-configurable options. The restructuring introduces a two-level schema: a `state:` nested block for tool-managed fields and an expanded `options:` nested block for user-configurable fields. This change affects `common.py` (parse/write functions), `input-header.py` (CLI), `verify-input.py` (validation), `finalize-input.py` (seed template), `initialize.py` (seed template), `input-convention.md` (schema documentation), and all tests that construct or assert on the frontmatter. The "(rename from status)" annotation in the original input is interpreted as a historical note indicating the workflow-state field was formerly named `status` and is now `state`; the field retains its current name `state`. However, nesting `state` under a group also named `state:` creates a naming collision that constitutes a Decision Point.

**Log tool:** A minimal, single-purpose Python tool that: (a) reads request_id from input.md YAML header via the existing parse_input_header helper, (b) errors with a non-zero exit code if state is idle, (c) formats a log entry as `YYYYMMDD-HHmmss: <message>` using UTC time, (d) appends the entry to `.aib_memory/log_<request_id>.md` (creating the file if absent), and (e) prints the same entry to stdout. The tool is named `log-entry.py` following the verb-noun naming convention used by other AIB tools (finalize-input.py, create-request.py, close-request.py).

**--plan-only:** The aib-analyze.md prompt reads the user's chat message. When `--plan-only` is detected, the prompt bypasses S05 (analysis file generation) and S08 (question generation) and jumps directly to S09 (plan generation), substituting any `ask`-tagged Decision Points with autonomously-chosen recommended alternatives documented inline in the plan file. This mode is additive — it does not remove any existing analysis file but does not create or modify one.

**--exec-input:** The aib-implement.md prompt reads the user's chat message. When `--exec-input` is detected, Step 4 (plan file read) is replaced by reading `## Input` from input.md as the sole execution directive. All other steps (workspace-convention reads, test execution, request closure) remain in effect unless the Decision Point on context.md reading resolves otherwise.

## Research Results

### Workspace Pattern Scan

**Affected components and cross-references:**

- `common.py` — `parse_input_header()` and `write_input_header()` are called by: `input-header.py`, `finalize-input.py`, `verify-input.py`, `create-request.py`, `close-request.py`, `menu.py`. Any structural change to the YAML schema is a blast-radius change affecting all of these.

- `verify-input.py` — `_extract_raw_yaml_keys()` uses regex to detect top-level keys. For the new nested structure, top-level keys would be `state` and `options` (two keys) instead of the current eight. The `check_required_yaml_keys_present()` function and `REQUIRED_YAML_KEYS` tuple must be updated accordingly. Checks for `check_enabled_flags_are_boolean` and `check_result_flags_valid` scan by key name at the top level; these must be updated to scan within nested blocks.

- `finalize-input.py` — `_SEED_TEMPLATE` is a hardcoded string constant at the top of the module. It must reflect the new YAML structure. The `_is_stub_equivalent()` function strips frontmatter and compares bodies, which is format-agnostic and should require no changes.

- `initialize.py` — Contains a separate hardcoded `input_seed` string literal at line 69. Must be updated to match the new structure.

- `test_tools_common.py` — `INPUT_MD_IDLE` fixture uses the old flat format. `TestParseInputHeader` and `TestWriteInputHeader` test classes will fail with new nested format unless updated.

- `test_verify_input.py`, `test_finalize_input.py`, `test_initialize.py` — likely contain hardcoded YAML strings that must be updated.

- `test_lifecycle_e2e.py` — end-to-end test likely creates input.md with the old format; must be reviewed.

- `move-request-artifacts.py` — `_ARTIFACT_TYPES = ("plan", "analysis")` defines which files are moved on close. Log file lifecycle (move or leave) is a Decision Point.

- `aib-refresh-context.md` — Currently does not read or write input.md during normal operation (it only writes context.md). Adding log-entry.py invocations requires that an active request exists at the time of execution; this is not guaranteed, making this a Decision Point.

**Prior solutions consulted:**

- The `options:` nested block in the current frontmatter (containing only `minimum_questions`) establishes the pattern for nested YAML groups. Extending this pattern to the `state:` group is consistent with existing tooling.
- The `artifact_name()` helper in common.py constructs filenames as `<type>-<request_id>.md`. The log file pattern `.aib_memory/log_<request_id>.md` uses an underscore separator instead of a hyphen; this inconsistency should be noted but was explicitly specified by the developer.

### Industry Knowledge

- **YAML nested mapping best practices (YAML 1.2 specification):** Nested mappings are idiomatic for grouping related keys. Using a top-level key named `state:` while having a sub-key also named `state:` is syntactically valid YAML but creates semantic ambiguity for human readers. The YAML community convention (from CloudFormation, Ansible, GitHub Actions YAML schemas) is to use distinct key names at each nesting level. Applicability: directly applicable — confirms that naming collision should be resolved.

- **Audit logging in CLI tools (12-Factor App, UNIX tool design):** Tools that modify state should produce an append-only audit log. Log entries should include UTC timestamps to avoid timezone ambiguity. The Python `datetime.utcnow()` or `datetime.now(timezone.utc)` pattern is standard for UTC timestamps in log tools. Applicability: directly confirms the tool design (UTC time, append-only, stdout + file dual output).

- **Single-responsibility principle (SOLID):** A tool that does one thing well (appending a log entry) is preferable to embedding logging logic directly in prompts. By accepting only a message and auto-resolving the request context, log-entry.py follows the UNIX philosophy of small composable tools. Applicability: confirms the tool API design (message only, auto-resolves request_id).

### AI Agent Critique

- `common.py` `write_input_header()` contains the YAML serialization logic as a f-string template (lines 279-292). This is fragile when the schema changes because the template is not derived from the data structure. Changing the schema requires careful manual f-string editing with no compile-time safety. This is a pre-existing issue, not introduced by this request.

- `verify-input.py` `_extract_raw_yaml_keys()` (line 88-101) relies on regex to detect top-level keys by checking for no leading whitespace. Under the new two-group schema, only `state` and `options` will appear at the top level. The function itself is correctly written but the `REQUIRED_YAML_KEYS` constant at line 17 enumerates all eight keys as top-level, which will break under the new structure.

- `finalize-input.py` and `initialize.py` each independently contain hardcoded seed templates. These are two sources of truth that must be kept in sync. Any future schema change requires updating both independently. This is a pre-existing maintainability risk.

- `input-convention.md` Section 2 states "All eight keys MUST be present; no additional top-level keys are permitted." After restructuring, this statement will be incorrect: only two top-level keys (`state:` and `options:`) will exist, each containing nested sub-keys. The convention must be comprehensively updated.

- `aib-analyze.md` S01.1a invokes `verify-input.py` which currently checks for all eight keys at the top level. After the schema change, this check will fail on any existing input.md that uses the old flat format unless the tool handles backward compatibility.

- The `## Options` section in the body of input.md (containing `Minimum questions:`) is separate from the `options:` YAML frontmatter block. The developer's input does not mention changing the body section; only the YAML frontmatter is to be restructured. This distinction should be preserved.

- The log file naming pattern `log_<request_id>.md` uses underscores while all other artifact files use hyphens (`plan-<request_id>.md`, `analysis-<request_id>.md`). This inconsistency is specified by the developer and should be implemented as specified.

### Edge Cases

- **State transition during --plan-only:** If the user invokes `--plan-only` when state is `questions_generated`, there are unanswered questions in input.md. The --plan-only mode should either consume and autonomously answer these questions, or clear them and proceed. Undefined behavior here could produce an inconsistent state.

- **--exec-input with no ## Input content:** If the developer invokes `--exec-input` but `## Input` in input.md is empty or stub-equivalent, the implement prompt has no instructions. A guard check (analogous to Appendix A's check in aib-analyze.md) is needed.

- **log-entry.py invoked after request is closed (state == idle):** The tool should emit a clear error and return non-zero exit code. The aib-implement.md prompt invokes log-entry.py both before and after the close-request.py step; the final log entry must be written before close-request.py is called (or the tool must tolerate post-close invocation if the log file already exists).

- **Log file already exists for a re-run:** The tool must append, not overwrite. The `_is_stub_equivalent` check in finalize-input.py clears input.md but should not clear the log file, as the log is a cumulative audit trail.

- **Concurrent execution:** If two aib sessions somehow run simultaneously on the same workspace, both appending to the same log file, file-level race conditions could corrupt entries. Append-mode file I/O in Python is not atomic on all platforms. This is low-risk for the single-developer AIB use case.

- **Old input.md format during transition:** Workspaces that have already been initialized with the old flat format will need to be migrated. The migration path depends on the DP-backward-compatibility resolution.

- **--plan-only with no existing analysis:** Plan generation (S09) uses the analysis's `### Execution Steps` section as the primary source. Without an analysis, the planner must derive execution steps inline. The prompt must specify fallback behavior.

Requirements Gate: 8/8 PASS — all categories satisfied.

## Proposed Solution

### High-Level Concept

Refactor the input.md YAML frontmatter into a two-group nested schema (`state:` for tool-managed fields and `options:` for user-configurable fields), updating all dependent tools and tests; introduce a new `log-entry.py` tool and `log-convention.md` for per-request audit logging integrated into all three prompts; and add read-time modifier flags (`--plan-only` in aib-analyze.md, `--exec-input` in aib-implement.md) that enable phase-skipping fast-paths.
