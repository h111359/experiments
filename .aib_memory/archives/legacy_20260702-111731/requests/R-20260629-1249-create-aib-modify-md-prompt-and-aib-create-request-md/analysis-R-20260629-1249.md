# Analysis: R-20260629-1249

## Overview

- Request ID: R-20260629-1249
- Request title: Create aib-modify.md prompt and aib-create-request.md

### Background

The current AIB workflow separates analysis (`aib-analyze.md`) from implementation (`aib-implement.md`), requiring a full analysis-plan cycle before any change can be applied to the workspace. There is no lightweight "execute this directly" path that still integrates with the request lifecycle and respects workspace conventions. Additionally, the Auto-Request Creation logic (Appendix A) is embedded inline in `aib-analyze.md`, making it unreachable by other prompts that may also need to auto-create a request when invoked without one. The developer requests a quick-execute prompt (`aib-modify.md`) and a reusable, standalone request-creation prompt (`aib-create-request.md`) to address both limitations.

### Scope

- Create `.aib_brain/prompts/aib-create-request.md` as a standalone prompt encapsulating the Auto-Request Creation Branch (Appendix A) currently embedded in `aib-analyze.md`.
- Create `.aib_brain/prompts/aib-modify.md` as a new direct-execution prompt that reads `input.md ## Input` as an implementation directive, follows `instructions.md`, and considers `context.md`, without finalizing or closing the active request.
- Modify `.aib_brain/prompts/aib-analyze.md` to replace the inline Appendix A content with a delegation instruction to execute `aib-create-request.md`.
- Update `.aib_memory/context.md` to reflect the two new prompts in the File Structure and Solution sections.
- Update `.aib_brain/README.md` to document the new prompts.

### Out of scope

- Changes to `aib-implement.md`, `aib-refresh-context.md`, or any other existing prompt beyond `aib-analyze.md`.
- Changes to any tool scripts under `.aib_brain/tools/`.
- Changes to convention files under `.aib_brain/conventions/`.
- New automated test files (new prompts are `.md` files, not executable Python code).
- Modification of any product source code, CI workflow, or scripts outside `.aib_brain/` and `.aib_memory/`.

## Input Interpretation

### User Original Inputs

"Goal: To be created new prompt .aib_brain\prompts\aib-modify.md which should take the Input section from input.md file as direct instruction and should implement it. Like in .aib_brain\prompts\aib-implement.md, the instructions in .aib_memory\instructions.md file should be followed and the .aib_memory\context.md should be considered. But no finalization of the request should be made. If there is no active request detected - it should be created. For the purpose - take the Appendix A — Auto-Request Creation Branch out of .aib_brain\prompts\aib-analyze.md prompt and create a separate prompt .aib_brain\prompts\aib-create-request.md. Both .aib_brain\prompts\aib-modify.md and .aib_brain\prompts\aib-analyze.md should execute it in case of no active request."

### AI Interpretation

The developer requests a new prompt, `aib-modify.md`, that acts as a lightweight implementation executor: it reads the `## Input` section of `input.md` as a direct implementation directive, follows `instructions.md` persistent directives, considers `context.md` for product awareness, and executes changes immediately without requiring a prior analysis or planning phase. Unlike `aib-implement.md`, it does not close or finalize the active request after execution, leaving the request lifecycle open for further actions. If no active request exists when `aib-modify.md` is invoked, it must auto-create one before proceeding.

To enable reuse of request auto-creation logic across multiple prompts, the developer requests that the Appendix A (Auto-Request Creation Branch) be extracted from `aib-analyze.md` into a standalone prompt `aib-create-request.md`. Both `aib-analyze.md` and the new `aib-modify.md` should delegate to `aib-create-request.md` when no active request is found, replacing the inline Appendix A in `aib-analyze.md` with an execution reference to the new standalone prompt.

## Research Results

### Workspace Pattern Scan

**Existing prompts:**

- `aib-analyze.md` (28.7 KB): Full analysis workflow (11 steps). Contains Appendix A (Auto-Request Creation Branch) at lines 334–351. The Appendix A logic is: (A.1) check `## Input` non-empty; (A.2) derive title ≤ 60 chars; (A.3) call `create-request.py --workspace . --title "<derived-title>"`; (A.4) call `input-header.py --workspace . --operation read` to resolve the new `request_id`. After A.4, execution resumes at Step 2 of the main flow.
- `aib-implement.md` (4.2 KB): Implementation executor. Reads `plan.md` (or `input.md ## Input` in `--exec-input` mode). Includes test execution (Steps 6–8) and request closure (Step 9). Contains explicit prohibitions on modifying `.aib_brain/` assets. Uses `instructions.md` and `context.md`.
- `aib-refresh-context.md`: Context population prompt; called inline from `aib-analyze.md` Step S02.2 using the pattern `execute .aib_brain/prompts/aib-refresh-context.md`.

**How prompts delegate to other prompts:**

The existing delegation pattern, established in `aib-analyze.md` S02.2, is: "execute `.aib_brain/prompts/<name>.md`". This is the authoritative model for one prompt calling another.

**Tools available and their constraints:**

- `log-entry.py`: Normal mode requires an active request (exits code 1 otherwise); `--general` flag bypasses this check. In `aib-analyze.md` S01, the error from `log-entry.py` on a pre-creation call is explicitly suppressed ("suppress the error and proceed"). This pattern applies to `aib-create-request.md` as well.
- `input-header.py`: Reads or writes the YAML frontmatter of `input.md`. After `create-request.py` runs, `input-header.py` can resolve the newly created `request_id` from the YAML header.
- `create-request.py`: Creates request folder and sets YAML header `state: analysis_ready`.
- `finalize-input.py`: Archives `input.md` and resets it to seed template. Called during archival phase of analysis, not request closure.
- `close-request.py`: Marks request as Closed; called only during full request finalization.

**Industry Knowledge:**

1. **Separation of concerns (SOLID — Single Responsibility Principle):** Extracting Appendix A into a standalone prompt follows SRP — the request-creation concern is orthogonal to both analysis and direct execution. This mirrors how modern CI/CD systems (GitHub Actions reusable workflows, GitLab CI templates) extract reusable job definitions into shared includes rather than inlining them in every consuming workflow.

2. **Command pattern (Gang of Four):** A "direct execute" prompt that bypasses planning is equivalent to the Command pattern: encapsulating an instruction with its execution context for immediate dispatch. Tools such as GitHub CLI `gh workflow run` (instant workflow trigger) and Terraform `apply -auto-approve` (skip plan step) embody the same trade-off between safety-gate overhead and execution speed.

3. **DRY (Don't Repeat Yourself):** Extracting Appendix A into `aib-create-request.md` eliminates future duplication: any prompt needing auto-request creation (currently two: `aib-analyze.md` and `aib-modify.md`) delegates to a single source of truth, reducing the maintenance surface for future logic changes.

**AI Agent Critique:**

- `aib-analyze.md` currently contains Appendix A inline, creating a maintenance risk: any change to the auto-creation logic must be applied in one place only after extraction, but in multiple places today. This is the primary technical debt this request addresses.
- `aib-implement.md` already has a `--exec-input` mode that partially overlaps with `aib-modify.md`'s intent (direct execution from `input.md ## Input` without a plan). The key distinction is that `aib-modify.md` does not finalize the request. If `aib-modify.md` diverges too far from `aib-implement.md`'s structure, the two prompts may drift and become inconsistent over time.
- The `instructions.md` directive "MUST create a commit after each execution of the implementation phase of each request" does not scope itself to `aib-implement.md` by name; it applies to any implementation phase. `aib-modify.md` is an implementation phase, so the commit directive applies.
- `aib-implement.md` prohibits modifying `.aib_brain/` assets. If `aib-modify.md` inherits this rule, it cannot be used to modify prompts or conventions (including the very request that creates it). This restriction must be resolved as a decision point.
- `context.md` File Structure currently lists only three prompts; both new prompts must be added there.
- The `README.md` in `.aib_brain/` documents the prompt ecosystem; it must be updated per the `instructions.md` README maintenance directive.
- `aib-analyze.md` S01.1a runs `verify-input.py` and `verify-context.py` before state resolution. If `aib-modify.md` skips these verifications, it loses the safety gate that catches malformed input before execution.

**Edge Cases:**

- `aib-modify.md` invoked when `state == questions_generated`: `input.md` contains Q-blocks in `## Questions` but the `## Input` section may have been archived and reset. The prompt must decide whether to halt (because Q-blocks indicate a pending analysis cycle) or proceed (because `## Input` is the only directive).
- `aib-modify.md` invoked when `## Input` is empty or stub-equivalent: must halt with a clear error message, consistent with `aib-implement.md --exec-input` behavior.
- `aib-create-request.md` invoked when state is already `analysis_ready` or `questions_generated` (an active request already exists): the prompt must decide whether to create a second request (violating the single-active-request invariant), halt with an error, or silently succeed without creating a duplicate.
- `aib-modify.md` with a very large `## Input` that spans multiple implementation concerns: the prompt has no Q-block mechanism to clarify ambiguous instructions, unlike `aib-analyze.md`. If the input is ambiguous, execution may produce unintended results.
- `aib-create-request.md` called before `log-entry.py` has an active request: the standard `log-entry.py` call exits with code 1. This is already handled in `aib-analyze.md` by suppressing the error; `aib-create-request.md` must either suppress pre-creation log calls or use `--general` flag.

## Proposed Solution

### High-Level Concept

Extract the Auto-Request Creation Branch from `aib-analyze.md` Appendix A into a standalone prompt `aib-create-request.md`, then create `aib-modify.md` as a lightweight direct-execution prompt that reads `input.md ## Input` and implements it immediately using `context.md` and `instructions.md` as guides, without closing the request at the end, and update `aib-analyze.md` to delegate to `aib-create-request.md`.

### Execution Steps

#### Task 1: Create aib-create-request.md

- `.aib_brain/prompts/aib-create-request.md`: Create new prompt file containing the standalone Auto-Request Creation logic extracted from Appendix A of `aib-analyze.md`; include: preflight log using `--general` flag (suppress error if no request); check that `input.md ## Input` is non-empty (halt with same error message as Appendix A.1 if empty); derive request title (first meaningful sentence or noun phrase, ≤ 60 characters); invoke `create-request.py --workspace . --title "<derived-title>"`; invoke `input-header.py --workspace . --operation read` to resolve and confirm the newly created `request_id`; log completion using `--general` flag; output the resolved `request_id` to the conversation.
  > Note: For state guard, the prompt must halt with error when `state != idle` on entry (a request already exists); error message: `ERROR: Active request <request_id> already exists. aib-create-request.md must only be called when state is idle.`

#### Task 2: Create aib-modify.md

- `.aib_brain/prompts/aib-modify.md`: Create new prompt file following the structure of `aib-implement.md` with the following specification: (1) read `instructions.md` as persistent directives; (2) skip all input/context verification (no `verify-input.py` or `verify-context.py`); (3) check state via `input-header.py`; if `state == idle`, execute `aib-create-request.md` then re-read state; if `state == questions_generated`, halt with error requiring the developer to answer Q-blocks or reset state before running; (4) read `input.md ## Input` as the implementation directive (halt if empty); (5) read `context.md` for product awareness only — never update `context.md` (user must run a separate analysis/context-refresh cycle); (6) read `coding-general-convention.md` unconditionally and language-specific convention files conditionally before editing any source-code file; (7) implement changes directly from the input directive applying `instructions.md` directives — MUST NOT modify `.aib_brain/` assets (inherit restriction from `aib-implement.md`); (8) skip test execution entirely (leave validation to the developer); (9) no modifier flags; (10) after successful implementation, archive `input.md` and reset to seed template via `finalize-input.py`, leave the YAML state unchanged; (11) follow `instructions.md` commit directive (create a git commit after successful implementation); (12) confirm completion with `--- I am done with the modification of <request_id> ---`.

#### Task 3: Update aib-analyze.md

- `.aib_brain/prompts/aib-analyze.md`: Replace the entire inline Appendix A — Auto-Request Creation Branch content with a delegation instruction: `Execute .aib_brain/prompts/aib-create-request.md. After execution completes, resume at Step 2 (S02).` The section heading `## Appendix A — Auto-Request Creation Branch` and trigger description must be retained; only the procedural steps (A.1–A.4) are replaced.

#### Task 4: Update context.md

- `.aib_memory/context.md`: Add new Solution statements describing `aib-modify.md` and `aib-create-request.md` behaviors; update the File Structure `prompts/` line to include the two new prompt files.

#### Task 5: Update README.md

- `.aib_brain/README.md`: Add documentation for `aib-modify.md` and `aib-create-request.md` in the prompts section; describe the extraction of Appendix A and the new direct-execution workflow.

#### Decision Point: aib-modify-test-execution

- Tag: resolved-by-user

#### Decision Point: aib-modify-context-update

- Tag: resolved-by-user

#### Decision Point: aib-modify-state-transition

- Tag: resolved-by-user
- Resolution: Option A — Leave the `input.md` YAML state unchanged after `aib-modify.md` completes; the developer manages state transitions manually.

- Tag: resolved-by-user

- Tag: resolved-by-user

#### Decision Point: aib-create-request-non-idle-state

- Tag: resolved-by-user
- Resolution: Option A — Halt with an explicit error message identifying the existing `request_id` when `aib-create-request.md` is invoked with `state != idle`. Error message: `ERROR: Active request <request_id> already exists. aib-create-request.md must only be called when state is idle.`

#### Decision Point: aib-modify-modifier-flag

- Tag: resolved-by-user
- Resolution: Option A — No modifier flags; `aib-modify.md` is a single-mode prompt for simplicity. No `--no-tests`, `--dry-run`, or `--plan-only` flags are supported.

#### Decision Point: aib-modify-coding-conventions

- Tag: resolved-by-user
- Resolution: Option A — Inherit full coding-convention enforcement from `aib-implement.md`: read `coding-general-convention.md` unconditionally and language-specific convention files conditionally (using the same extension-to-convention mapping table as `aib-implement.md`) before generating or editing any source-code file.
