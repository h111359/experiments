# Analysis: R-20260701-0528

## Overview

- **Request ID:** R-20260701-0528
- **Request title:** Context Management Enhancements

### Background

The current AIB framework treats `context.md` as a snapshot of the present product state, with no mechanism to record future intentions, open issues, or entries added outside the standard analysis→implementation cycle. Developers have no way to mark features as planned-but-not-yet-implemented, cannot sync `context.md` from external specification documents, and cannot extend it with referenced sub-files to manage token budgets. The `aib-refresh-context.md` prompt exists but lacks the ability to reverse-engineer a workspace and fill in missing critical information reliably. The `aib-implement.md` prompt relies on the plan to drive `edit-context.py` calls, but there is no explicit guarantee that all intended context components (concepts, requirements, technical solutions, references) are updated. This request addresses all of these gaps through a coordinated set of convention updates, new tools, and new prompts.

### Scope

- Updating `context-convention.md` to permit `[PLANNED]` tagged future-intent entries and a new section for identified issues and contradictions.
- Updating `edit-context.py` and `verify-context.py` to support the new tags and section.
- Enhancing `aib-refresh-context.md` to reverse-engineer the workspace and populate missing critical information without duplicating information already derivable from code or scripts.
- Strengthening `aib-implement.md` to guarantee that all context components (new concepts, requirements, technical solutions, and references) are added or edited during implementation.
- Defining a lifecycle rule for `[PLANNED]` entries and Issues entries (removal on realization or resolution).
- Inventing a mechanism to add concepts, requirements, and solutions to `context.md` outside the analysis→implementation cycle and marking them as not yet implemented.
- Creating a new interactive prompt `aib-sync-spec.md` that aligns `context.md` with an external specification file of arbitrary format, detects contradictions, and asks the user for resolution decisions.
- Creating a new prompt that reads `context.md`, collects all `[PLANNED]` entries and Issues, and generates text into the `## Input` section of `input.md` targeting their implementation.
- Making `context.md` extendable with referenced sub-files; prompts evaluate extension summaries before deciding whether to read them. Extensions carry a read-only vs. writable flag.
- Providing a mechanism to register extensions in `context.md`.
- Updating `README.md` and `user_guide.html` to document all new context management mechanisms.

### Out of scope

- Automatic implementation of features tagged as future intents. They must remain as planning markers only until explicitly requested.
- Real-time interactive CLI contradiction resolution outside of the dedicated `aib-sync-spec.md` flow.
- Modifying the core LLM execution engine to support dynamic tool use if a pre-evaluation prompt approach suffices for reading extensions.

### AI Interpretation

This request extends AIB's product-memory management along five orthogonal dimensions:

**Dimension 1 — Future-intent entries in `context.md`:** The convention currently mandates current-state-only content. The developer requires a `[PLANNED]` tag (resolved by Q001) that marks statements representing intended but not-yet-implemented features. A companion `## Issues` section (or equivalent mechanism) should capture identified contradictions and quality concerns. Lifecycle rules govern tag removal when the underlying feature is realized or the issue is resolved. The `context-convention.md`, `edit-context.py`, and `verify-context.py` all require coordinated updates.

**Dimension 2 — External spec synchronization (`aib-sync-spec.md`):** A new standalone interactive prompt reads an external specification file of arbitrary format (e.g., a Word export, a Markdown design document, a CSV of requirements), extracts statements, maps them to context sections, detects contradictions with existing context content, and halts to raise Q-blocks for user resolution of each contradiction. Non-contradictory new items are added to `context.md` as `[PLANNED]` entries. The prompt must operate within AIB conventions for Q-block generation and context editing.

**Dimension 3 — Context extensions for token saving:** `context.md` can reference sub-files (extensions) that hold detail-level content too large to inline. Each extension registration in `context.md` includes a summary and a read-only vs. writable flag. Prompts evaluate the summary before deciding to read the full extension file. Writable extensions are updated alongside `context.md` when aib-refresh-context.md runs; read-only extensions are left unchanged.

**Dimension 4 — Planned-entry input generator:** A new prompt (`[TBD name]`) reads `context.md`, collects all `[PLANNED]` statements and Issues entries, and generates a structured intent text that it appends to `input.md ## Input`. This enables the developer to trigger implementation of accumulated planned features without manually authoring the input.

**Dimension 5 — Strengthened implement-time context updates:** The `aib-implement.md` prompt must guarantee that all context components (new concepts, requirements, technical solutions, and references) introduced or modified by an implementation run are reflected in `context.md`. This requires the plan-convention.md mandatory context update task to be auditable and the implement prompt to verify it was executed.

## Research Results

### Workspace Pattern Scan

**`context-convention.md`:** Defines 6 valid H2 sections. Pruning rules explicitly prohibit historical or future-tense content. No `[PLANNED]` or `[ISSUES]` concept exists. The `## References` section already uses a `###` sub-heading + `Location:` + `Summary:` format, which could be extended for extension registration without requiring a new H2 section. Alternatively, a 7th section could be introduced. The verify-context.py quality gate check 7 would reject `[PLANNED]` prefixes on Product/Concepts/Solution bullets as format violations — it must be updated.

**`verify-context.py`:** Implements exactly the 10 checks mandated by context-convention.md. Check 7 enforces plain-bullet format for Product, Concepts, Solution. Check 8 enforces modality-prefixed format for Requirements. Both checks would flag `[PLANNED]` entries as violations without a convention update.

**`edit-context.py`:** Supports CRUD on four sections (Product, Concepts, Requirements, Solution). File Structure and References are out of scope for edit-context.py operations. An Issues section (if added as H2) would require a new area in VALID_AREAS. [PLANNED] tagged inserts would require the insert logic to not strip the tag as invalid text.

**`aib-refresh-context.md`:** Phase 5 references "type D statements" and "area subsection of `## 2. Statements`" — these are artefacts of a legacy format and are incorrect relative to the current 6-section context.md structure. This is a pre-existing bug. The prompt also does not handle `[PLANNED]` preservation logic, which must be added. No extension file update logic exists.

**`aib-implement.md`:** Step 4 reads context.md (always). Step 5 follows the plan. The plan-convention.md mandates a context update task including exact edit-context.py invocations. However, aib-implement.md does not verify that the context update task was executed successfully or that context.md was actually modified. There is also no explicit mention of updating References, Concepts, or other sections beyond what the plan specifies.

**`aib-sync-spec.md`:** Does not exist. Needs to be created from scratch.

**New prompt for planned entries:** Does not exist. Needs to be created. No name has been defined in the workspace.

**`input-convention.md`:** Defines the `## Input` section as the developer's intent channel. An aib-populate-input-style prompt would write to this section, which is the standard channel.

**`plan-convention.md`:** Already mandates a context update task in every plan with exact edit-context.py invocations. The `## Constraints` section captures autonomous choices in `--plan-only` mode.

**`.aib_brain/README.md`:** Exists and describes prompt invocation commands and daily workflow. Would need updates for the new prompts and mechanisms.

**`user_guide.html`:** Mentioned in context.md as self-contained HTML. Would need updates for all new context management workflows.

### Industry Knowledge

**Finding 1 — Living Requirements Documents (IEEE 29148, BABOK):** Established requirements engineering practices differentiate between realized and planned items using status markers (e.g., `[DRAFT]`, `[APPROVED]`, `[IMPLEMENTED]`). IEEE 29148 emphasizes traceability between requirements and their implementation status. Applicability: aligns with the `[PLANNED]` tag approach; lifecycle rules for tag removal are consistent with standard RE lifecycle management. The `## Issues` section maps to the BABOK concept of an issues log maintained throughout a project lifecycle.

**Finding 2 — Lazy loading / deferred loading for knowledge graphs (Open Source: Retrieval-Augmented Generation patterns):** In RAG architectures, a summary index (e.g., a vector store) is consulted before fetching full documents. The LLM evaluates the summary to decide relevance before loading the full chunk. Applicability: the extension summary mechanism in context.md directly mirrors this pattern — the summary acts as the retrieval index, and the prompt's decision to read the full extension file mirrors the retrieval decision. Read-only vs. writable flags map to static vs. dynamic document stores.

**Finding 3 — Convention-driven specification synchronization (TOGAF, Zachman Framework):** Enterprise architecture frameworks maintain an authoritative architecture description document and synchronize it with external inputs (business capability models, system specifications) through a structured reconciliation process. Contradictions are escalated to decision-makers rather than auto-resolved. Applicability: `aib-sync-spec.md` follows this pattern exactly — it is the reconciliation process, and user Q-blocks are the escalation mechanism. The "arbitrary format" spec file maps to TOGAF's concept of external views that may be expressed in different notations.

### AI Agent Critique

- **`aib-refresh-context.md` Phase 5, Pass 1:** References "type D statements" and "area subsection of `## 2. Statements`" — legacy format artefacts that do not match the current 6-section context structure. This is a pre-existing bug unrelated to the current scope but must be corrected as part of any aib-refresh-context.md update.
- **`aib-refresh-context.md` Phase 4, Section 4.1 Preamble:** References "the Preamble Format section" of context-convention.md, but context-convention.md does not contain a "Preamble Format" section. This is a stale cross-reference.
- **`aib-refresh-context.md` Safety section:** "MAY read analysis-<request_id>.md and plan-<request_id>.md for the active request only (needed for enrichment passes in Phase 4b)" — but there is no "Phase 4b" in the prompt; Phase 5 is the enrichment verification phase. This reference is stale.
- **`context-convention.md` Pruning Rules:** "Aggressively remove historical context, old iterations, resolved questions, and deprecated features. `context.md` reflects CURRENT product state only." This rule conflicts directly with the goal of adding `[PLANNED]` future-intent entries. The convention must be updated before the tag can be used.
- **`verify-context.py` Check 7:** Rejects any bullet prefix in Product/Concepts/Solution sections. Adding `[PLANNED]` tagged items requires either updating check 7 or exempting tagged lines from the check. Without this change, any `[PLANNED]` item would cause verify-context.py to exit code 1 and block all subsequent analysis/implement runs.
- **`edit-context.py` VALID_AREAS:** The Issues section (if implemented as H2) is not in VALID_AREAS. Without adding it, the Issues section cannot be managed via `edit-context.py`.
- **`plan-convention.md` context update task mandate:** The mandate exists but there is no enforcement in `aib-implement.md`. An implementation run that accidentally omits the context update task would proceed without any warning.
- **`aib-implement.md` Step 4:** "MUST NOT read `.aib_memory/context.md` during implementation. All context required for execution is contained within the plan." This rule is well-established but creates a design tension: if the plan's context update task specifies edit-context.py invocations based on the plan author's snapshot of context.md, and context.md has changed between plan generation and implementation (e.g., due to a `--plan-only` run or a manual edit), the edit-context.py calls may fail silently or produce incorrect results. This is an existing risk, not introduced by this request, but should be noted.
- **`aib-analyze.md` S09.2 documentation requirement:** States "read `.aib_memory/context.md` to identify the exact text of statements that need to change, then embed those exact texts into the plan task procedure steps." This is good practice but creates a race condition if context.md is modified between S09 execution and aib-implement.md execution.
- **`aib-create-request.md`:** Not referenced anywhere in `README.md` or user guide. End users may not know this is invoked implicitly. Low severity, but should be documented.

### Edge Cases

- **Re-run with `[PLANNED]` entries present:** When `aib-refresh-context.md` re-runs and encounters existing `[PLANNED]` entries, it must not silently drop them (since they are intentional future-intent markers, not stale content). A preservation-vs-revalidation policy is needed.
- **`aib-sync-spec.md` with all-new spec (no overlap):** When the external spec contains only new information with no overlap with existing context, the prompt must handle this gracefully without raising false contradiction Q-blocks.
- **Extension file deleted from workspace:** If a registered extension file is removed from the workspace and a prompt tries to read it, the read will fail. The extension registration in `context.md` becomes a dangling reference. Graceful handling (warn, skip) is needed.
- **`[PLANNED]` entry referencing a closed request:** If a `[PLANNED]` entry was added as part of request R-001 and R-001 is later closed without implementing the feature, the entry remains. No automatic cleanup exists. The lifecycle rule must cover orphaned planned entries.
- **Writable extension file format:** If a writable extension is in a non-Markdown format (e.g., JSON, YAML), the AI agent may not be able to update it in a structured way. The format constraints for writable extensions must be defined.
- **Multiple `[PLANNED]` entries for the same feature:** Without uniqueness enforcement (the current uniqueness invariant applies to full statement text), a feature tagged `[PLANNED]` could be re-added if text differs slightly. The uniqueness check covers exact text matches but not semantic duplicates.
- **`aib-sync-spec.md` spec file too large to read in one context:** Large external specs may exceed the LLM context window. A chunking or prioritization strategy is needed.
- **New prompt for planned entries when input.md already has content:** If the developer has already written instructions in `## Input` and then runs the planned-entry prompt, appending to `## Input` may produce contradictory or confusing instructions. A check for non-empty `## Input` is needed.
- **Removing `[PLANNED]` tag via `edit-context.py`:** The current delete operation matches on full statement text. To remove a `[PLANNED]` prefix, the operation would be delete-then-insert (since there is no in-place replace operation). This creates a two-step sequence that could partially fail.

- **Solution**: "aib-analyze.md invokes verify-input.py and verify-context.py..." — No change needed here, but verify-context.py behaviour changes must be reflected.

### Conflict Resolution & Intent Preservation

- The existing Pruning Rules mandate "current state only" content in `context.md`. The `[PLANNED]` tag extension exempts future-intent entries from this rule without removing the rule itself — the original intent (prevent accumulation of stale historical content) is preserved. The update adds a precise carve-out: `[PLANNED]` entries are not stale history; they are forward-looking markers with an explicit removal lifecycle.
- The `## References` section format (###, Location:, Summary:) is being extended with a new `Flag:` line for extensions. This preserves backward compatibility — existing Reference entries without a `Flag:` line remain valid; only extension entries require the Flag field.

## Decision Register

### Decision Points

#### Decision Point: PLANNED-tag-syntax
- **Tag:** resolve-autonomously
- **Rationale:** The `input.md ## Input` Details section consistently uses `[PLANNED]` (e.g., "Update `context-convention.md` to permit future items, requiring them to use a specific tag like `[PLANNED]` or `[INTENT]`"). The detail section also repeatedly uses `[PLANNED]` as the working example. Resolution: use `[PLANNED]` as the canonical tag name.
- **Chosen alternative:** `[PLANNED]` prefix on statement text (e.g., `- [PLANNED] feature description`).

#### Decision Point: PLANNED-tag-placement
- **Tag:** ask
- **Alternatives:**
  - **Option A — Inline in existing sections:** `[PLANNED]` tagged statements live in the same sections as current-state statements (Product, Concepts, Solution). The section mixes current and planned content. Simple to implement; no new H2 needed. Risk: context becomes harder to read; planned items may be confused with realized items.
  - **Option B — Dedicated `## Planned` H2 section:** Add a 7th valid H2 section `## Planned` containing only `[PLANNED]` statements grouped by type (product/concept/solution). Clean separation; easy to scan all planned items. Requires context-convention.md to expand valid sections to 7 and update verify-context.py.
  - **Option C — Inline in existing sections with sorted placement:** `[PLANNED]` items appear at the end of each applicable section (after all current-state items). Provides visual grouping without a new section; easier to parse in one pass.

#### Decision Point: PLANNED-tag-in-requirements
- **Tag:** ask
- **Alternatives:**
  - **Option A — Allow `[PLANNED]` in Requirements:** A planned requirement would appear as `- [PLANNED] MUST: <text>` or `- MUST: [PLANNED] <text>`. Requires format decision on where the tag appears relative to the modality prefix.
  - **Option B — Prohibit `[PLANNED]` in Requirements:** Requirements section remains modality-prefixed only. Planned requirements are stored as Concepts or Solution planned entries instead.
  - **Option C — Separate tag syntax for Requirements:** Use a different marker for planned requirements, e.g., `- OPTIONAL: [PLANNED] <text>` to reuse OPTIONAL modality for future items.

#### Decision Point: issues-section-structure
- **Tag:** ask
- **Alternatives:**
  - **Option A — New 7th H2 section `## Issues`:** Added to the valid sections list in context-convention.md. Clean separation; discoverable. Requires verify-context.py and context-convention.md update.
  - **Option B — Sub-section within `## Solution`:** Issues are tracked as a `### Issues` sub-heading inside `## Solution`. No new H2 needed; stays within the 6-section structure. Risk: mixing architectural solutions with unresolved issues in the same section reduces clarity.
  - **Option C — Sub-section within `## Concepts`:** Issues are tracked as a `### Issues` sub-heading inside `## Concepts`. Issues are domain concerns, not solutions. Risk: same readability concern as Option B.

#### Decision Point: issues-section-format
- **Tag:** ask
- **Alternatives:**
  - **Option A — Plain bullet list:** Each issue is a single bullet `- <description>`. Simple; consistent with other sections. No structured status field. Lifecycle (removal on resolution) is manual.
  - **Option B — Structured sub-heading entries:** Each issue uses a `####` sub-heading with `Description:`, `Status:` (open/resolved), and `Detected:` (request ID or date) fields. Rich metadata; supports lifecycle tracking. More verbose; requires dedicated verify-context check.
  - **Option C — Plain bullet with inline status tag:** Each issue is `- [OPEN] <description>` or `- [RESOLVED] <description>`. Middle ground between A and B; supports lifecycle without sub-headings.

#### Decision Point: verify-context-PLANNED-handling
- **Tag:** ask
- **Alternatives:**
  - **Option A — Allow `[PLANNED]` prefix in all content sections:** Check 7 is updated to permit lines matching `- [PLANNED] <text>` in Product, Concepts, and Solution. Requirements keeps its own modality check.
  - **Option B — Allow `[PLANNED]` only in specific sections:** Only Concepts and Solution sections permit `[PLANNED]` prefix; Product section remains current-state only.
  - **Option C — Separate dedicated check for `[PLANNED]` lines:** Check 7 remains unchanged for plain lines; a new check 11 validates `[PLANNED]` lines specifically (correct prefix format, non-empty text).

#### Decision Point: PLANNED-lifecycle-enforcement
- **Tag:** ask
- **Alternatives:**
  - **Option A — No automated enforcement:** Lifecycle rule is documented but verify-context.py makes no check on the age or status of `[PLANNED]` entries. Manual cleanup only.
  - **Option B — Warning on stale `[PLANNED]` entries:** verify-context.py adds a warning (non-blocking) when a `[PLANNED]` entry has existed since a request ID that is now more than N requests old. Implementation requires request age tracking which is complex.
  - **Option C — enforce at implement time only:** `aib-implement.md` and `aib-refresh-context.md` are responsible for removing `[PLANNED]` tags on feature realization; verify-context.py remains unchanged for lifecycle. Only format correctness is checked.

#### Decision Point: extensions-registration-mechanism
- **Tag:** ask
- **Alternatives:**
  - **Option A — Enhance `## References` section:** Extend the existing Reference entry format with an optional `Flag:` line (values: `read-only` or `writable`). Backward-compatible — existing Reference entries without `Flag:` remain valid. Extensions are indistinguishable from plain references structurally but carry the Flag field.
  - **Option B — New `## Extensions` H2 section:** Add a dedicated `## Extensions` section with its own format (Location, Summary, Flag required). Clean separation from bibliographic references. Requires context-convention.md to expand valid sections.
  - **Option C — YAML-block embedded in context.md:** Extensions are registered as a fenced code block with YAML inside `## References` or a new section. Machine-readable; easily parsed by Python tools. Risk: violates context-convention.md formatting rules (no code blocks currently allowed in context.md).

#### Decision Point: extension-flag-format
- **Tag:** ask
- **Alternatives:**
  - **Option A — `Flag: read-only` / `Flag: writable`:** Clear English values. Easy to read.
  - **Option B — `Mode: static` / `Mode: dynamic`:** More generic terminology; aligns with RAG/caching vocabulary.
  - **Option C — `Update: false` / `Update: true`:** Boolean-style flag; minimal. May be less self-documenting.

#### Decision Point: extension-auto-update-trigger
- **Tag:** ask
- **Alternatives:**
  - **Option A — During `aib-refresh-context.md` execution:** Writable extensions are updated as part of the refresh run. Single-command trigger; consistent with existing refresh behaviour.
  - **Option B — Separate `aib-update-extensions.md` prompt:** Extensions are updated by an independent prompt invoked explicitly by the developer. More controlled; allows targeted extension updates without a full context refresh.
  - **Option C — During `aib-implement.md` completion:** Writable extensions are updated after each implementation run when new information is available. Tightly coupled to implementation; may update extensions with incomplete information if implementation is partial.

#### Decision Point: extension-relevance-mechanism
- **Tag:** ask
- **Alternatives:**
  - **Option A — Keyword matching against request topic:** The prompt extracts keywords from the active request title/input and checks if they appear in the extension Summary. Simple; deterministic; may produce false negatives.
  - **Option B — Semantic relevance judgement by AI:** The AI agent reads all extension Summaries and makes a relevance judgement for the active request. More accurate; relies on AI reasoning; non-deterministic.
  - **Option C — Explicit tags on extension entries:** Each extension entry carries a `Topics:` field listing topics it is relevant to. The prompt matches the request topic against the Topics list. Deterministic and explicit; requires developer to maintain topics lists.

#### Decision Point: extension-read-who
- **Tag:** ask
- **Alternatives:**
  - **Option A — `aib-analyze.md` only:** Extensions are checked and read during analysis (S03). The implementation prompt never reads extensions (it reads only the plan). This is consistent with `aib-implement.md`'s read-plan-only rule.
  - **Option B — `aib-analyze.md` and `aib-refresh-context.md`:** Both prompts check extension relevance. Refresh uses extension content to populate context.md; analyze uses it for research.
  - **Option C — All AIB prompts:** Every prompt that reads context.md also checks for relevant extensions. Maximizes utility; increases complexity and execution time for every prompt.

#### Decision Point: refresh-non-repeating-policy
- **Tag:** ask
- **Alternatives:**
  - **Option A — Exclude tool script signatures and CLI interfaces:** Specifically exclude function signatures, argument names, and CLI output formats from context.md since these are derivable by reading the scripts. State the high-level purpose only.
  - **Option B — Exclude all content derivable from code reads:** Any fact that can be verified by reading a source file is excluded from context.md. Context.md contains only architectural intent and product-level facts. Risk: context.md becomes very thin and may miss important facts only discoverable through code analysis.
  - **Option C — No exclusion policy — current behaviour retained:** context.md may include derivable facts. The redundancy is acceptable because context.md is the single source of truth used by prompts without requiring code reads. Current behaviour.

#### Decision Point: refresh-PLANNED-handling
- **Tag:** ask
- **Alternatives:**
  - **Option A — Preserve all `[PLANNED]` entries unchanged:** During a full refresh run, existing `[PLANNED]` entries are copied verbatim to the new context.md without re-evaluation. Safe; prevents accidental removal of planned features.
  - **Option B — Re-evaluate `[PLANNED]` entries against current workspace:** For each `[PLANNED]` entry, check whether the described feature now exists in the workspace. If it does, remove the `[PLANNED]` tag (feature is realized). Risk: AI re-evaluation may make incorrect judgements.
  - **Option C — Preserve entries but flag potentially realized ones:** During refresh, if a `[PLANNED]` entry appears to be realized (based on workspace evidence), add a note in the refresh output and preserve the entry; removal requires explicit developer action.

#### Decision Point: refresh-extension-update
- **Tag:** ask
- **Alternatives:**
  - **Option A — Always update writable extensions during refresh:** Every writable extension registered in context.md is updated as part of the refresh run. Simple; keeps extensions current.
  - **Option B — Update extensions only if referenced section changed:** A writable extension is updated only when the context section it relates to has changed in the current refresh run. More efficient; requires change-detection logic.
  - **Option C — Never update extensions during refresh — separate trigger only:** Refresh leaves extensions unchanged; extension updates are triggered only by an explicit separate command. Clear separation of concerns.

#### Decision Point: implement-context-verification
- **Tag:** ask
- **Alternatives:**
  - **Option A — Add explicit check that `edit-context.py` was called:** After executing all plan tasks, `aib-implement.md` checks whether at least one `edit-context.py` invocation was logged in the current session. If none was found, output a warning but do not halt (plan may have legitimately not required context changes).
  - **Option B — Verify `context.md` was modified:** After the context update task, re-read context.md and verify its modification timestamp or content has changed. Halt with error if unchanged and the plan specified context changes.
  - **Option C — No additional verification — current behaviour retained:** The plan-convention.md mandate is sufficient. If the plan specifies context changes and the implement agent does not execute them, that is a plan compliance failure caught by testing.

#### Decision Point: implement-PLANNED-removal
- **Tag:** ask
- **Alternatives:**
  - **Option A — `aib-implement.md` automatically checks and removes `[PLANNED]` tags:** After implementation completes, the agent scans context.md for `[PLANNED]` entries and for each, checks whether the described feature is now present in the workspace. If yes, removes the tag. Risk: automated judgement may incorrectly tag/untag entries.
  - **Option B — Plan task explicitly includes `[PLANNED]` tag removal:** The plan's context update task includes `edit-context.py delete` for the `[PLANNED]` statement followed by `edit-context.py insert` for the plain statement. Removal is deterministic and plan-driven. Requires S09 plan generation to detect `[PLANNED]` entries and include the removal steps.
  - **Option C — Manual removal only:** `[PLANNED]` tag removal is never automated. The developer manually removes tags via `edit-context.py` or by editing context.md. Simple; no risk of incorrect automation.

#### Decision Point: implement-context-update-failure
- **Tag:** ask
- **Alternatives:**
  - **Option A — Halt with error:** If `edit-context.py` exits non-zero during the context update task, halt implementation immediately with an error message. No request auto-close.
  - **Option B — Warn and continue:** If `edit-context.py` exits non-zero, output a warning in the conversation and continue with request close. Developer must manually fix context.md.
  - **Option C — Retry once then halt:** On non-zero exit, attempt one retry; if the second attempt also fails, halt with error.

#### Decision Point: sync-spec-input-mechanism
- **Tag:** ask
- **Alternatives:**
  - **Option A — Spec file path in `input.md ## Input`:** The developer writes the spec file path into `## Input` before running `aib-sync-spec.md`. The prompt reads the path from `## Input` and reads the spec file.
  - **Option B — Spec file placed in `.aib_memory/attachments/`:** The developer copies the spec file into the `attachments/` folder. The prompt finds and reads it from there.
  - **Option C — Spec file path as chat message parameter:** The developer passes the path inline in the chat message, e.g., `Execute aib-sync-spec.md --spec path/to/spec.md`. The prompt parses the chat message for the path.

#### Decision Point: sync-spec-non-contradictory-handling
- **Tag:** ask
- **Alternatives:**
  - **Option A — Auto-add as `[PLANNED]` entries:** All non-contradictory new items from the spec are immediately added to the appropriate context sections as `[PLANNED]` statements without user confirmation.
  - **Option B — Show for user approval before adding:** After extraction, present all non-contradictory items to the user in a summary Q-block. The user confirms which items to add. More controlled but adds user interaction overhead.
  - **Option C — Queue for context.md addition — user triggers separately:** Non-contradictory items are written to a staging area (e.g., a temporary file) and the user reviews and applies them explicitly. Most controlled; adds a step to the workflow.

#### Decision Point: sync-spec-contradiction-resolution
- **Tag:** ask
- **Alternatives:**
  - **Option A — One Q-block per contradiction:** Each detected contradiction generates one Q-block asking the user how to resolve it (keep existing, adopt spec version, merge, or skip). Maximum granularity; may produce many Q-blocks for a large spec.
  - **Option B — Batch all contradictions in one Q-block:** All contradictions are listed in a single Q-block with an overall resolution strategy (e.g., "prefer spec version", "prefer existing context", "manual review"). Less granular; may force a blanket policy on mixed-severity contradictions.
  - **Option C — Categorize contradictions and batch by severity:** Critical contradictions get individual Q-blocks; minor ones are batched. Requires an AI-defined severity classification which may be inconsistent.

#### Decision Point: sync-spec-request-lifecycle
- **Tag:** ask
- **Alternatives:**
  - **Option A — Creates an AIB request:** `aib-sync-spec.md` auto-creates a request (via `create-request.py`) and tracks the sync as a formal request. Provides audit trail; adds lifecycle overhead for what may be a quick operation.
  - **Option B — Operates ad-hoc without a request:** The prompt runs outside the normal request lifecycle. It reads and writes context.md directly without creating a request folder. Simple; no audit trail in the request folder.
  - **Option C — Optional request creation:** The developer can run with `--request` flag to create a formal request, or without to run ad-hoc.

#### Decision Point: sync-spec-parsing-granularity
- **Tag:** ask
- **Alternatives:**
  - **Option A — Sentence-level parsing:** The spec is split into sentences; each is evaluated for context relevance and mapped to a section. High granularity; may over-extract trivial sentences.
  - **Option B — Paragraph-level parsing:** The spec is split into paragraphs; each paragraph maps to one context statement. Balanced granularity; suitable for prose specs.
  - **Option C — Heading-section parsing:** The spec is split by headings; each section under a heading is mapped to one or more context statements. Works well for structured specs (Markdown, Word); may miss detail in unstructured text.

#### Decision Point: sync-spec-PLANNED-items
- **Tag:** ask
- **Alternatives:**
  - **Option A — All new items from spec default to `[PLANNED]`:** Any item in the spec that is not already in context.md is added as a `[PLANNED]` entry, regardless of whether it is a future feature or a current-state fact.
  - **Option B — Only items describing future work are tagged `[PLANNED]`:** The AI categorizes each extracted item as current-state or future-intent. Current-state items are added as plain entries; future-intent items get `[PLANNED]`. Risk: misclassification.
  - **Option C — No `[PLANNED]` tags in sync outputs — all items are current state:** The sync prompt treats all spec content as current-state product description. No `[PLANNED]` tagging. Simpler; may add items that are not yet realized.

#### Decision Point: edit-context-PLANNED-support
