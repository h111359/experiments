Details:

Context Management Enhancements

Goals:
- Update `.aib_memory/context.md` to represent the workspace fully without repeating info gatherable from code/scripts.
- Update/Create `.aib_brain/prompts/aib-refresh-context.md` to reverse engineer the current workspace and populate missing critical info in `context.md` or updates the entries to reflect the current state.
- Ensure `aib-implement.md` adds/edits all components (new concepts, requirements, technical solutions, references) in `context.md` during execution.
- Allow "future implementation" entries in `context.md` (intentions not yet realized) by updating `context-convention.md` to permit and tag them (e.g., `[PLANNED]`).
- Add a new section in `context.md` for identified issues/contradictions to be addressed in future AIB runs.
- Define context lifecycle rules: When a planned functionality is realized (or found that it is realized), the `[PLANNED]` tag must be removed. When an issue is resolved (or not detected any more), it must be removed from the `context.md` issues section.
- Invent a mechanism to add concepts/requirements/solutions to `context.md` outside the standard analysis->implementation cycle, marking them as not implemented.
- Create a distinct interactive prompt/tool (`aib-sync-spec.md`) to update `context.md` from an external specification file of arbitrary format. This tool must detect contradictions and ask the user for a decision on how to proceed.
- Create a new prompt responsible for generating text and appending it (via a tool) to the Input section of `input.md`. This text should target the implementation of all future planned entries and the resolution of logged issues.
- Make `context.md` extendable with referenced files to save tokens. The context must contain a summary of the extension, and the prompt will evaluate this summary to decide if the extension file needs to be read. 
- Extensions should be automatically updatable alongside `context.md` based on a read-only vs. writable flag.
- Invent a mechanism to register new extensions in `context.md`.
- Update `README.md` and the user guide to describe all new context-related mechanisms well.

Out of Scope:
- Automatic implementation of features tagged as future intents (they must remain as planning markers only until explicitly requested).
- Real-time interactive CLI contradiction resolution outside of the dedicated `aib-sync-spec.md` flow.
- Modifying the core LLM execution engine to support dynamic tool use if a pre-evaluation prompt approach suffices for reading extensions.

Success Criteria:
- [ ] `context-convention.md` explicitly allows future items using specific tags.
- [ ] `aib-refresh-context.md` successfully reads workspace files and updates missing information in `context.md` without duplicating code details.
- [ ] Execution of `aib-implement.md` demonstrably updates `context.md` with new architectural or requirement decisions made during a test task.
- [ ] `aib-sync-spec.md` can process a dummy external spec, identify a contradiction with current context, and halt to output a Q-block/prompt for user resolution.
- [ ] A test proves that a prompt evaluates an extension summary in `context.md` and successfully ignores the extension if irrelevant, but reads it if relevant.
- [ ] `README.md` and user guide documentation are fully updated with the new context management workflows.

Questions:

### Resolved Questions

**Q001**: How should we resolve the conflict of adding "future intention" entries to `context.md` when the convention mandates current product state only?
**Resolution**: Update `context-convention.md` to permit future items, requiring them to use a specific tag like `[PLANNED]` or `[INTENT]`.

**Q002**: How should the agent technically access dynamic extensions to save tokens?
**Resolution**: The prompt first evaluates `context.md` summaries and decides if the extension (which is simply another file in the workspace) should be read and considered in addition to the `context.md`.

**Q003**: How should the interactive contradiction resolution for external specs be orchestrated?
**Resolution**: Create a distinct interactive prompt/tool (e.g., `aib-sync-spec.md`) dedicated entirely to aligning external specs and asking user input in real-time.

**Q004**: Should we decompose this massive request?
**Resolution**: No, attempt to implement all of these features in this single request iteration.

**Q005**: What constitutes measurable success for the token-saving dynamic extensions feature?
**Resolution**: The extensions must be proven to be read only if relevant based on the summary evaluation.
