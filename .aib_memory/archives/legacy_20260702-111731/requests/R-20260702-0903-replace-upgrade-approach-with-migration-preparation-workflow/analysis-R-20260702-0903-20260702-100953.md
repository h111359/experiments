# Analysis: R-20260702-0903

## Overview

- **Request ID:** R-20260702-0903
- **Request title:** Replace upgrade approach with migration-preparation workflow

### Background

The current `.aib_memory` upgrade process (`initialize.py --upgrade`) restores `context.md` directly from the archive after re-seeding. This breaks when the archived `context.md` was created under an older structural convention that differs from the current one — in particular, versions prior to the context-convention.md 6-section format (`Product`, `Concepts`, `Requirements`, `Solution`, `File Structure`, `References`). Because the restoration is a direct file copy, an incompatible legacy `context.md` is placed back into active memory, causing downstream failures in verify-context.py, analysis, and all prompts that read context.md. The scope of this request is to replace the direct-restore approach with a migration-preparation workflow: the upgrade archives the full legacy state, creates a fresh compliant memory structure, and generates migration instructions in `input.md` for the developer to execute later via `aib-modify.md`.

### Scope

- `initialize.py` — `_run_upgrade()` function: replace restore-context logic with migration-preparation logic; remove interactive request-migration prompt; change archive folder path to `.aib_memory/archive/legacy_TIMESTAMP/`; copy `instructions.md` unchanged; generate valid empty `context.md`; generate migration-ready `input.md` with instructions for `aib-modify.md`
- `initialize.py` — `_prompt_migrate_requests()` function: remove entirely
- `tests/test_initialize.py` — update tests to match new upgrade behavior
- `.aib_brain/README.md` — add or update upgrade process documentation
- `.aib_brain/user_guide.html` — add or update upgrade section

### Out of scope

- Automatic execution of `aib-modify.md` by the upgrade script
- Deletion of archived legacy files after migration
- Automatic restoration of archived requests
- Changes to `instructions.md` content
- Changes to `menu.py` (the `check_version_compatibility` function continues to invoke `initialize.py --upgrade` without modification)
- Renaming or migrating old `.aib_memory/archives/` folders created by prior upgrade runs

## Input Interpretation

### User Original Inputs

The developer's original request is reproduced in the archived `input.md` file at `.aib_memory/requests/R-20260702-0903-replace-upgrade-approach-with-migration-preparation-workflow/`. The key intent is summarised below.

**Goal:** Replace the current `.aib_memory` upgrade approach with a migration-preparation workflow that reliably supports upgrades from older memory versions whose structure differs from the current release.

**Business Need:** Users encounter upgrade failures when attempting to migrate older `.aib_memory` versions because the old `context.md` structure cannot always be transformed deterministically by a script. A semantically-aware migration process is required.

**Scope bullets:** Update upgrade process, remove incompatible-structure migration logic, archive entire legacy `.aib_memory` into `.aib_memory/archive/legacy_TIMESTAMP/`, preserve archived files unchanged, copy `instructions.md` into new structure, create empty `requests/` folder, discontinue restore-requests question, never restore archived requests, create valid empty `context.md`, generate migration-ready `input.md` with detailed instructions for `aib-modify.md`, update README.md and user_guide.html.

**Constraints:** `context.md` migration cannot rely on deterministic structural mapping; semantic transformation must be delegated to `aib-modify.md`; upgrade must preserve auditability; `instructions.md` must be copied directly; archived content must remain available; new memory must conform to current conventions; existing archive location must be `.aib_memory/archive/legacy_TIMESTAMP/`.

### AI Interpretation

The upgrade workflow implemented in `initialize.py::_run_upgrade()` currently follows a backup-clean-reseed-restore pattern that returns `context.md` directly from the archive. When the archived `context.md` uses an older structural convention — for example, the pre-v1.3 22-area classified-statement model — the restored file fails `verify-context.py` checks and causes all AIB prompts to malfunction. The proposed solution replaces the restore-and-fix pattern with a prepare-and-defer pattern: the upgrade script archives everything, constructs a minimal conforming memory, and injects an `input.md` pre-loaded with migration instructions that the developer executes through `aib-modify.md` at a time of their choosing. This decouples the structural upgrade from the semantic reconstruction, leveraging the AI reasoning capability of `aib-modify.md` for the difficult part while keeping the upgrade script deterministic and Python-only.

The archive path changes from `.aib_memory/archives/<timestamp>/` (plural, no prefix) to `.aib_memory/archive/legacy_<timestamp>/` (singular, `legacy_` prefix). This is a naming-only change with no behavioral impact on the archive content.

The `_prompt_migrate_requests()` function and the associated interactive TTY prompt are removed. The `requests/` directory is never restored; it remains exclusively in the archive. A fresh empty `requests/` folder is created in the new memory structure.

The generated `input.md` must have an idle YAML state header (no active request) and a populated `## Input` section containing detailed migration instructions. The instructions must include the exact relative paths to the archived legacy files, references to the conventions governing each reconstruction target, and explicit direction that missing or incompatible optional files (`input.md`, `aib-setup.yaml`) do not block migration.

### Industry Knowledge

- **Migration-preparation pattern (infrastructure provisioning):** Tools like Terraform and Ansible distinguish between applying an upgrade and staging a migration. The staging approach — serialize state, tear down, re-provision, inject migration data — is well established for handling incompatible schema changes. IEEE 12207 (System lifecycle) recommends separating migration planning from migration execution to allow human review. Applicability: strong — the proposed workflow mirrors this two-phase pattern.
- **Copy-on-write archive semantics (database systems):** PostgreSQL's pg_upgrade and Oracle's RMAN follow the pattern of archiving the full prior state before any structural change and never restoring incompatible structures directly. The primary motivation is auditability and rollback safety. Applicability: strong — the archive-then-build pattern in the proposed workflow satisfies the same auditability goal.
- **Deferred semantic migration (ETL design):** In ETL pipelines, schema incompatibilities are commonly handled by storing raw/legacy data in a staging area and running a separate transformation job that is schema-aware. AWS Glue, Apache NiFi, and dbt all implement this pattern. The AI-assisted semantic reconstruction via `aib-modify.md` is the AIB equivalent of a transformation job. Applicability: strong — the pattern is directly analogous; the "transformation" is delegated to the AI agent rather than a deterministic script.

- `tests/test_initialize.py` `TestUpgrade.test_upgrade_archive_requests_choice` and `test_upgrade_migrate_requests_choice` — both test interactive request-migration behavior that will be removed. These tests must be deleted or repurposed.

- No circular dependency risk: `aib-modify.md` reads `input.md` and `context.md`; the new upgrade sets both correctly before the developer runs `aib-modify.md`.

- `run.bat` / `run.sh` launchers — invoke `menu.py` which calls `check_version_compatibility` which calls `initialize.py --upgrade`. No changes needed in the launchers.

### Edge Cases

- **No legacy `context.md` in archive:** If the legacy `.aib_memory` had no `context.md` (unlikely but possible if initialization was incomplete), the migration instructions should still be generated but should note that the primary migration source is absent.
- **No legacy `instructions.md`:** The copy step should silently skip; the new `instructions.md` is seeded as an empty file per existing `_seed_memory()` behavior.
- **Empty legacy `requests/`:** Archive copy includes an empty `requests/` folder; this is preserved in the archive without issue.
- **Archive folder collision (same second):** If two upgrades run within the same second, the `legacy_TIMESTAMP` folder name collides. A counter suffix (`legacy_TIMESTAMP-1`, `legacy_TIMESTAMP-2`) resolves this, mirroring the existing code's counter pattern.
- **Existing `archives/` directory from prior upgrades:** Old `.aib_memory/archives/<timestamp>/` folders remain untouched; the new code uses `archive/` (singular). No migration of old archive directories is required.
- **`aib-setup.yaml` absent from archive (very old workspaces):** The merge-restore strategy already handles this gracefully by falling back to a fresh seed. No change needed.
- **Non-TTY environment (CI):** The old code defaulted to `migrate=True` in non-TTY mode. After removal of the prompt, this distinction disappears — CI environments will always get the new migration-preparation behavior.
- **`default_questions_number` from `aib-setup.yaml`:** The generated `input.md` should use the value from the preserved `aib-setup.yaml` so the developer's question threshold preference is respected.
- **Legacy `input.md` with active request:** The archived `input.md` may have had an active request (state != idle). The migration instructions in the new `input.md` are placed in `## Input` while the YAML header is reset to `idle`. The migration instructions reference the archived `input.md` as optional context.
- **Migration instructions referencing archived path with forward slashes:** On Windows, the path separator in the generated instructions should use forward slashes for portability with `aib-modify.md` which is model-executed.
