# Analysis — R-20260626-1251

## Overview

**Request ID:** R-20260626-1251

**Request title:** Add context/input verification scripts and YAML flags

### Background

AIB's `verify-context.py` tool already validates `context.md` format compliance and is invoked in `aib-refresh-context.md` Phase 8. However, no equivalent programmatic validator exists for `input.md`, and neither verification tool is wired into the primary analysis workflow (`aib-analyze.md`) or exposed in the interactive menu (`menu.py`). Developers have no automated signal when `input.md` contains format violations before analysis begins. This request closes that gap by extending the verification infrastructure to cover `input.md`, adding YAML header flags to track verification state, integrating both scripts into the analysis prompt and the developer menu.

### Scope

- Assess `verify-context.py` against `context-convention.md` (10 quality gates) and confirm or update as needed.
- Add `context_verification_enabled` and `context_verification_result` YAML flags to `input.md` header.
- Add `input_verification_enabled` and `input_verification_result` YAML flags to `input.md` header.
- Create `.aib_brain/tools/verify-input.py` that validates `input.md` format.
- Update `verify-context.py` to write `context_verification_result` to `input.md` after running checks.
- Update `common.py` (`parse_input_header`, `write_input_header`) to support new YAML fields.
- Update `input-header.py` CLI to support read/write of new YAML fields.
- Update `finalize-input.py` `_SEED_TEMPLATE` to include new YAML fields with defaults.
- Update `initialize.py` `input_seed` to include new YAML fields with defaults.
- Update `aib-analyze.md` to invoke verification scripts at the beginning of the workflow.
- Add `verify_input` and `verify_context` menu commands to `menu.py` `_SCRIPT_ACTIONS`.
- Add tests for `verify-input.py` following the `test_verify_context.py` pattern.
- Update `context.md` with statements capturing the convention-to-script relationships.

### Out of scope

- Creation of a formal `input-convention.md` document under `.aib_brain/conventions/`.
- CI automation of verification (verification remains a local developer tool).
- Verification of plan.md, analysis documents, or other AIB artifacts beyond context.md and input.md.
- Changes to `context-convention.md` or any other existing convention file content.
- Network-dependent features or external service integrations.

**Industry knowledge:**

1. **Fail-fast validation at pipeline entry** (CI/CD best practices, Continuous Integration literature, Martin Fowler): Validating input format before processing begins prevents malformed data from propagating into downstream pipeline stages. Applied here: running `verify-input.py` and `verify-context.py` at the start of `aib-analyze.md` prevents malformed files from silently producing incorrect analysis artifacts. Highly applicable.

2. **Separation of verification and result persistence** (Command Query Separation / CQRS, Greg Young): Query operations (read and validate) should be separated from command operations (state write). Applied here: whether the verify scripts themselves write the result flag or delegate to a caller is a significant design choice that affects testability and reuse of the scripts. Informs Decision Point `verify-context-result-writing`.

3. **Convention-script coupling documentation** (Architecture Decision Records, Michael Nygard): When a script enforces a convention, the coupling must be documented in a shared authoritative source so that convention changes trigger script reviews. Applied here: adding MUST requirements in `context.md` that verify scripts be updated when their governing convention changes implements this pattern. Directly applicable.

**AI Agent critique:**

- `aib-refresh-context.md` Phase 1 step 4 performs a manual format detection heuristic while Phase 8 invokes `verify-context.py` for full validation. These two checks are redundant and inconsistent in depth; Phase 1 only checks for a section heading, while Phase 8 runs all 10 checks.

- `common.py` `parse_input_header` parses YAML with hand-rolled regex and silently ignores unknown keys. Adding new flags requires careful extension of both the parse and write functions; a mismatch between the two functions would cause silent data loss.

- `input-header.py` `reset` operation hardcodes `options.minimum_questions: 0` while both `finalize-input.py` and `initialize.py` seed with `5`. This pre-existing inconsistency should be noted for the implementer, though fixing it is outside this request's scope.

- `context.md` Solution section states "verify-context.py validates context.md format compliance against context-convention.md with the 6-section check set" — should read "10-check validation set."

- `menu.py` `_SCRIPT_ACTIONS = []` is currently empty. Verify commands will be the first entries in this list, establishing the precedent for future static menu actions.

- `aib-analyze.md` S03.4 references "Read the `## Options` section of `.aib_memory/input.md`" but `minimum_questions` is stored in the YAML frontmatter, not in a body section. This is a stale reference unrelated to this request but worth noting.

- No test file exists for `verify-input.py`. Following the `tests/test_verify_context.py` pattern, a `tests/test_verify_input.py` must be created.

### Edge Cases

- **Existing input.md files without new YAML flags**: Older workspaces and request archives that pre-date this change have no `input_verification_enabled` etc. in their YAML. `parse_input_header` must default gracefully. Backward-compatible defaults must be defined explicitly. (See Decision Point `backward-compatibility-defaults`.)

- **verify-input.py called when input.md has no YAML frontmatter**: Script must handle missing frontmatter gracefully, reporting a check failure rather than raising an unhandled exception.

- **Verification enabled but script file missing**: If `input_verification_enabled` is true but `verify-input.py` does not exist (corrupt install), the analysis prompt must handle the tool invocation failure gracefully.

- **Context verification when context.md does not exist**: `verify-context.py` already handles this — it exits with code 1 and prints `[FAIL] file_exists`. The result should be written as `invalid`, not cause a crash in the caller.

- **YAML boolean serialization**: `parse_input_header` currently handles only string values. New bool flags (`true`/`false` in YAML) must be parsed as Python booleans to avoid `"true" != True` comparison bugs.

- **Concurrent runs**: If two analysis runs start simultaneously and both write `input_verification_result`, the last write wins. Acceptable given AIB's single-developer model.

- **Result field retention when verification is disabled**: When `input_verification_enabled` is false, the result field should retain its last known value rather than be cleared, to preserve audit history.

- **First-run with initialize.py**: New `_SEED_TEMPLATE` and `input_seed` must include the four flags so fresh workspaces start with correct defaults. The `--upgrade` logic in `initialize.py` restores `input.md` from archive; the archive copy may not have the new flags and must be treated with backward-compatible defaults.

- **Q-block validation scope**: Input.md in `questions_generated` state contains Q-blocks in `## Questions`. Whether `verify-input.py` validates Q-block format is a scope decision that could expand significantly. (See Decision Point `verify-input-checks-scope`.)

## Decision Register

### Decision Points

#### Decision Point: verify-input-checks-scope

- Tag: ask

- Rationale: The request describes creating a "similar" script to `verify-context.py` for `input.md`, but does not specify which checks to run. No formal `input-convention.md` exists. The scope of checks produces significantly different implementations.

- Alternatives:
  - **Option A — YAML header only**: Validate YAML frontmatter structure — required keys present (request_id, title, state, options.minimum_questions, plus new flags), state has a valid value from the allowed set, minimum_questions is a non-negative integer, verification result flags have valid values (null/valid/invalid). Simple and deterministic. (~3–4 checks)
  - **Option B — YAML + mandatory body sections**: All checks from Option A, plus: `## Input` section is present in the body, only allowed H2 headings (## Input, ## Questions, ## Options) appear, `## Questions` is present when state is `questions_generated`. (~6–8 checks)
  - **Option C — YAML + body sections + Q-block format**: All checks from Option B, plus: each Q-block in `## Questions` follows `q-block-convention.md` format (QID pattern, checkbox lines, Why-this-matters line, Answer line). (~10–15 checks)

#### Decision Point: yaml-flag-placement

- Tag: ask

- Rationale: The four new YAML flags need placement in the input.md frontmatter. Two valid structural options exist, each requiring different parse/write changes in `common.py`.

- Alternatives:
  - **Option A — Top-level keys**: Flags added as first-class keys alongside `request_id`, `title`, `state`. Flat YAML structure. Requires extending `parse_input_header` regex matching and `write_input_header` serialization directly.
  - **Option B — Nested under a new `verification:` block**: Flags grouped under `verification:` parallel to `options:`. Keys become shorter (e.g., `input_enabled`). Requires new nested-block parsing logic in `common.py`.

#### Decision Point: verify-context-result-writing

- Tag: ask

- Rationale: The request states the scripts should update their respective result flags in `input.md`. Currently `verify-context.py` is a pure validator with no write capability. Two design options exist.

- Alternatives:
  - **Option A — Scripts own result writing**: Both `verify-context.py` and `verify-input.py` accept `--workspace` and write their result flag to `input.md` directly after checks complete. Each script is self-contained.
  - **Option B — Caller owns result writing**: Verify scripts remain pure validators (exit 0/1 only). Callers (menu.py and aib-analyze.md) read the exit code and invoke `input-header.py` to write the result to `input.md`.

#### Decision Point: analysis-failure-behavior

- Tag: ask

- Rationale: When `aib-analyze.md` runs verification and the result is `invalid`, the prompt needs a defined behavior. The request does not specify whether analysis should halt or continue.

- Alternatives:
  - **Option A — Halt on invalid**: If the verification result is `invalid` after running, halt analysis with an explicit error message directing the developer to fix format violations before re-running.
  - **Option B — Warn on invalid, continue**: If result is `invalid`, output a warning note but continue analysis. The result flag captures the state for developer review.
  - **Option C — Halt only for context invalid, warn for input invalid**: Context invalidity is more severe (analysis reads context); input format issues are less severe. Different behaviors per verification type.

#### Decision Point: analysis-verification-timing

- Tag: ask

- Rationale: The request says verification should run "in the beginning of analysis prompt." The prompt has a defined step sequence; the exact insertion point affects correctness and auditability.

- Alternatives:
  - **Option A — New dedicated step S00 before S01**: Add step S00 that reads YAML flags and runs scripts before any other prompt action, including before reading `instructions.md`.
  - **Option B — Within S01 preflight, after reading instructions.md**: Insert verification as S01.1a after `instructions.md` is read (S01.1) and before `input-header.py` is invoked (S01.2). Allows `instructions.md` directives to potentially modulate verification.
  - **Option C — Between S01 and S02**: Run verification after request state is resolved (S01) but before context check (S02). The active request ID is known at this point.

#### Decision Point: refresh-context-phase1-modification

- Tag: ask

- Rationale: `aib-refresh-context.md` Phase 1 step 4 uses manual format detection; Phase 8 invokes `verify-context.py`. The request says to use the script "during context verification steps in aib-refresh-context.md." Whether this requires modifying Phase 1 or only confirming Phase 8 is ambiguous.

- Alternatives:
  - **Option A — No change to aib-refresh-context.md**: Phase 8 already invokes `verify-context.py`; that coverage is sufficient. Phase 1 step 4 is a lightweight pre-screen that does not need changing.
  - **Option B — Update Phase 1 step 4 to invoke verify-context.py**: Replace the manual format detection in Phase 1 step 4 with a call to `verify-context.py`, using its exit code to determine format compliance.

#### Decision Point: input-header-extension

- Tag: ask

- Rationale: The four new YAML flags need programmatic read/write support via CLI. Whether this capability lives in `input-header.py` or directly in the verify scripts affects the tool surface area and maintenance.

- Alternatives:
  - **Option A — Extend input-header.py CLI**: Add `--input-verification-enabled`, `--input-verification-result`, `--context-verification-enabled`, `--context-verification-result` to `input-header.py` write command; add these fields to the `read` command output.
  - **Option B — Verify scripts use common.py directly**: Verify scripts import and use `parse_input_header` / `write_input_header` from `common.py` to update their own result flag. No `input-header.py` CLI changes needed.

#### Decision Point: menu-command-visibility

- Tag: ask

- Rationale: The request says verify commands should be "available in the menu when the input verification is enabled." The exact visibility behavior (hidden vs always visible) is not specified.

- Alternatives:
  - **Option A — Hidden when disabled**: When `input_verification_enabled` is false, the `verify_input` action does not appear in the menu (same pattern as close-request conditional injection). Same logic for `verify_context`.
  - **Option B — Always visible with state indicator**: Both verify commands always appear in the menu; their title/description indicates enabled/disabled status. Selecting a disabled command shows an informational message.

#### Decision Point: backward-compatibility-defaults

- Tag: ask

- Rationale: Existing `input.md` files and archived copies do not have the four new YAML flags. When `parse_input_header` reads them, it must apply defaults. The choice of defaults affects behavior for all existing workspaces after upgrade.

- Alternatives:
  - **Option A — Default enabled flags to true, result flags to null**: Missing `input_verification_enabled` treated as `true`; missing result flags as `null`. Verification is automatically active for all upgraded workspaces, consistent with the "default: true" stated in the request.
  - **Option B — Default enabled flags to false, result flags to null**: Missing flags treated as disabled. Developers must explicitly set them after upgrade. No behavior change for existing workspaces.
  - **Option C — Raise error on missing flags**: `parse_input_header` raises `ValidationError` when new flags are absent, forcing explicit migration.
